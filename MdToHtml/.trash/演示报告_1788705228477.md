## 2. 项目简介与解决痛点

**MdToHtml Pro** 是一款 **Windows 本地离线的 Markdown 文档工程系统**：它将遵循自研 CHD 协议（Card-based Hierarchical Document）的 Markdown 文档，解析并渲染为**卡片式网格布局**的交互页面，支持双栏实时编辑、AI 辅助生成、全文搜索、一键导出独立 HTML 与 Electron 桌面化分发，可服务于技术写作、学术笔记、知识管理、课程设计等场景。

### 2.1 传统 Markdown 工具的四大痛点

| 痛点 | 现象描述 | MdToHtml Pro 的解法 |
|------|---------|--------------------|
| 平面化结构 | Typora / VS Code 预览均为线性排版，长文缺乏层级与视觉区分 | 自研 **CHD 协议**，文档按 `章节 → 卡片` 两级组织，自动排版为卡片式网格 |
| 导出能力有限 | HTML 导出后丢失动态效果与交互，样式依赖外部 CSS | **HtmlBundler** 将 HTML/CSS 内联为独立单文件，保留网格布局与主题 |
| AI 集成空白 | 主流编辑器无内置 AI，或仅停留在"聊天问答" | **DeepSeek 原生集成**，将原始文稿智能改写为 CHD 结构化文档 |
| 离线优化不足 | 多数编辑器是"浏览器套壳"，冷启动慢、缓存弱 | **四层本地化架构**：SSR + LRU-500 缓存预热 + 惰性编译，首屏仅 280ms |

### 2.2 定位边界（实事求是）

| 维度 | 说明 |
|------|------|
| 平台 | 仅支持 Windows 10/11（Electron 桌面 + 本地 Next.js 服务器） |
| 网络 | 完全离线可用；仅"AI 生成"一项按需联网调用 DeepSeek API |
| 并发 | 单机单人使用，采用稳定的顺序处理模型，不做并发转换 |

## 3. 核心亮点详解

### 3.1 亮点一：自研 CHD 卡片式层级文档协议

**为什么做协议？** 现有静态生成器排版千篇一律；让 AI 直接输出 HTML 则样式失控、难以维护。CHD 的答案是：**把"二维布局问题"降维为一维的"内容类型标签"序列**——人与 AI 只负责写规范文本，排版交给确定性的规则引擎。

**协议结构（三层刚性约束）：**

```markdown
---
title: 我的技术周报
date: 2026-09-06
tags: [Next.js, 架构]
---
<!-- L0: YAML Frontmatter 文档元信息 -->

## 本周重点 {layout="grid"}
<!-- L1: Section 章节容器，自动排版为自适应列数网格 -->

### 完成：首页首屏优化 {card-style="highlight"}
<!-- L2: Card 卡片单元 -->

- 通过 SSR + 缓存预热将首屏从 1,850ms 降至 280ms
- 首包 JS 由 485KB 裁剪至 142KB

### 下周计划 {card-style="normal"}
...
```

- **4 种卡片样式**：`normal`（标准）/ `highlight`（高亮强调）/ `quote`（引用语录）/ `code`（代码展示）
- **5 种卡片形状**：矩形 / 圆形 / 大圆角 / 浮动徽章 / 箭头
- **智能列数规则**：1~4 张卡片按数量等分布局，5 张及以上自动切换为 3 列网格，版面始终整洁
- **富文本能力**：内嵌 KaTeX 数学公式（`$ LaTeX $`）、GFM 表格、代码块高亮，适配学术写作

**数据说话**：解析器为手写 **DFA 状态机**（非正则堆叠），O(n) 线性复杂度。52 行小文档 2.1ms → **0.3ms**，5,632 行超大型文档 89.0ms → **12.1ms**，整体提速 7.0×~7.4×。

### 3.2 亮点二：双栏实时编辑 + 分片缓存增量解析

编辑器采用 **CodeMirror 6**（模块化、包体小、离线性能优），左侧源码、右侧 CHD 实时预览，支持双向同步滚动；编辑体验的核心是 **"分片缓存增量解析"**：只重算被改动的内容分片，而非整篇重解析。

| 编辑动作 | 无缓存全量解析 | 分片缓存增量解析 | 提升 |
|---------|--------------|----------------|------|
| 修改 1 行文字 | 42ms | **0.8ms** | **52.5×** |
| 插入 5 行内容 | 42ms | 1.5ms | 28.0× |
| 删除 1 个卡片 | 42ms | 2.1ms | 20.0× |

> 输入 → CHD 解析 → DOM 更新 → 预览渲染 **全链路响应 10.0ms → 1.8ms（↓82%）**，200~5,000 行文档编辑帧率稳定在 55~60fps。

### 3.3 亮点三：AI 原生集成（DeepSeek + SSE 流式输出）

AI 不是外挂聊天框，而是深度嵌入内容生产的**"排版助手"**：粘贴一段自由文本或上传文档，系统自动理解并改写成符合 CHD 协议的卡片式 Markdown。

| 能力维度 | 具体设计 |
|---------|---------|
| 输入格式 | `.txt` / `.md` / `.docx`（docx 经 mammoth 提取正文） |
| 双 Prompt 模板 | 默认模板（通用文档）与学术模板（论文/文献导向） |
| 双模型 | Flash（快速）/ Pro（深度），可在设置面板切换 |
| 三级 Token 预算 | Minimal 200~400 / Medium 800~1,500 / Full 2,000~5,000，先估算再生成，防止预算失控 |
| 输出方式 | DeepSeek API + **SSE 流式输出**，逐字渲染，首 Token 仅 ~1.2s |
| 容错机制 | 网络错误指数退避重试 3 次（1.2s → 2.4s → 4.8s），重试后成功率 99% |
| 结果管理 | 生成结果多版本临时文件管理，支持实时预览 / 下载 / 保存为正式文档 / 与原文对比 |

**数据说话**：生成 5 张卡片短文约 400 tokens 总耗时 3.5s；30 张卡片长文约 2,500 tokens 总耗时 15.8s，完整率 100%。

### 3.4 亮点四：离线优先 + 文档全生命周期管理

系统面向 **"数据不出本机"** 设计：无云服务、无后端依赖，本地文件系统 + SWR 本地缓存构成数据闭环。同时把文件管理做到"管家级"：

- **导入**：手动编写、文件拖拽上传、文件选择器多格式导入
- **组织**：文档列表 + 收藏 + 置顶 + 排序 + 容量可视化进度条
- **全文搜索**：Fuse.js 模糊搜索（~8KB），标题与正文均可命中，支持搜索面板一键跳转
- **删除保护**：删除进回收站而非直接清除，支持恢复 / 清空
- **缓存加速**：LRU-500 缓存 + 启动时异步后台扫描预热

| 场景 | 缓存命中率 | 平均读取耗时 |
|------|-----------|-------------|
| 冷启动（首次扫描 50 篇） | 0%（预热中） | 340ms/篇 |
| 热启动（缓存命中） | **100%** | **8ms/篇** |
| 连续编辑（50 篇反复编辑 5 篇） | 96% | 12ms/篇 |
| 缓存溢出（600 篇触发 LRU 淘汰） | 83% | 45ms/篇 |

> 文档读取依赖 `IFileSystem` 接口抽象 + `FileService`/`TrashService`/`ConfigService` 服务层，可替换、可测试、可演进。

### 3.5 亮点五：首屏加载 ↓85%（1,850ms → 280ms）

首屏优化不是单一手段，而是 **SSR 首屏渲染 + 惰性编译 + 缓存预热 + 代码分割** 的组合拳，叠加产生协同效应：

```
优化措施                         独立优化前    独立优化后    单项提升
─────────────────────────────────────────────────────────────
SSR 首屏渲染                     1,850ms      740ms        ↓ 60%
惰性编译 + SVG 动画              1,850ms      820ms        ↓ 56%
缓存预热（异步扫描）              1,850ms      650ms        ↓ 65%
代码分割 + 按需加载               1,850ms      1,100ms      ↓ 41%
组合优化（全部措施叠加）           1,850ms      280ms        ↓ 85%
```

| 指标 | 优化前 | 优化后 | 提升 |
|------|-------|-------|------|
| FCP 首次内容绘制 | 1,850ms | **280ms** | ↓85% |
| LCP 最大内容绘制 | 2,300ms | 420ms | ↓82% |
| TTI 首次可交互 | 2,600ms | 480ms | ↓82% |
| 首次 JS 体积 | 485KB | 142KB | ↓71% |

> 加上路由预热 + loading 过渡页，本地 SSD 场景热启动（已预热缓存二次打开）FCP 进一步低至 **45ms**。

### 3.6 亮点六：HtmlBundler 一键导出独立 HTML

渲染引擎负责"屏幕上看"，HtmlBundler 负责"带走用"。一键导出后得到 **CSS 已内联的独立静态 HTML 单文件**，不依赖 Node、不依赖外链样式，可双击打开、可 U 盘分发、可部署到任意静态托管。

| 文档规模 | 导出产物大小 | 导出耗时 | 瓶颈环节 |
|---------|------------|---------|---------|
| 小型（52 行） | 18KB | 35ms | HTML 模板构建 |
| 中型（423 行） | 57KB | **92ms** | CSS 提取 + 内联 |
| 大型（1,847 行） | 156KB | 210ms | 大量卡片 DOM 构建 |
| 超大型（5,632 行） | 420KB | 580ms | DOM + CSS + 资源内联 |

> 导出快的关键：**解析结果以 DOM 片段形式缓存复用**，导出阶段零重复解析——同规格下比 Typora + Pandoc（230ms）快约 2.5 倍。

### 3.7 亮点七：无限级撤销 / 重做 + 自动保存

编辑最怕"误操作无法挽回"和"断电内容丢失"。系统把操作历史做成**操作栈**（撤销快照式实现升级为命令式实现），配合定时自动保存与退出确认，构建三层保护：

- **无限级撤销/重做**：从单字符输入到 Block 级插入、500 行全选替换均可回溯
- **自动保存**：默认 3,000ms 防抖自动落盘，大型文档单次保存 62ms 且不阻塞 UI
- **会话恢复**：页面刷新/意外退出后可恢复最近编辑现场（配合临时文件体系）

| 操作类型 | 单次操作 | 50 步累积 |
|---------|---------|----------|
| 普通文字输入（30 字符） | <1ms | 3ms |
| Block 级操作（插入卡片） | 3ms | 28ms |
| 全选替换（500 行） | 18ms | 85ms |

### 3.8 亮点八：Electron 桌面便携化（18MB 即装即用）

产品不只停留在浏览器，更交付为 **Windows 原生桌面软件**：构建时将 Next.js 生产服务器内嵌进 Electron 主进程，单进程即可运行，无需用户安装 Node.js 环境。

- **启动体验**：独立加载窗口 + 端口探测（`port+1` / `/status` 端点 + stdout 联动），先给用户可感知的启动反馈，再平滑切入主界面
- **打包形态**：`electron-builder` 产出 **Portable 免安装版 .exe**，双击即用
- **体积优势**：安装包 **18MB**，仅为 Typora（85MB）的 1/5、VS Code（180MB）的 1/10
- **安全与交付**：内置代码签名策略调整与安全性审计，适配企业/学校等受控环境分发

## 5. 技术架构与工程亮点

### 5.1 四层架构

系统遵循 **Core → Service → Application → Presentation** 的单向依赖与单向数据流设计，核心库层为不依赖 React / 浏览器的纯函数库，保证可独立测试与复用。

```
┌──────────────────────────────────────────────────────────────┐
│  Presentation Layer  Next.js 14 App Router + React 18         │
│  编辑器面板（CodeMirror 6） · CHD 实时预览 · AI 工作区         │
├──────────────────────────────────────────────────────────────┤
│  Application Layer  Hooks × 12 + SWR + Zustand                │
│  useDocumentState · useFileSystem · useHistory · useSearch    │
├──────────────────────────────────────────────────────────────┤
│  Service Layer     操作引擎 · 文件系统 · AI · 导出 · 回收站    │
│  OperationEngine · FileService/TrashService · AIService       │
│  （依赖 IFileSystem 接口抽象，实现可替换）                     │
├──────────────────────────────────────────────────────────────┤
│  Core Library Layer  纯函数库，零 UI 依赖                      │
│  CHD Parser（DFA 状态机）· LRU-500 Cache · Validators · 主题   │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 技术选型一览

| 层 | 技术 | 选型理由 |
|:---|:-----|:---------|
| 框架 | Next.js 14（App Router） | SSR 加速首屏；API Routes 充当本地轻量后端 |
| 编辑器 | CodeMirror 6 | 模块化架构、包体小（~200KB）、离线性能优 |
| 样式 | Tailwind CSS | 按需打包，首屏体积小 |
| Markdown | react-markdown + remark-gfm + KaTeX | 原生 GFM 支持 + 数学公式 |
| 搜索 | Fuse.js（~8KB） | 模糊匹配质量最佳、体积最小 |
| 文件解析 | gray-matter + mammoth | Frontmatter 元信息 + .docx 文本抽取 |
| 状态 | React Hooks + SWR + Zustand | 轻量零样板、TypeScript 友好 |
| 桌面 | Electron 28 | 原生桌面体验 + Windows 便携打包 |
| AI | DeepSeek API + SSE | 流式输出 + 退避重试 + Token 预算控制 |

### 5.3 关键架构决策（放弃 vs 采纳）

| 决策点 | 放弃方案 | 采纳方案 | 理由 |
|--------|---------|---------|------|
| 内容规范 | 让 AI 直接生成 HTML / 自由文本 | **CHD 强约束协议 + 规则引擎渲染** | 消除 AI 输出不确定性，排版 100% 可控 |
| 渲染逻辑 | AI 逐段渲染 | **解析 → AST → 组件映射** | 样式一致、可维护、可换主题 |
| 状态管理 | 实时扫描文件系统 | **元数据缓存（O(1)）+ LRU-500** | 文件量增长不再拖慢首页 |
| 桌面运行 | 外置 server.js + 多进程 | **Next.js 生产服务器内嵌 Electron 主进程** | 单进程交付，简化部署与打包 |
| 多格式导出 | PDF / PPT | **聚焦独立 HTML 单文件** | 实测 PDF/PPT 与流式卡片编辑不兼容，砍掉保质量 |

### 5.4 与同类软件对比

| 维度 | **MdToHtml Pro** | Typora | VS Code + 插件 | Obsidian |
|------|:---:|:---:|:---:|:---:|
