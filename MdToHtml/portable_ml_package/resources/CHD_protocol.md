## 1. 协议概述 (Core Philosophy)

**"Structure First, Content Condensed" (结构优先，内容精炼)**

CHD (Card-based Hierarchical Document) 是一套专为降低 AI 理解成本并提升人类写作结构化程度而设计的文档工程协议。其核心理念是将非结构化的“文本流”转化为结构化的“语义卡片流”。

### AI 的角色定义
*   **❌ 不是**: 简单的文本搬运工（不要直接复制粘贴长段落）。
*   **✅ 而是**:
    *   **信息架构师**: 将线性文本重构为网格化的卡片结构。
    *   **UI 设计师**: 根据内容的重要性选择合适的 `layout` (布局) 和 `card-style` (样式)。
    *   **数据分析师**: 从文本中提取关键指标，通过 `highlight` 卡片进行可视化呈现。

## 2. 文档结构定义 (L0-L3)

CHD 协议定义了严格的三级刚性结构，禁止四级及更深层级。

### L0: 文档根节点 (Document)
文档必须以 YAML Frontmatter 开头，定义元数据。

```yaml
---
title: "文档主标题"       # 必填，对应 L1 概念
subtitle: "副标题"        # 必填，一句话概括核心价值
tags: ["标签1", "标签2"]  # 必填，3-5个核心关键词
version: "2.0"            # 协议版本
status: "done"            # 选填，done/wip
training_sample: true     # 选填，标识是否为高质量样本
---
```

### L1: 章节节点 (Section)
使用二级标题 (`##`) 定义章节。章节是文档的逻辑分割单位。

**约束规则：**
- 必须使用 `## ` 开头。
- 标题文本应简洁，作为该逻辑块的核心总结。
- 章节下不能直接包含正文文本，必须包含 L2 卡片。
- **强制布局**: 必须使用 `{layout="grid"}`。其他布局 (`single`, `gallery`) 在 v2.0 中已**暂时锁定**，所有内容强制使用 Grid 布局以保证一致性。

### L2: 卡片节点 (Card)
使用三级标题 (`###`) 定义卡片。卡片是内容的最小语义单元。

**约束规则：**
- 必须使用 `### ` 开头。
- 标题即卡片名称。
- 卡片包含具体的内容块（文本、代码、列表、图表）。
- **禁止**在卡片内使用四级标题 (`####`)。
- 一个卡片对应一个独立的语义点（Concept, Example, Metric 等）。

### 结构示意图
```
[Document L0]
  ├── [Metadata]
  ├── [Section L1] "## 研究背景" {layout="grid" columns=2}
  │     ├── [Card L2] "### 传统方法局限" (Text)
  │     └── [Card L2] "### 核心洞察" (Text)
  ├── [Section L1] "## 实验结果" {layout="grid" columns=3}
  │     ├── [Card L2] "### 准确率对比" (Chart/Metric)
  │     └── [Card L2] "### 性能提升" (Data)
```

## 3. 扩展语法 DSL

为了支持更丰富的布局和语义，CHD 支持在标题后使用扩展属性语法 `{key="value"}`。

### 3.1 布局控制 (Layout)
应用于 Section (`##`)，控制其下 Cards 的排列方式。

```markdown
## 方法设计 {layout="grid" columns=2}
## 实验结果 {layout="grid" columns=3 section-color="chart-1"}
```

*   **`layout`**:
    *   `"grid"`: 网格布局（默认且强制）。适合展示多个并列的观点、特征或数据。
*   **`columns`**: (仅在 grid 布局下有效)
    *   **智能列数规则 (Smart Columns)**:
        *   **1-4 张卡片**: 列数 = 卡片数量 (1->1, 2->2, 3->3, 4->4)。
        *   **5张及以上**: 强制分行，每行 3 列 (如 5 张 -> [3, 2], 6 张 -> [3, 3])。
        *   **最大列数**: 4 (仅当卡片数为 4 时)。
*   **`section-color`**: (选填)
    *   `"chart-1"` 到 `"chart-5"`: 应用莫兰迪主题色背景。
    *   `"default"`: 默认背景。

### 3.2 卡片样式与形态 (Card Style & Shape)
应用于 Card (`###`)，定义卡片的视觉呈现语义。

```markdown
### 核心性能 {card-style="highlight"}
### 用户评价 {card-style="quote"}
### 算法实现 {card-style="code"}
```

**支持的样式类型 (`card-style`)：**
1.  `normal`: 标准卡片（默认）。适合一般性描述。
2.  `highlight`: 高亮卡片。适合核心观点、重要结论、关键数据（如 "**SOTA +2.5%**"）。
    *   **注意**: v2.0 已移除 `stat` 样式，请使用 `highlight` 代替。
3.  `quote`: 引用卡片。适合名言、用户评价、设计理念。
4.  `code`: 代码卡片。**严格限制**！仅限于展示代码块、伪代码、命令行或配置文件。
    *   **禁止滥用**: 严禁将普通文本内容设置为 `code` 样式以试图获得特殊高亮（请使用 `highlight` 或 `quote`）。非必要不使用！

**支持的尺寸属性：**
- `row-span`: 跨行数 (默认为 1，可设为 2 以展示竖向内容)。
- **[v2.1 更新] `col-span` (跨列)**: **已弃用 (Deprecated)**。为了保证视觉统一性，所有卡片宽度必须完全一致。禁止 AI 为卡片指定 `col-span` 属性。

## 4. 禁止规则 (Strict Constraints)

为了保证 AI 解析的确定性，以下行为被严格禁止：

1.  **禁止四级标题**：`####` 及更深层级标题是非法的。如果需要更细粒度，请拆分为新的卡片或使用列表。
2.  **禁止孤儿文本**：`## Section` 下方必须紧跟 `### Card`，不允许在 `##` 和 `###` 之间直接书写正文。
3.  **禁止混合层级**：文档必须严格遵循 L0 -> L1 -> L2 的层级顺序。
4.  **禁止隐式结构**：不要使用粗体或字号大小来模拟标题，所有结构必须通过 `##` / `###` 显式声明。
5.  **禁止滥用代码样式**：`card-style="code"` 仅限于展示代码块、伪代码、命令行或配置文件。禁止将普通文本内容设置为 `code` 样式以试图获得特殊高亮。

## 5. 最佳实践 (Best Practices)

为确保文档的可读性与美观性，建议遵循以下实践（源自 FORMAT_SPEC 经验）：

### 5.1 核心原则
1.  **Section 综述**：由于禁止孤儿文本，若需对章节进行综述，请在章节下的第一个位置创建一个 `### 综述 {card-style="normal"}` 的卡片。
2.  **字数控制**：单个卡片（Card）的内容建议不超过 **200 字**。若内容过长，请考虑拆分为多个维度的卡片（如“原理”、“实现”、“优缺点”）。
3.  **拒绝“光杆司令”**：尽量避免一个 Section 下只有一个 Card。若内容较少，可考虑合并 Section。

### 5.2 特定场景处理
1.  **论文摘要 (Abstract)**:
    *   不要直接复制一大段摘要文本。将其拆解为 `## 核心亮点` 或 `## 论文概览`。
    *   将“背景”拆为一个卡片，“贡献”拆为 2-3 个 `highlight` 卡片。
2.  **实验数据 (Experiments)**:
    *   不要仅仅列出表格。使用 `highlight` 卡片展示最关键的提升指标。
    *   使用 `normal` 卡片解释数据背后的原因。
3.  **技术架构 (Architecture)**:
    *   不要用纯文本描述流程。使用 `code` 样式卡片展示模块名称或伪代码。
    *   使用 `columns=3` 的网格布局，按逻辑顺序排列。

### 5.3 视觉一致性 (Visual Consistency)
1.  **Section 内部一致性**: 同一个 Section 下的 Card 样式应尽可能保持统一。例如，如果 Section 是关于“核心概念”的，建议全部使用 `normal` 或 `highlight`；如果是“代码实现”，则全部使用 `code`。避免在一个逻辑段落内无意义地混用多种样式。
2.  **特殊区域例外 (Footer Exceptions)**: 对于文档的结尾部分（如“引言”、“总结”、“参考文献”），允许其样式与正文部分不同。例如，可以使用 `card-style="quote"` 来突出总结性陈述。

## 7. 内容原子化与布局规范 (Content Atomicity & Layout)

为了确保生成的文档能够被 CHD 引擎完美渲染，必须遵循**原子化**原则。

### 7.1 原子化原则 (Atomicity Principle)
**"One Card, One Point" (一卡一义)**

*   **禁止单体巨石 (No Monolithic Cards)**: 严禁将整个章节的所有内容（如多个无序列表项、多段长文本）塞进同一个 `###` 卡片中。这会导致卡片高度过大，破坏 Grid 布局的紧凑性。
*   **拆解策略**:
    *   遇到含有多个 `h4` 或加粗标题的段落，应拆分为多个独立的 `###` 卡片。
    *   遇到长列表（超过 5 项），应考虑按逻辑分组拆分为多个卡片。

**错误示例 (Anti-Pattern):**
```markdown
### 技术架构详情
- 前端使用 Next.js...
- 后端使用 Python...
- 数据库使用 PostgreSQL...
- 缓存使用 Redis...
(内容过长，导致必须 col-span=3，挤占整行)
```

**正确示例 (Best Practice):**
```markdown
### 前端架构
- Next.js SSR
- Tailwind CSS

### 后端架构
- Python FastAPI
- Celery Task Queue

### 数据存储
- PostgreSQL
- Redis Cache
(三个小卡片并排显示，布局紧凑)
```

### 7.2 智能尺寸与流式布局
CHD 引擎内置了智能算法，会根据文本量自动分配 `col-span`。

*   **默认行为**: 不指定 `col-span` 时，引擎会自动判断。
    *   短文本 -> `span-1`
    *   中长文本 -> `span-2`
*   **显式覆盖**: 仅在需要特殊视觉效果（如全宽横幅、代码块）时才手动指定 `col-span`。
*   **交替节奏**: 推荐在文档中交替使用长短不一的卡片，以激活引擎的“马赛克布局”能力，避免单调的网格排列。
