# 2026-02-21 单文件导出与主题修复

## 1. 核心变更
- **单文件导出升级**: 彻底移除了基于服务端的导出 API，全面转向基于客户端的 `HtmlBundler` 方案。实现了“编辑分离、导出内聚”的核心理念。
- **主题一致性修复**: 解决了导出 HTML 文件在不同系统偏好下（如 Dark Mode 系统 + Light Mode 编辑器）显示异常的问题。现在导出文件会严格继承编辑器当前的主题状态。
- **UI 优化**: 将导出按钮从页面悬浮位置迁移至顶部工具栏，与“保存”、“预览”等操作并列，提升了操作的一致性和便捷性。

## 2. 问题分析与修复 (Root Cause Analysis)
### 2.1 导出文件样式异常 (White Cards on Dark Background)
- **现象**: 用户在 Light Mode 下导出，但生成的 HTML 文件背景为黑色，且卡片背景为白色，导致高反差视觉错误。
- **原因**: 
    1.  `HtmlBundler` 使用的 `template.ts` 包含一段自动检测系统 `prefers-color-scheme` 的脚本。如果用户系统是 Dark Mode，导出文件会自动添加 `dark` 类。
    2.  与此同时，`Card` 组件的默认背景色是 `bg-white` (Tailwind)，这在 Light Mode 下正常，但在 Dark Mode 下会导致“黑底白块”。
    3.  `HtmlBundler` 在打包时并未捕获当前应用的主题状态 (`theme` context)。
- **修复**:
    1.  改造 `HtmlBundler.bundle` 方法，增加 `theme` 参数。
    2.  在 `template.ts` 中引入动态脚本注入机制。
    3.  当传入明确的 `light` 或 `dark` 主题时，生成的 HTML 会强制应用该主题类，忽略系统偏好。

### 2.2 功能入口不统一
- **现象**: 编辑器页和预览页的导出逻辑不一致，且使用了悬浮按钮，容易遮挡内容。
- **修复**:
    1.  统一在 `EditorPage` 和 `InteractivePost` 中使用 `HtmlBundler`。
    2.  将导出按钮移至 Top Bar，移除悬浮按钮组件。

## 3. 技术细节
- **文件**: `src/lib/export/HtmlBundler.tsx`
- **变更**:
    ```typescript
    // Before
    static async bundle(markdown: string, title: string): Promise<Blob>
    
    // After
    static async bundle(markdown: string, title: string, theme: string = 'system'): Promise<Blob>
    ```
- **模板注入**:
    ```javascript
    // Injected Script Logic
    if (theme === 'dark') document.documentElement.classList.add('dark');
    else if (theme === 'light') document.documentElement.classList.remove('dark');
    ```

## 4. 后续规划
- **图片内联**: 目前仅处理了文本和样式，后续需在 `HtmlBundler` 中增加图片转 Base64 的逻辑，实现完全离线的单文件分发。

## 5. 卡片组件深色模式修复 (Card Dark Mode Fix)
- **问题**: 导出文件在深色模式下显示为“黑底白卡片”，原因是 `Card` 组件样式硬编码为 `bg-white`，未适配深色模式。
- **修复**:
    - 修改 `src/components/CHD/Card.tsx`: 将默认样式从 `bg-white` 改为 `bg-card` (Tailwind 语义化颜色)。
    - 修改 `src/app/globals.css`: 在 `.dark` 类中补充 `--border-soft` 定义，确保边框颜色在深色模式下正确显示。

# 2026-02-21 单文件导出与同步机制

## 1. 背景与目标
为了满足“单个网页文件表示一个网页”的需求，并将编辑器中完美的渲染效果（内联样式、动态计算）完整复刻到静态输出目录 `output/` 中，我们需要重构导出流程。

## 2. 核心变更

### 2.1 静态导出结构调整
- **配置修改**: 在 `next.config.js` 中将 `trailingSlash` 从 `true` 改为 `false`。
- **效果**: Next.js 构建产物从 `output/slug/index.html` 变为 `output/slug.html`，实现了扁平化的单文件结构。

### 2.2 客户端-服务端同步导出机制 (Client-Server Sync)
由于服务端构建（`npm run build`）无法完全模拟浏览器的动态渲染（如 CSS 变量计算、客户端组件交互），导致静态产物可能出现样式缺失或内容空白。为此，我们实现了**所见即所得**的同步导出机制：

1.  **前端 (Client)**: 
    - 利用 `HtmlBundler` 在浏览器端抓取当前的 DOM 和 CSSOM。
    - 生成包含内联样式和脚本的自包含 HTML Blob。
    - 触发浏览器下载（用户侧备份）。
    - **同步发送**: 将生成的 HTML 内容通过 POST 请求发送给后端 API。

2.  **后端 (Server)**:
    - 新增 API `/api/save-export`。
    - 接收前端发送的 HTML 内容。
    - 自动清理文件名（去除非法字符）。
    - 将文件同步写入 `output/` 目录。

### 2.3 输出目录治理
为了保持 `output/` 目录的整洁，我们实施了严格的清理策略：
- **系统页面归档**: `index.html`, `404.html`, `editor.html` 等非内容页面被移动到 `output/system/` 子目录。
- **冗余清理**: 自动删除 `_next` 静态资源目录（因样式已内联）、`.txt` 数据文件和 `api` 目录。
- **文件名解码**: 自动将 URL 编码的文件名（如 `%E4%B8%AD...html`）重命名为中文文件名。

## 3. 结果
- `output/` 根目录现在只包含与 `input/` 对应的 Markdown 文章的 HTML 版本。
- 导出的 HTML 文件完全独立，不依赖外部 CSS/JS 文件，且渲染效果与编辑器完全一致。

## 4. Git 工作流与文件管理反思

### 4.1 分支切换冲突与解决
在本次开发过程中，我们在切换分支时遇到了阻碍。
- **问题**: 在尝试从 `feature/single-file-web` 切换回 `master` 时，由于 `scripts/process_single_file.js` 存在未提交的修改，导致 Git 拒绝切换分支 (`error: Your local changes to the following files would be overwritten by checkout`).
- **解决**: 必须先提交 (`git commit`) 或暂存 (`git stash`) 当前分支的修改，确保工作区干净 (clean) 后再执行 `git checkout`。
- **教训**: 在进行分支操作前，务必使用 `git status` 检查工作区状态。

### 4.2 运行时生成文件的版本控制策略
我们观察到大量运行时生成的文件被纳入了版本控制，导致 `git status` 输出混乱，掩盖了真实的代码变更。
- **data/ 目录**: 包含 `history.json`, `metadata.json`, `output.md` 等中间产物。这些文件随程序运行频繁变化，且属于用户数据或缓存，**不应提交到代码库**。
- **input/ 目录**: 包含用户的 Markdown 源文件。如果是通用工具项目，用户文档应作为私有数据被忽略（保留 `.gitkeep` 或示例文件除外）。
- **output/ 目录**: 包含构建生成的 HTML 文件。构建产物通常不应入库，除非用于特定部署目的。
- **根目录残留**: 旧版本的 HTML 文件（如 URL 编码文件名）残留在根目录，应及时清理。

**改进措施**:
1.  更新 `.gitignore`，显式忽略 `data/`、`input/`（保留结构）、`output/` 及根目录生成的 HTML。
2.  使用 `git rm --cached -r <dir>` 从版本库中移除上述目录的跟踪，但保留本地文件，确保用户数据不丢失。
3.  定期清理根目录下的临时文件。

# 2026-02-21 导出还原度优化

## 问题描述
用户反馈导出后的网页与编辑器预览存在明显差异：
1. **卡片颜色不对**：默认背景色为纯白，未跟随主题配置。
2. **页面宽度不对**：导出页面过窄，未能还原编辑器的宽屏体验。
3. **主题失效**：自定义主题（如 Ocean, Mint）在导出文件中未生效。

## 解决方案

### 1. 主题严格同步 (Theme Injection)
- **原理**：在 `HtmlBundler` 中捕获当前编辑器的 `theme` 状态（如 `ocean`）。
- **实现**：将 `theme` ID 注入到 HTML 模板的 `<html>` 标签中：`<html data-theme="ocean">`。
- **效果**：确保 CSS 变量（如 `--bg-page`, `--chart-1`）正确解析为当前主题的颜色值。

### 2. 布局容器升级 (Layout Container)
- **原理**：调整导出页面的容器宽度，使其更接近编辑器的视觉体验。
- **修改**：
  - `max-width` 从 `64rem` (1024px) 增加至 `90rem` (1440px)。
  - 添加 `min-height: 100vh` 确保背景色铺满全屏。
  - 统一 Padding 为 `2rem`，与编辑器预览保持一致。

### 3. 卡片样式修正 (Card Style Fix)
- **原理**：修正卡片组件的默认背景色类名。
- **修改**：
  - 将 `Card.tsx` 中的默认背景色从 `bg-card` (Shadcn默认) 修改为 `bg-bg-card` (项目自定义)。
  - **原因**：项目使用了自定义的 `--bg-card` 变量来控制卡片背景，而 `bg-card` 映射到了未被主题覆盖的 `--card` 变量。
  - **效果**：卡片背景色现在完全遵循用户定义的颜色配置。

## 验证方法
1. 在编辑器中切换不同主题（如 Ocean, Mint）。
2. 点击“导出 HTML”。
3. 打开导出的 HTML 文件，检查：
   - 背景色是否与编辑器一致。
   - 卡片颜色是否正确。
   - 页面宽度是否宽敞（90rem）。
