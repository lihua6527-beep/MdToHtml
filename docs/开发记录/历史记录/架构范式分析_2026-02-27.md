# 前端架构范式演进分析：从原型到工程化

**日期**: 2026-02-27
**标签**: 架构设计, 服务层, 状态管理, SWR

## 1. 背景：为什么早期架构显得“凌乱”？

在项目的初始阶段（原型期），代码往往呈现出一种“凌乱”的状态，表现为：
- 组件内部充斥着大量的 `fetch` 调用。
- 状态更新依赖手动刷新（`window.location.reload()` 或 `router.refresh()`）。
- 错误处理分散在各个 `try-catch` 块中。

**这种现象的深层原因并非仅仅是“代码质量差”，而是特定的工程权衡：**

1.  **速度优先 (Time-to-Market)**：
    在需求不明确的早期，直接在组件中写数据获取逻辑是最快的路径。开发者不需要在 `api/`, `services/`, `hooks/`, `types/` 之间来回切换，思维连贯性强。
    
2.  **认知负荷 (Cognitive Load)**：
    对于简单的 CRUD 操作，引入 Service 层和 Custom Hooks 看起来像是过度设计（Over-engineering）。直接看到 `fetch('/api/users')` 比看到 `UserService.getUsers()` 更直观，尤其是在没有复杂业务逻辑的时候。

3.  **敏捷迭代 (Agile Iteration)**：
    早期 API 变动频繁，如果封装层过厚，每次后端改接口都需要修改多个文件。直接调用的方式修改成本最低。

**结论**：早期的“凌乱”是**战术上的妥协**，为了换取开发的灵活性和速度。

## 2. 演进：为什么分层架构（Service + SWR）能提升稳定性与效率？

随着项目规模的扩大和功能的复杂化，早期的“战术妥协”开始变成“技术债务”。引入统一的服务层（Service Layer）和状态管理库（如 SWR）解决了以下核心问题：

### 2.1 关注点分离 (Separation of Concerns)
- **UI 层 (Components)**：只负责渲染数据和响应用户交互，不再关心数据是从哪里来的、怎么获取的、失败了怎么办。
- **服务层 (Services)**：负责与后端的通信协议、数据转换、错误归一化。
- **状态层 (SWR Hooks)**：负责数据的缓存、自动刷新、去重、乐观更新。

**收益**：
- **可维护性**：后端接口变更时，只需修改 Service 层，无需搜索整个项目。
- **可测试性**：可以单独对 Service 层进行单元测试，而不依赖 UI 环境。

### 2.2 统一的副作用管理 (Unified Side Effects)
- **错误处理**：在 Service 层的基类（如 `ApiClient`）中统一处理 401 未登录、500 服务器错误、网络超时等，配合全局 Toast 组件，用户体验一致且友好。
- **请求拦截**：可以在统一入口自动注入 Token、Request ID 等元数据。

### 2.3 状态自动同步 (Automatic State Sync)
这是 SWR/React Query 带来的最大范式转变：**从命令式（Imperative）转向声明式（Declarative）。**

- **旧模式**：用户点击删除 -> 等待 API 成功 -> 手动操作 DOM 或重新调用 `fetchList()`。容易遗漏，且逻辑分散。
- **新模式**：用户点击删除 -> API 成功 -> 自动触发 `mutate('key')` -> 所有订阅该 Key 的组件自动更新。
- **乐观更新 (Optimistic UI)**：先在界面上显示操作成功，后台再发送请求，极大提升用户感知的流畅度。

## 3. 架构范式总结：从“脚本式”到“系统化”

| 维度 | 原型期 (Script-style) | 工程期 (Systematic) |
| :--- | :--- | :--- |
| **数据获取** | 组件内直接 `fetch` | 封装 `Service` + `useSWR` |
| **状态同步** | 手动刷新 / EventBus | 自动变异 (Auto Mutation) / 响应式流 |
| **错误处理** | `console.error` / `alert` | 统一拦截器 / Toast / Error Boundary |
| **类型安全** | `any` / 弱类型 | 严格 TypeScript 接口定义 (`DTO`, `VO`) |
| **复用性** | 复制粘贴代码块 | 组合式 Hooks / 高阶组件 |

**建议**：
在未来的项目中，即使是初期，也建议**轻量级地**引入 Service 层和类型定义。现代脚手架（如我们生成的 Skill）可以自动化生成这些样板代码，从而在不牺牲初期开发速度的前提下，保留良好的架构扩展性。
