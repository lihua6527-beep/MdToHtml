# 运行架构澄清计划

> **创建日期**: 2026-07-10 | **优先级**: P2 | **状态**: 计划中

---

## 一、背景与问题

系统审计发现项目的运行架构存在根本性矛盾，影响开发、测试和部署。

### 1.1 静态导出与动态 API 的矛盾

| 问题 | 详情 |
|:-----|:------|
| `next.config.js` | 设置了 `output: 'export'`（SSG 静态导出模式） |
| 但系统依赖 | **24 个 API Route Handlers** 进行文件读写、回收站操作、AI 生成等 |
| 实际运行时 | 通过 `start.bat` 启动 `next dev`（开发模式），API Routes 才能工作 |
| 构建后 | `next build` 生成的 `out/` 目录**不含 API 服务**，静态 HTML 页无法执行文件写入 |

### 1.2 数据流向不清晰

文件系统访问存在**两条并行路径**，容易导致状态不一致：

```
路径 A（API 方式）：Component → FileService → ApiClient → /api/* Route → 文件系统
路径 B（直接方式）：page.tsx/SSR → lib/posts.ts → MetadataCacheManager → 文件系统
```

- `FileService.ts` 调用 API Route 写入文件
- `lib/posts.ts` 直接调用 `fs.readFileSync` 读取文件
- `lib/data-collector.ts` 也直接调用文件系统
- 写入和读取之间可能缓存不一致

### 1.3 测试欺骗性

| 问题 | 详情 |
|:-----|:------|
| 17 个测试套件中 | 部分因 API 请求失败而跳过，但测试报告显示"通过" |
| `npm test` | 运行时 API Route 不可用（Jest 不启动 Next.js） |
| 开发者容易误判 | 看到绿色 ✅ 以为所有测试通过 |

## 二、方案设计

### 2.1 核心决策：明确运行时模式

从以下两种模式中选择一种，**必须二选一并一致执行**：

#### 方案 A：纯静态模式（移除 API 依赖）

| 项目 | 说明 |
|:-----|:------|
| 架构 | 保留 `output: 'export'`，所有文件操作改为直接文件系统访问 |
| 变更 | 移除全部 API Routes，FileService/TrashService 改为直接调用 lib/ 下的工具库 |
| 优势 | 真正离线可用，`next build` 产物可直接独立运行 |
| 代价 | 需要修改 FileService、TrashService、ConfigService 的实现 |
| 影响范围 | 约 10 个文件 |

#### 方案 B：动态模式（移除静态导出）

| 项目 | 说明 |
|:-----|:------|
| 架构 | 移除 `output: 'export'`，改为 `next dev` 或 `next start` |
| 变更 | 在 README 和索引中澄清运行模式，不再误导"静态导出" |
| 优势 | 保留全部 API Route 能力，改动最小 |
| 代价 | 无法在无 Node.js 环境运行，构建产物依赖后端 |
| 影响范围 | 约 3 个文件 |

### 2.2 数据流向统一

无论选择哪种模式，都需要统一数据流向：

```
当前（混乱）：
Component <-> FileService <-> API Route <-> 文件系统
page.tsx         <-> lib/posts.ts  <-> 文件系统
lib/data-collector.ts              <-> 文件系统

目标（统一，以动态模式为例）：
所有文件操作 → FileService/ConfigService/TrashService → API Route → 文件系统
├── FileService (文件 CRUD)
├── TrashService (回收站)
└── ConfigService (配置)
```

### 2.3 测试架构修复

| 改进 | 说明 |
|:-----|:------|
| API Mock 全覆盖 | 所有依赖 API 的测试必须添加 jest.mock |
| 测试分类明确 | `npm run test:unit` = 纯逻辑测试 / `npm run test:integration` = 带 API 测试 |
| CI 环境 | API 测试默认跳过，添加 `--run-integrational` 标志启动 |

## 三、影响分析与变更清单

### 3.1 按方案 B（推荐）的变更清单

| 文件 | 操作 | 变更说明 |
|:-----|:-----|:---------|
| `next.config.js` | ✏️ 修改 | 移除或注释 `output: 'export'` |
| `README.md` | ✏️ 修改 | 澄清运行时需要 `next dev` 或 `next start` |
| `PROJECT_SYSTEM_INDEX.md` | ✏️ 修改 | 更新架构描述，移除"静态导出"的误导描述 |
| `build_static.bat` | ✏️ 修改 | 改为 `next build && next start` 或保留说明 |
| `lib/posts.ts` | ✏️ 移除直接文件系统 | 改为通过 API Client 获取数据 |
| `services/core/ApiClient.ts` | ✏️ 修改 | 确保所有文件操作走 API |
| 测试文件 | ✏️ 修改 | 为 API 请求加 mock |

### 3.2 风险

| 风险 | 可能性 | 应对 |
|:-----|:------|:-----|
| 纯静态模式下无 API 服务 | 高 | 通过 README 清晰说明，或在 build 脚本中启动内置 Node 服务 |
| 数据流向重叠导致不一致 | 中 | 统一所有文件操作走 FileService |
| 测试环境无 API | 高 | 统一添加 mock，明确区分单元/集成测试 |

## 四、推荐方案

**推荐方案 B（动态模式）**，理由：
1. 当前项目已完全依赖 API Routes（24 个端点），改为纯静态模式改动量过大
2. 项目定位是 Windows 本地工具，Node.js 环境始终存在
3. 只需修正文档描述和澄清架构，不需要大规模重构
