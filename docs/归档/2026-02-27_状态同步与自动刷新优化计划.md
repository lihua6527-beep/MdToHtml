# 状态同步与自动刷新优化计划书 (2026-02-27)

## 1. 背景与问题
当前系统在执行文件操作（如上传、删除、恢复、保存）后，部分 UI 组件（文档列表、容量进度条、编辑器状态）未能及时自动刷新，往往需要用户手动刷新页面才能看到最新状态。这破坏了操作的流畅性与“即时反馈”体验。

## 2. 目标
建立全局状态同步机制，确保任何数据变更操作（CUD）完成后，所有相关联的 UI 组件立即自动更新，无需人工干预。

## 3. 核心问题分析
1.  **文档列表滞后**: 删除/恢复/上传后，`DocumentList` 数据未重新拉取。
2.  **容量显示不同步**: 文件增删后，`CapacityProgressBar` 仍显示旧容量。
3.  **编辑器状态隔离**: 编辑器内部保存后，外部列表的“最后修改时间”或“状态”未联动。
4.  **跨组件通信缺失**: 回收站（Modal）的操作未能通知主列表（Parent）刷新。

## 4. 解决方案：SWR 全局变异 (Global Mutation)

利用 SWR 的 `mutate` 机制实现数据的主动再验证（Revalidation）。

### 4.1 缓存键（Cache Keys）标准化
统一管理 SWR Key，确保 Service 层与 Hooks 层使用相同的 Key 常量：
- `KEYS.FILES_LIST`: `'/api/files'`
- `KEYS.TRASH_LIST`: `'/api/trash'`
- `KEYS.CAPACITY`: `'/api/config/capacity'`
- `KEYS.APP_INFO`: `'/api/app-info'`

### 4.2 Service 层增强 (Smart Services)
在 Service 层的方法成功执行后，自动触发对应的 Key 失效/刷新。

**示例流程**:
- `FileService.deleteFile()` 成功 -> 触发 `mutate(KEYS.FILES_LIST)` & `mutate(KEYS.CAPACITY)` & `mutate(KEYS.TRASH_LIST)`。
- `TrashService.restore()` 成功 -> 触发 `mutate(KEYS.TRASH_LIST)` & `mutate(KEYS.FILES_LIST)` & `mutate(KEYS.CAPACITY)`。
- `Editor.save()` 成功 -> 触发 `mutate(KEYS.FILES_LIST)` (更新修改时间)。

### 4.3 编辑器与列表联动
- 确保编辑器保存操作（`handleSaveToWorkspace`）调用 Service 层的新方法。
- Service 层负责广播更新事件（或直接操作 SWR mutate）。

## 5. 执行步骤 (Next Step)

1.  **定义 Key 常量**: 创建 `src/constants/swr-keys.ts`。
2.  **改造 Service 层**: 引入 `swr` 的 `mutate` (或 `unstable_serialize` 配合全局配置)，在 CUD 操作成功后执行关联 Key 的 Revalidate。
3.  **重构 Editor 保存**: 将 `editor/page.tsx` 中的保存逻辑迁移至 `FileService`，并接入自动刷新流。
4.  **验证**: 测试删除、恢复、上传、保存操作后的 UI 响应速度与正确性。

## 6. 预期结果
用户执行任何文件变更操作，界面在 <100ms 内自动体现最新状态（列表刷新、容量变更），无需手动 F5。
