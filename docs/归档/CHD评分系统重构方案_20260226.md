# CHD 评分系统重构方案 (Scoring System Refactoring)

**日期**: 2026-02-26
**状态**: Planning
**目标**: 建立基于"内容质量 + 修改过程"的混合评分体系，准确反映文档价值与用户工作量。

## 1. 背景与问题诊断

当前评分系统 (`RuleBasedScorer`) 仅基于静态内容分析，存在以下局限性：
1.  **无法量化用户贡献**: 无论是自动生成的初始文档，还是用户精心打磨后的文档，只要符合语法规则，得分差异不大。
2.  **缺乏激励机制**: 用户进行了大量编辑（布局调整、内容修正），分数却可能因为 strict 规则反而下降。
3.  **初始分过高**: 当前默认起步 100 分，导致优化空间在视觉上不明显。用户期望初始文档在 80-90 分区间，通过人工修订达到 100 分。

## 2. 新评分体系设计 (Hybrid Scoring Model)

我们将采用 **"静态基准 + 动态增量 - 严重惩罚"** 的混合模型。

### 2.1 核心公式

$$ FinalScore = \text{Clamp}(0, 100, BaseScore + ProcessBonus - Penalty) $$

- **BaseScore (基准分)**: 基于当前 Markdown 内容的静态质量评分 (Max: 90)。
- **ProcessBonus (过程分)**: 基于编辑历史 (`history.jsonl`) 的工作量激励 (Max: 15)。
- **Penalty (惩罚项)**: 严重错误的阻断性扣分。

### 2.2 静态基准 (BaseScore) - 权重调整

将起步分调整为 **85 分**，通过"加分项"和"扣分项"浮动。

| 维度 | 权重 | 说明 | 评分逻辑 |
| :--- | :--- | :--- | :--- |
| **结构规范** | 30% | CHD 协议符合度 | 必须包含 Frontmatter, Section, Card 三级结构。 |
| **内容原子性** | 20% | 卡片粒度 | 卡片长度适中 (<500字)，无过长段落。 |
| **样式与布局** | 30% | 视觉丰富度 | **[新增加分]** 使用 Grid 布局 (+2), 自定义列数 (+2), 多种卡片样式 (+2)。 |
| **元数据** | 10% | 信息完整性 | Title, Date, Tags 完整。 |
| **语法正确性** | 10% | Markdown 语法 | 无未闭合标签，无本地绝对路径。 |

**调整策略**: 
- 普通文档默认约 85 分。
- 使用了高级特性（如复杂 Grid、Tag Styles）才能突破 90 分。

### 2.3 动态增量 (ProcessBonus) - 新增维度

通过读取 `history.jsonl` 或内存中的 `operationLog` 计算。

- **计分规则**:
    - **有效编辑**: 每次保存 (Content Edit) 或 布局调整 (Layout Change) **+3 分**。
    - **上限**: 最多累计 **15 分** (即约 5 次有效交互)。
- **防刷机制**:
    - 短时间内 (<10s) 的连续微小修改合并计算。
    - 撤销操作不计分。

### 2.4 熔断机制 (Critical Penalty)

当检测到以下严重错误时，触发熔断，分数强制降级或归零，并提示"需重新生成"：

1.  **解析崩溃**: Frontmatter 无法解析 (-100)。
2.  **结构断裂**: 存在孤立的 H3 卡片（未在 H2 Section 内）(-20)。
3.  **渲染错乱**: 检测到未闭合的 HTML 标签或导致页面布局崩溃的 CSS 注入 (-50)。
4.  **空内容**: 内容为空 (-100)。

## 3. 实施方案

### 3.1 后端改造 (API)
- **API**: `/api/posts/[slug]`
- **变更**: 响应数据中增加 `historyCount` 字段。
    ```typescript
    // src/app/api/posts/[slug]/route.ts
    const historyCount = (await fs.readJSON(historyPath)).length;
    return NextResponse.json({ content, historyCount, ... });
    ```

### 3.2 评分引擎升级 (`scorer.ts`)
- **接口变更**:
    ```typescript
    static evaluate(content: string, historyCount: number = 0): ScoreResponse
    ```
- **逻辑实现**:
    ```typescript
    // 基础分 (上限 90)
    const baseScore = Math.min(90, calculateStaticScore(content));
    
    // 过程分 (每次 +3, 上限 15)
    const processBonus = Math.min(15, historyCount * 3);
    
    // 总分
    let totalScore = baseScore + processBonus;
    
    // 严重错误处理
    if (hasCriticalErrors) {
        totalScore = Math.max(0, totalScore - 50); // 大幅扣分
    }
    
    return Math.min(100, totalScore);
    ```

### 3.3 前端集成 (`useScoring.ts`)
- **Hook 签名**: `useScoring(content: string, historyCount: number)`
- **状态同步**: 从 `useMarkdownInteraction` 或 API 获取 `historyCount` 并传入。

## 4. 预期效果

- **初始态**: 刚导入的文档，得分 **85分** (Good)。
- **编辑态**: 用户调整一次布局，得分 **88分**；修正一处错别字，得分 **91分** (Excellent)。
- **完成态**: 经过 5 次以上交互，得分可达 **100分** (Perfect)。
- **异常态**: 格式错乱文档，得分 **40分** (Fail)，提示用户通过 AI 修复。
