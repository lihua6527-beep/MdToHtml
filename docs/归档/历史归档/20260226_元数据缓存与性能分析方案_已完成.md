# 元数据缓存与性能分析方案 (Metadata Caching & Performance Plan)

> **目标**: 引入**Top 20 最近访问缓存机制**，确保无论总数据量多大，启动速度始终保持毫秒级恒定。
> **状态**: 规划中 (Planning)
> **优先级**: 极高 (Critical)

## 1. 需求分析与核心变更

- **痛点**: 随着 Markdown 文件数量无限增长（如达到 1000+），全量扫描和缓存所有文件的元数据会导致启动时间线性增长，且内存占用不可控。
- **核心变更**:
    1.  **Top 20 限制**: 启动时**只维护前 20 个最近访问的文档**的状态。
    2.  **O(1) 启动复杂度**: 无论磁盘上有多少文件，启动时仅读取和校验这 20 个缓存条目，确保启动速度与总文件数无关。
    3.  **懒加载全量**: 剩余的“冷数据”仅在用户主动展开“全部文档”列表时才按需加载，不占用启动资源。

## 2. 技术方案

### 2.1 缓存结构设计 (`.metadata_cache.json`)

采用 LRU (Least Recently Used) 策略，仅保留最近使用的 20 个条目。

```json
{
  "version": "2.0",
  "lastUpdated": 1677654321000,
  "recentFiles": [
    // 数组有序，索引 0 为最近访问，最大长度 20
    {
      "path": "c:/.../docs/project-a.md",
      "mtime": 1677654321000,
      "status": "completed",
      "title": "项目A计划",
      "tags": ["Priority"],
      "excerpt": "..."
    },
    // ... 最多 19 个其他条目
  ]
}
```

### 2.2 启动与生命周期管理

1.  **极速启动 (Cold Start)**:
    -   **读取**: 应用启动仅读取 `.metadata_cache.json`。
    -   **校验**: 仅对 `recentFiles` 中的 20 个文件进行 `fs.stat` 校验。
        -   若文件存在且 `mtime` 未变 -> 直接使用缓存。
        -   若文件不存在 -> 从缓存移除。
        -   若文件已修改 -> 重新解析 Frontmatter 更新缓存。
    -   **渲染**: 首页列表仅展示这 20 个文档，实现**无视数据量的瞬开**。

2.  **运行时维护 (Runtime Maintenance)**:
    -   **打开文档**: 用户打开任意文档（包括从文件管理器打开或新建） -> 该文档插入 `recentFiles` 头部 -> 若长度超过 20，移除末尾条目。
    -   **状态更新**: 文档状态变更（如“完成”）-> 更新缓存 -> 异步持久化。
    -   **全量访问**: 只有当用户点击“展开更多”时，才触发全量文件扫描（详见《大数据量文档列表扩展方案》），此过程不阻塞主界面。

3.  **退出与持久化 (Shutdown)**:
    -   仅将当前的 Top 20 列表写入磁盘。
    -   **优势**: 写入量极小，退出速度极快，无磁盘 I/O 压力。

### 2.3 性能分析 (Performance Analysis)

-   **启动时间**: 恒定为 **< 50ms**（读取 JSON + 20次 `fs.stat`），不受 10,000+ 文件规模影响。
-   **内存占用**: 极低，仅维护 20 个对象。
-   **用户体验**: 95% 的场景下用户只关注最近编辑的文档，核心体验极佳；查阅历史文档的低频需求通过“扩展列表”满足。

## 3. 实施步骤

1.  **缓存管理器**: 实现 `LRUCacheManager`，强制限制容量为 20。
2.  **启动逻辑**: 修改 `main.js` 或启动脚本，仅加载 LRU 列表。
3.  **UI 适配**: 首页列表增加“最近编辑”标题，底部增加“查看全部文档”入口。

## 4. 风险控制

-   **冷启动无缓存**: 首次安装或缓存丢失时，列表为空，需引导用户“打开文件”或自动扫描最近修改的 20 个文件填充缓存。
-   **文件移动**: 若用户在外部移动了文件，缓存路径失效，需在校验阶段自动清理无效条目。
