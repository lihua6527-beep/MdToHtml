# CHD 智能文档系统 - Phase 2 全栈实施路线图

## 1. 概述与目标

本阶段（Phase 2）的核心目标是将系统从 "基于规则的编辑器" 升级为 "数据驱动的智能辅助创作平台"。我们将打通前端编辑器 (`MdToHtml`) 与模型服务 (`workflow_hub`) 之间的数据闭环，实现“编辑-采集-训练-反馈”的自动化飞轮。

**核心交付物**：
1.  **数据基建**: 自动化的合成数据生成器与真实会话清洗管道。
2.  **规则引擎 2.0**: 经过真实数据验证的高精度校验器 (`validator.ts`)。
3.  **智能服务**: 基于 TinyModel 的实时结构建议与评分 API。
4.  **交互升级**: 前端集成 "智能诊断" 与 "一键修复" 功能。

## 2. 阶段一：数据基建与基准建立 (Week 1)
**目标**: 建立可靠的数据采集管道，并量化当前系统的性能基准。

### 2.1 任务分解
| ID | 任务名称 | 描述 | 验收标准 (DoD) |
| :--- | :--- | :--- | :--- |
| **D-01** | **合成数据生成器增强** | 升级 `portable_ml_package/data/generator.py`，覆盖 CHD 协议所有违规场景（孤儿卡片、深层标题、非闭合属性等）。 | 生成 10,000 条样本，包含 Positive/Negative 对；覆盖率 100%。 |
| **D-02** | **批量评估脚本开发** | 开发 `scripts/batch_eval.ts`，支持对 `input/` 及 `data/sessions/` 下的所有 Markdown 文件运行当前的 Scorer。 | 脚本输出 CSV 报告，包含：文件名、总分、违规项列表。 |
| **D-03** | **数据清洗管道** | 在 `workflow_hub` 建立 ETL 脚本，解析前端上传的 Session 数据，提取 `{raw, perfect}` 对。 | 能将 `data/sessions/` 下的 JSON/MD 转换为 `raw_pairs.jsonl` 训练集。 |
| **D-04** | **基准测试报告** | 运行 D-02 脚本，统计当前存量文档的评分分布与常见报错。 | 输出《Phase1_基准测试报告.md》，明确当前的误报率与漏报率。 |

### 2.2 交付物
*   `data/dataset_v1.zip` (合成数据 + 清洗后的真实数据)
*   `Phase1_基准测试报告.md`

## 3. 阶段二：规则引擎优化 (Week 2)
**目标**: 消除误报，提升硬编码规则的可信度，使其成为模型的“老师”。

### 3.1 任务分解
| ID | 任务名称 | 描述 | 验收标准 (DoD) |
| :--- | :--- | :--- | :--- |
| **R-01** | **Validator 正则调优** | 根据 D-04 报告，修正 `validator.ts` 中的正则逻辑，解决“误判代码块为标题”、“属性解析失败”等问题。 | 基准测试集上的误报率 (False Positive) 降至 0%。 |
| **R-02** | **Scorer 权重校准** | 调整 `scorer.ts` 的扣分策略，确保核心结构错误（如 H4 标题）的扣分显著高于样式警告。 | 评分结果与人工专家评分的相关系数 (Correlation) > 0.8。 |
| **R-03** | **Lint 规则扩充** | 新增 3-5 条高频错误的检测规则（如：卡片内容过长检测、空卡片检测）。 | 新增规则在测试集中能正确触发。 |
| **R-04** | **单元测试覆盖** | 为 `validator.ts` 和 `scorer.ts` 编写 Jest 单元测试。 | 测试覆盖率 > 90%。 |

### 3.2 交付物
*   `validator.ts` (v2.0)
*   `scorer.ts` (v2.0)
*   `tests/validator.test.ts`

## 4. 阶段三：模型服务集成 (Week 3)
**目标**: 引入 AI 能力，处理规则引擎无法覆盖的“语义级”问题。

### 4.1 任务分解
| ID | 任务名称 | 描述 | 验收标准 (DoD) |
| :--- | :--- | :--- | :--- |
| **M-01** | **TinyModel 重训** | 使用 D-03 产出的数据重新训练 `TinyTextModel` (分类/打分)。 | 验证集准确率 > 95%；ONNX 模型导出成功。 |
| **M-02** | **API 服务开发** | 在 `workflow_hub` 实现 `/api/inference` 接口 (FastAPI)，集成 `score` 和 `suggest` 功能。 | 接口响应时间 < 200ms；符合 `schemas.py` 定义。 |
| **M-03** | **前端 API Client** | 在 `MdToHtml` 中封装 `services/ai.ts`，实现对后端模型接口的调用与错误处理。 | 能成功联调，并处理超时/失败情况。 |
| **M-04** | **建议生成逻辑** | 实现基于规则+模型的建议生成算法 (e.g., "检测到长文本 -> 建议拆分")。 | 对于典型长难句，能返回 `split_card` 建议。 |

### 3.2 交付物
*   `tiny_model_v2.onnx`
*   `workflow_hub` API 服务 (Docker Image)

## 6. 资源需求与风险管理

### 6.1 资源需求
*   **计算资源**: 本地 GPU (用于模型训练) 或 CPU (TinyModel 训练开销极低)。
*   **开发环境**: Node.js v18+, Python 3.10+。
*   **测试数据**: 至少 50 篇真实 Markdown 文档。

### 6.2 风险评估
| 风险点 | 可能性 | 影响 | 缓解措施 |
| :--- | :--- | :--- | :--- |
| **数据质量不足** | 中 | 高 | 优先完善合成数据生成器；人工构造典型边缘案例。 |
| **模型推理延迟** | 低 | 中 | 采用 ONNX Runtime 加速；前端增加 Loading 状态与缓存。 |
| **前后端接口不一致** | 中 | 高 | 严格遵守 `model-interface.ts` 契约；CI 阶段增加类型检查。 |

---

## 7. 验收与集成流程 (CI/CD)

1.  **代码提交**: 每次 Commit 必须通过 `npm run lint` 和 `npm run test`。
2.  **每日构建**: 每天生成最新的 Frontend Build 和 Backend Image。
3.  **自动化验收**:
    *   运行 `scripts/batch_eval.ts` 确保评分基线不下降。
    *   运行 `pytest` 确保模型接口逻辑正确。
