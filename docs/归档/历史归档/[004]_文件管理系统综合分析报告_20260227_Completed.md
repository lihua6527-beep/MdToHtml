## 2. 文件生命周期与调用链

- 导入（Import）
  - UI：设置面板或直接将 .md 放入 Input 目录；上传经由 [upload](file:///c:/Users/86171/Desktop/MdToHmtl/MdToHtml/src/app/api/upload/route.ts)
  - FS：保存到 Input 目录（由 [path-manager](file:///c:/Users/86171/Desktop/MdToHmtl/MdToHtml/src/lib/path-manager.ts) 决定）
  - 缓存：下次扫描由 [cache-manager](file:///c:/Users/86171/Desktop/MdToHmtl/MdToHtml/src/lib/cache-manager.ts) 识别，生成/更新条目
- 使用（Edit/Load/Save）
  - 加载：/api/load 直接读 Input 中文件
  - 保存：/api/save → data-collector 记录到 Data 目录（initial.md + history.jsonl），随后 cache-manager.update 写回 Input 并触发 scanAndSync（容量检查）
- 导出（Export）
  - 编辑器内导出为 HTML，调用 /api/save-export 将 HTML 落盘至 Output；若配置 emitJson，则同名 JSON 元数据同步写入
- 删除（Delete）
  - UI：DocumentList 拖拽或菜单 → /api/delete
  - 服务：cache-manager.delete 定位并交给 trash-manager.moveToTrash 将源 Markdown 移入回收站；可选将 Output HTML 也移动至回收站
- 回收站（Trash）
  - 列表/统计：/api/trash/files、/api/trash/stats
  - 恢复：/api/trash/restore → trash-manager.restoreFiles 将文件复制回 Input，并刷新创建时间与修改时间（Windows 设 CreationTime）
  - 清空/删除：/api/trash/empty、/api/trash/delete
- 容量与清理（Capacity Cleanup）
  - cache-manager.scanAndSync 在条目超过 capacityLimit 时，按 mtime 降序保留前 N，其余溢出移动至回收站（TrashManager）

状态转换一致性评估：

- 导入 → 列表：一致（下一次 scanAndSync 生效）
- 保存 → 列表：一致（update 后触发 scanAndSync）
- 删除 → 回收站：一致（renameSync 原子移动），缓存条目删除并保存
- 恢复 → 列表：一致（restore 后主动 scanAndSync）
- 导出 → Output：一致（立即写入）；与源文件生命周期相互独立（可选随删除一并移入回收站）

## 3. 冲突检测与一致性风险

- 并发读写
  - 保存与容量清理同时进行：cache-manager.update 写入后立即 scanAndSync；若并发删除导致文件不存在，下一轮扫描会剔除条目；风险较低
  - 删除与导出：删除的是 Input 源文件；导出写入 Output；互不影响，除非 UI 选择“删除输出文件”，则一起移动到回收站（同一 Trash 目录，采用时间戳命名避免覆盖）
- 命名与路径映射
  - 输入/输出/数据/回收站路径统一由 path-manager 解析，默认位于 appRoot 下；不可写时回退至 “用户文档/MdToHtml”
  - 输出 HTML 文件名通过 save-export 进行非法字符清洗（替换为下划线）并强制 .html 后缀；与源 Markdown 的 slug 不强耦合
- 锁机制/事务边界
  - 无集中式锁；单文件移动使用 fs.renameSync（同卷原子），多文件操作（删除源 + 删除输出）不是单事务，可能出现部分成功；API 层已尽量按顺序处理并记录警告
- 元数据与物理文件一致性
  - 删除：cache.entryMap 删除并保存缓存；物理文件入回收站；一致性可接受
  - 容量清理：由 cache-manager 直接决定溢出集并调用 trash-manager；无双写；一致性可接受
  - 恢复：恢复后调用 cache-manager.scanAndSync 保证列表即时出现；Windows 下通过 PowerShell 调整 CreationTime 以符合“按导入时间排序”的期望
- 潜在竞态
  - cache-manager 与 trash-manager 双向调用的注释提示：目前 delete → Trash 是单向，避免循环调用；缓存刷新通过 scanAndSync 主动推进

冲突矩阵（简化）

| 操作/对象 | Input 源文件 | Output 文件 | 缓存条目 | 回收站文件 | 数据记录 |
| - | - | - | - | - | - |
| 保存 | 覆写/新增 | 无 | 更新/保持一致 | 无 | 追加历史 |
| 删除 | 移入 Trash | 可选移入 | 移除并落盘 | 增加 | 无 |
| 恢复 | 复制回 Input | 无 | 扫描重建 | 减少 | 无 |
| 导出 | 无 | 写入/覆写 | 无 | 无 | 无 |
| 容量清理 | 移入 Trash | 无 | 修剪至 N | 增加（超限自动清理至 500） | 无 |

## 4. 资源浪费与占用评估

- 存储位置
  - Input：Markdown 正文（单份）
  - Output：导出 HTML 与可选 JSON 元数据（单份）
  - Data：initial.md + history.jsonl（按需追加）
  - .trash：被删除或容量清理的完整文件副本（源/输出混放，时间戳后缀）
- 冗余与重复
  - 列表源自 .metadata_cache.json 与实时扫描，不另存 Top20/最近副本；避免多份冗余
  - Data 只在内容真正变化时追加正文（operations 存在时优先仅记录操作，减少冗余）
  - 回收站保存完整文件副本，空间换安全；超 500 自动清理最早项
- 过期策略
  - 列表容量：capacityLimit（默认 500，可通过设置面板调整）
  - 回收站容量：硬上限 500，超限自动按删除时间清理
- 建议的监控指标/统计表（可由设置页面或 CLI 扫描生成）
  - Input/Output/.trash/Data 目录：文件数、总大小、Top N 大文件、最近变更分布
  - 每日新增/删除/恢复计数；容量利用率（entries/limit）

## 5. 统一抽象设计（文件管理系统）

- 概述
  - 将 Input/Output/Data/Trash、缓存、容量控制收敛为统一“文件管理系统（FMS）”
  - 职责：统一 CRUD、状态机、事件流；提供一致的事务语义与扩展钩子
- 统一接口（TypeScript 草案）

```ts
export type FileId = string; // slug 或绝对路径
export type FileKind = 'markdown' | 'html' | 'json' | 'other';
export type FileState = 'active' | 'trashed' | 'exported';

export interface FileMeta {
  id: FileId;
  kind: FileKind;
  title?: string;
  tags?: string[];
  mtime: number;
  birthtime: number;
  size?: number;
  state: FileState;
  link?: string; // 例如导出的 html 相对路径
}

export interface CreateOptions { overwrite?: boolean }
export interface DeleteOptions { includeOutput?: boolean }
export interface ExportOptions { emitJson?: boolean }

export interface IFileManager {
  // CRUD
  list(): Promise<FileMeta[]>;
  read(id: FileId): Promise<string>;
  createOrUpdate(id: FileId, content: string, opts?: CreateOptions): Promise<FileMeta>;
  remove(id: FileId, opts?: DeleteOptions): Promise<void>;

  // Export
  export(id: FileId, html: string, meta?: Partial<FileMeta>, opts?: ExportOptions): Promise<void>;

  // Trash
  trash(id: FileId): Promise<void>;
  restore(trashName: string): Promise<FileMeta>;
  emptyTrash(): Promise<void>;
  listTrash(): Promise<{ name: string; originalName: string; size: number; deletedAt: number }[]>;

  // Capacity & Stats
  getCapacity(): Promise<{ limit: number; count: number; usage: number }>;
  setCapacity(limit: number): Promise<void>;

  // Events
  on(event: 'created'|'updated'|'deleted'|'trashed'|'restored'|'exported'|'capacityOverflow', handler: (payload: any)=>void): void;
  off(event: string, handler: (payload: any)=>void): void;
}
```

- 状态机（简版）
  - Draft/Active（存在于 Input） ↔ Deleted（存在于 Trash）
  - Exported 为衍生状态（存在于 Output），与 Active/Deleted 正交
- 事件流与钩子
  - 钩子阶段：beforeCreate/afterCreate、beforeDelete/afterDelete、beforeExport/afterExport、beforeRestore/afterRestore、onCapacityOverflow
  - 扩展点：
    - 外部存储（S3、OSS）、外部缓存（Redis）
    - 自定义清理策略（基于权重/标签/访问频度）
    - 审计与埋点（落 Data 目录或远端）

## 6. 性能与可维护性评估

- 现状
  - I/O：目录扫描 + 单文件读写，典型上限 500；删除/恢复为 rename/copy + unlink，单文件 O(1)
  - 内存：缓存条目常驻 Map，O(N) 存储；排序 O(N log N)，N≤500 低成本
  - CPU：frontmatter 解析发生在扫描阶段（gray-matter），批量导入时为热点
- 统一抽象后的变化（定性）
  - I/O：减少重复扫描；事件驱动刷新；批量操作可分批提交与失败回滚（幂等）
  - 内存：统一缓存层（仅一处 .metadata_cache.json），避免多源维护
  - CPU：解析与容量判定分层，支持增量扫描/文件系统 watch
- 定量基线（建议）
  - 1k 文件冷启动扫描 ≤ 2s；增量扫描（单文件保存） ≤ 50ms
  - 批量删除 100 个文件 ≤ 1s（同卷重命名）
  - 导出 HTML + JSON 单文件 ≤ 100ms（不含打包）

## 8. 改进方案与落地

- 近期可落地
  - 将“输出文件同步入回收站”的逻辑抽象为 FMS 层流程，提供事务型批处理（部分失败回滚或重试）
  - 在 cache-manager 中新增轻量事件总线，save/delete/restore 后广播，文档列表订阅以减少手动刷新
  - 将回收站上限（500）抽象为配置项（随 app-info 暴露只读，随 config 可写）

  - 增量扫描与 FS Watch，减少全量扫描频率
  - Data 目录引入分段归档与压缩，控制历史文件膨胀
  - 导出管线支持多目标（本地/远端），并发队列 + 失败重试


## 8.5 风险收益评估与实施优先级 (Risk/Benefit Analysis)

为了稳健地推进系统规范化，我们将改进措施按照“风险”和“收益”进行分级，并据此制定实施顺序。

### 实施路线图 (Roadmap)

根据“优先完成低风险高回报操作”的原则，我们将按照以下阶段执行：

#### 第二阶段：可观测性与健壮性 (P1 - P2) - [已完成]
1.  **增强日志记录**：在 `cache-manager` 和 `trash-manager` 中添加关键操作日志。（已完成）

5.  **Bug 修复**：修复容量显示失效与回收站恢复失效问题。（已完成）

#### 第三阶段：架构重构 (P3) - [已完成]
