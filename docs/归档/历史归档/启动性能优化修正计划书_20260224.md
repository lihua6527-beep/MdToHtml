# 启动性能优化修正计划书

## 1. 背景与问题回顾

### 1.1 问题描述
用户反馈系统启动速度慢，且在最近一次尝试优化（引入客户端分页加载）后，性能反而进一步下降。

### 1.2 错误复盘
在上一轮优化尝试中，存在以下严重失误：
1.  **流程违规**：未在独立分支（Feature Branch）进行开发，直接修改了 `master` 分支代码。
2.  **未审先做**：在文档未经过用户审阅确认的情况下，擅自编写并应用了代码。
3.  **技术判断失误**：
    *   **原方案**：服务端一次性读取所有文件（Node.js 本地 IO 速度极快）。
    *   **错误优化**：改为客户端分页 `fetch` 请求。
    *   **后果**：在本地单机环境下，HTTP 请求的建立与通信开销（Overhead）远大于文件 I/O 的开销。特别是当文档数量不多（几十到几百篇）时，串行的网络请求反而导致了明显的页面加载延迟。

## 2. 修正目标

1.  **立即止损**：回滚所有未经验证的代码修改，恢复系统至上一稳定版本。
2.  **流程合规**：严格遵守 "文档 -> 审阅 -> 分支开发 -> 验证 -> 合并" 的标准工作流。
3.  **重新分析**：基于真实瓶颈制定优化方案。

## 3. 性能瓶颈再分析

在 Windows 本地环境下，Node.js 的 `fs.readFileSync` 性能通常非常高。
如果用户感觉到“卡顿”，可能的原因排序如下：
1.  **前端渲染阻塞**：React 在一次性渲染大量复杂组件（如带有复杂样式的卡片）时可能会阻塞主线程。
2.  **大文件解析**：如果存在个别极大的 Markdown 文件，`gray-matter` 解析 Frontmatter 可能会消耗时间。
3.  **IO 阻塞**：确实存在大量小文件读取，但通常 SSD 能够轻松应对。

**结论**：之前的“网络请求分页”方案方向错误。应关注 **"服务端并行读取"** 或 **"前端虚拟滚动/分页渲染"**，而不是引入 HTTP 层面的分页。
