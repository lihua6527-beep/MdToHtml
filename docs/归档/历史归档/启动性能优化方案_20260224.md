# 启动性能优化方案

## 1. 问题背景
用户反馈每次进入系统时存在卡顿现象。经分析，主要原因是系统启动或访问主页时，会一次性加载所有 Markdown 文件，并读取其完整内容以解析 Frontmatter（元数据，如状态、标签等）。随着文档数量增加，IO 开销呈线性增长，导致显著的性能瓶颈。

## 2. 核心问题分析
- **全量加载**: `getAllPosts` 函数在每次调用时都会遍历所有文件。
- **全量读取**: 为了获取仅占文件头部一小部分的 Frontmatter 信息，系统使用了 `fs.readFileSync` 读取整个文件内容。对于大文件，这是极大的资源浪费。
- **缺乏缓存**: 即使文件未发生变更，系统也会重复读取和解析文件。

## 3. 优化策略

### 3.1 智能局部读取 (Smart Partial Read)
- **原理**: Frontmatter 通常位于文件头部。我们只需读取文件的前 4KB (4096 bytes) 即可涵盖绝大多数元数据信息。
- **实现**: 使用 `fs.openSync` + `fs.readSync` 替代 `fs.readFileSync`。
- **容错**: 如果局部读取解析失败（极少数情况），回退到全量读取，确保数据准确性。

### 3.2 内存缓存机制 (In-Memory Caching)
- **原理**: 利用 Node.js 模块的单例特性，维护一个内存缓存 `postCache`。
- **键值对**: Key 为文件绝对路径，Value 包含 `mtime` (最后修改时间) 和 `status` (解析后的状态)。
- **缓存命中**: 每次读取前先对比文件的 `mtime`。如果一致，直接返回缓存的状态，跳过文件读取；如果不一致，重新读取并更新缓存。

### 3.3 预期效果
- **IO 降低**: 文件读取量减少 90% 以上（取决于平均文件大小）。
- **CPU 降低**: 减少了对大文本的解析开销。
- **响应速度**: 二次访问（缓存命中）将接近零延迟；首次访问也将因局部读取而大幅提速。

## 6. 风险评估
- **Frontmatter 过长**: 极少数情况下 Frontmatter 超过 4KB，导致解析失败。已添加 fallback 机制处理此情况。
- **内存泄漏**: 当前缓存为简单的对象，若文件被大量删除重命名，缓存可能残留。考虑到是桌面单人应用，风险可控。后续可引入定期清理机制。
