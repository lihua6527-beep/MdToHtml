# 容量管理与自动清理方案 (Capacity Management & Auto-Cleanup Plan) - 修订版

> **目标**: 引入**回收站 (Trash)** 机制保障数据安全，并在文档列表顶部提供**容量进度条**与直观的**容量设置**，实现自动化与可视化的存储管理。
> **状态**: 实施中 (Implementation) - Branch: `feature/capacity-management`
> **优先级**: 高 (High) - 涉及数据安全

---

## 1. 核心需求与变更 (Core Requirements)

### 1.1 回收站机制 (Trash Mechanism)
- **强制移入回收站**: 所有“删除”操作（无论是用户手动删除还是自动清理）**严禁直接物理删除**，必须移入 `.trash` 目录。
- **文件命名**: 移入回收站的文件必须重命名为 `{original_name}_{timestamp}.md` 以防止重名冲突并记录删除时间。
- **回收站管理**:
    - **统计**: 实时维护回收站内的文件数量与总大小。
    - **清空**: 提供“一键清空”功能，彻底释放磁盘空间。

### 1.2 容量可视化 (Capacity Visualization)
- **进度条**: 在**文档列表顶部**（搜索栏下方/上方）新增容量进度条。
    - **显示**: `当前数量 / 容量上限` (例如: `32/100`)。
    - **样式**: 
        - 绿色 (<80%): 正常状态。
        - 橙色 (80%-99%): 预警状态。
        - 红色 (100%): 满载状态，触发自动清理建议或强制清理。

### 1.3 容量设置 (Capacity Settings)
- **入口位置**: 与“文件路径”设置同级（在文档列表左下角/顶部的设置菜单中）。
- **名称**: **"存储容量" (Storage Capacity)**。
- **交互方式**: 点击后在**右侧弹出选择框** (Popover/Select)。
- **选项**: 提供固定档位供选择：
    - `20` (极简模式)
    - `50` (轻量模式)
    - `100` (标准模式 - **默认值**)
    - `200` (专业模式)
    - `300` (扩容模式)
    - `500` (极限模式)
- **持久化**: 设置值需保存至 `config.json` 的 `capacityLimit` 字段。

## 3. 技术实现 (Technical Implementation)

### 3.1 数据结构 (`config.json`)
```json
{
  "capacityLimit": 100, // 默认 100
  "trashPath": ".trash" // 内部管理，通常固定
}
```

### 3.2 后端逻辑
1.  **删除/移动接口 (`/api/trash/move`)**:
    -   接收: `filepath` 或 `slug`。
    -   操作: `fs.rename(src, path.join('.trash', basename + '_' + timestamp + ext))`.
    -   更新: 更新内存缓存，移除列表项。
2.  **自动清理检查**:
    -   时机: 每次列表加载 (`GET /api/posts`) 或 新增文件 (`POST /api/save`) 后。
    -   逻辑:
        ```javascript
        if (currentFiles.length > config.capacityLimit) {
            const deleteCount = currentFiles.length - config.capacityLimit;
            const filesToDelete = currentFiles.slice(-deleteCount); // 假设已按时间倒序，取最旧的
            moveToTrash(filesToDelete);
        }
        ```
3.  **清空回收站 (`/api/trash/empty`)**:
    -   操作: `fs.rm(trashPath, { recursive: true, force: true })` 然后重建目录。

### 3.3 前端组件
-   **`CapacityProgressBar`**: 接收 `count` 和 `limit` props。
-   **`StorageSettings`**: Popover 组件，渲染单选列表。

## 4. 风险与可行性分析 (Risk & Feasibility)

### 4.1 原子性与事务
-   **文件移动**: `fs.rename` 在同一分区下是原子的。若跨分区（极为罕见，因为 .trash 在项目根目录），Node.js 会自动处理复制+删除。
-   **风险**: 移动过程中进程崩溃可能导致文件状态不一致（缓存 vs 磁盘）。
-   **对策**: 每次启动或刷新列表时，强制重新扫描磁盘状态 (`sync`)，以磁盘为准更新缓存。

### 4.2 依赖危机
-   **依赖**: `fs`, `path` (Node.js 内置)，无外部高风险依赖。
-   **路径**: 需确保 `.trash` 目录存在。启动时需检查并创建 `mkdir -p .trash`。

### 4.3 性能影响
-   **扫描**: 即使回收站有大量文件，只要主列表扫描逻辑显式 `ignore: ['.trash']`，就不会影响主程序性能。
-   **清理**: 批量移动 100+ 文件可能耗时。
    -   *优化*: 异步执行，前端先乐观更新 UI (移除列表项)，后台慢慢移动。

### 4.4 误操作风险
-   **场景**: 用户设置容量为 20，但当前有 100 个文件。
-   **处理**: 调整容量设置时，**不立即触发清理**，而是弹出提示 "当前文件数 (100) 超过新设定 (20)，将有 80 个旧文件被移入回收站，是否继续？"。确认后执行。
