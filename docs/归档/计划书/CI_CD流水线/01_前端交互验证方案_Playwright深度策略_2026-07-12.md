# Plan 01: 前端交互验证方案 — Playwright 深度策略

> **计划日期**：2026-07-12  
> **计划目标**：针对本系统"纯前端+密集交互"的特性，建立真正能验证 UI 可靠性的测试策略，而非"点一下看看元素在不在"的假测试。  
> **核心问题**：如何确认一个前端交互系统的功能是可靠的？

---

## 一、为什么传统前端测试不可靠？

### 1.1 常见误区

```
❌ "我写了 E2E 测试" ≠ "我的前端是可靠的"

常见问题：

  1. 测试写得太浅：
     await page.click('button')
     await expect(text).toBeVisible()  // 元素在≠功能对

  2. 测试跑得太顺：
     CI 全绿，但用户一用就出 bug
     → 因为测试只测了"happy path"

  3. 前端交互测不了：
     编辑器输入后预览更新？测不到
     拖拽排序后数据正确？测不到
     AI 流式输出逐字渲染？测不到
     撤销/重做后状态一致？测不到
```

### 1.2 本系统的前端交互风险矩阵

| 交互类型 | 风险等级 | 传统测试覆盖率 | 需要什么 |
|---------|---------|--------------|---------|
| **编辑器输入 → 预览更新** | 🔴 高 | 0% | 内容一致性验证 |
| **CHD 卡片渲染正确性** | 🔴 高 | 0% | 视觉回归 + DOM 结构验证 |
| **撤销/重做状态回退** | 🔴 高 | 0% | 操作历史状态验证 |
| **AI 流式输出渲染** | 🟠 中 | 0% | 流式内容逐帧验证 |
| **主题切换（浅色/暗黑）** | 🟠 中 | 0% | CSS 变量 + 截图对比 |
| **搜索高亮与跳转** | 🟡 中 | 0% | 搜索结果 + 滚动位置验证 |
| **保存 → 刷新 → 持久化** | 🔴 高 | 0% | localStorage + 文件系统验证 |
| **导出 HTML → 打开验证** | 🟠 中 | 0% | 文件内容验证 |
| **拖拽排序（如实现）** | 🟠 中 | 0% | 拖拽操作模拟 + 数据验证 |
| **回收站恢复数据完整性** | 🟡 中 | 0% | 完整状态机验证 |

## 二、前端交互验证的三层体系

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：功能验证（Functional Verification）                  │
│  用户操作 → 期望结果                                         │
│  e.g. 点击"新建文档"→ 编辑器打开 → 输入内容 → 预览更新      │
├─────────────────────────────────────────────────────────────┤
│  第二层：视觉回归（Visual Regression）                        │
│  截图对比 → 发现肉眼难以察觉的 UI 偏差                       │
│  e.g. 主题切换后卡片阴影变了1px → 自动告警                  │
├─────────────────────────────────────────────────────────────┤
│  第三层：状态验证（State Verification）                       │
│  验证应用内部状态（非仅 DOM 可见状态）                       │
│  e.g. 撤销后 Zustand store 中的文档内容是否正确回退          │
└─────────────────────────────────────────────────────────────┘
```

#### 测试 1：编辑工作流（最关键的测试）

```typescript
// e2e/core/01-editor-workflow.spec.ts
import { test, expect } from '@playwright/test';

test.describe('核心编辑工作流', () => {
  test('新建 → 编辑 → 预览更新：内容一致性验证', async ({ page }) => {
    // 1. 打开首页
    await page.goto('/');
    
    // 2. 新建文档（等待编辑器加载）
    await page.click('text=新建文档');
    await page.waitForSelector('.cm-editor');
    
    // 3. 在编辑器中输入 CHD 格式内容
    const editor = page.locator('.cm-content');
    await editor.fill('');
    
    // 逐行输入（模拟真实用户行为，非一次性 fill）
    const lines = [
      '## 第一章：系统概述',
      '',
      '### 卡片 1：核心概念',
      '',
      '这是第一张卡片的内容。包含**粗体**和*斜体*。',
      '',
      '### 卡片 2：技术特性',
      '',
      '- 特性一：支持 CHD 协议',
      '- 特性二：卡片式渲染',
      '',
      '> 这是一个引用',
      '',
      '### 卡片 3：代码示例',
      '',
      '```typescript',
      'const app = "MdToHtml";',
      'console.log(app);',
      '```'
    ];
    
    for (const line of lines) {
      await editor.press('Enter');
      await editor.type(line, { delay: 10 }); // 模拟逐字输入
    }
    
    // 4. 等待预览更新（防抖 + 解析延迟）
    await page.waitForTimeout(500);
    
    // 5. 【关键验证】检查预览中是否出现了对应的卡片
    //    元素存在 + 卡片数量正确 + 内容正确
    const cards = page.locator('.chd-card-normal');
    await expect(cards).toHaveCount(3); // 3 张普通卡片
    
    // 6. 验证每种卡片样式
    await expect(page.locator('.chd-card-quote')).toBeVisible(); // 1 张引用卡片
    await expect(page.locator('.chd-card-code')).toBeVisible();  // 1 张代码卡片
    
    // 7. 验证卡片标题
    await expect(page.locator('text=核心概念')).toBeVisible();
    await expect(page.locator('text=技术特性')).toBeVisible();
    await expect(page.locator('text=代码示例')).toBeVisible();
    
    // 8. 【关键验证】验证内容正确渲染
    await expect(page.locator('strong:has-text("粗体")')).toBeVisible();
    await expect(page.locator('em:has-text("斜体")')).toBeVisible();
    
    // 9. 验证代码块内容
    await expect(page.locator('code:has-text("MdToHtml")')).toBeVisible();
  });
  
  // 重要：测试增量编辑
  test('增量编辑后预览局部更新', async ({ page }) => {
    // 先建立基线
    await page.goto('/editor/1'); // 打开已有文档
    await page.waitForSelector('.cm-editor');
    
    // 记录当前卡片数
    const initialCardCount = await page.locator('.chd-card-normal').count();
    
    // 在末尾新增一个卡片
    const editor = page.locator('.cm-content');
    await editor.press('End');
    await editor.press('Enter');
    await editor.type('### 新增卡片', { delay: 10 });
    await editor.press('Enter');
    await editor.type('这是增量添加的内容。');
    
    // 等待预览更新
    await page.waitForTimeout(500);
    
    // 验证卡片数 +1
    await expect(page.locator('.chd-card-normal')).toHaveCount(initialCardCount + 1);
    await expect(page.locator('text=新增卡片')).toBeVisible();
  });
});
```

import { test, expect } from '@playwright/test';

test.describe('撤销/重做交互', () => {
  test('撤销后预览回退到之前的状态', async ({ page }) => {

    await page.waitForTimeout(500);
    
    // 5. 【关键验证】预览回退到初始状态
    const afterUndoText = await page.locator('.chd-card-normal').first().textContent();
    expect(afterUndoText).toBe(initialPreviewText);
    
    // 6. 执行重做
    await page.click('text=重做');
    await page.waitForTimeout(500);
    
    // 7. 验证内容恢复
    const afterRedoText = await page.locator('.chd-card-normal').first().textContent();
    expect(afterRedoText).not.toBe(initialPreviewText);
  });
  
  test('连续 50 次撤销/重做不崩溃', async ({ page }) => {
    await page.goto('/editor/1');
    await page.waitForSelector('.cm-editor');
    
    const editor = page.locator('.cm-content');
    
    // 连续输入 50 次并撤销
    for (let i = 0; i < 50; i++) {
      await editor.type(`${i}`, { delay: 1 });
    }
    
    // 连续撤销 50 次
    for (let i = 0; i < 50; i++) {
      await page.keyboard.press('Control+z');
    }
    await page.waitForTimeout(300);
    
    // 验证应用没有崩溃
    await expect(page.locator('.cm-editor')).toBeVisible();
    
    // 验证状态稳定
    const errorCount = await page.locator('.error-boundary-fallback').count();

  });

// e2e/interactive/06-ai-generation.spec.ts
import { test, expect } from '@playwright/test';

test.describe('AI 生成交互', () => {
  test('AI 流式输出逐字渲染', async ({ page }) => {
    await page.goto('/ai-input');
    
    // 1. 输入提示词
    await page.fill('textarea', '生成一份关于 TypeScript 的笔记');
    
    // 2. 点击生成
    await page.click('text=生成');
    
    // 3. 【关键验证】流式输出过程中，内容逐步出现
    // 等待至少出现一些文本
    await page.waitForSelector('.ai-stream-output');
    
    // 4. 检查是否逐块输出（检查输出区域的 innerHTML 是否有变化）
    const outputLocator = page.locator('.ai-stream-output');
    let lastLength = 0;
    let changedCount = 0;
    
    // 等待最多 10 秒，检查内容是否在增长
    for (let i = 0; i < 20; i++) {
      await page.waitForTimeout(500);
      const currentContent = await outputLocator.textContent();
      if (currentContent && currentContent.length > lastLength) {
        lastLength = currentContent.length;
        changedCount++;
      }
      // 如果内容超过 100 字符，认为流式输出正常工作
      if (lastLength > 100) break;
    }
    
    // 流式输出过程中内容至少增长 2 次
    expect(changedCount).toBeGreaterThanOrEqual(2);
    
    // 5. 点击保存
    await page.click('text=保存');
    
    // 验证保存成功提示
    await expect(page.locator('text=已保存')).toBeVisible();
  });
});

## 四、策略二：视觉回归测试（Visual Regression）

### 4.1 为什么需要视觉回归？

```
纯功能测试的盲区：

  ✅ 测试能测到 "卡片存在"
  ❌ 测不到 "卡片阴影偏移了 1px"
  ✅ 测试能测到 "主题切换了"
  ❌ 测不到 "主题切换后按钮颜色不对"
  ✅ 测试能测到 "AI 生成结果了"
  ❌ 测不到 "AI 生成的排版乱了"
```

### 4.2 实现方案：Playwright Screenshot

```typescript
// e2e/visual-regression/visual.spec.ts
import { test, expect } from '@playwright/test';

test.describe('视觉回归测试', () => {

    // 截取预览区域
    const previewPanel = page.locator('.preview-panel');
    await expect(previewPanel).toHaveSapshot('preview-panel.png');

    await page.goto('/');
    await page.click('text=主题');
    await page.click('text=暗黑');
    await page.waitForTimeout(500);
    
    await expect(page).toHaveSapshot('dark-theme.png', {
      maxDiffPixelRatio: 0.02
    });
  });
});

  // 视觉回归配置

  snapshotDir: './e2e/__snapshots__',
  
  // 更新基线截图：
  // npx playwright test --update-snapshots
  
  // 在 CI 中，首先尝试用基线对比
  // 如果基线不存在，自动生成基线
  expect: {
    toHaveScreenshot: {
      threshold: 0.1,  // 10% 差异阈值
      maxDiffPixels: 200,
      animations: 'disabled', // 禁用动画减少噪音
    },
  },
  
  // 对于每个测试屏幕尺寸统一
  use: {
    viewport: { width: 1440, height: 900 },
    colorScheme: 'light',
  },
});
```

### 4.4 视觉测试维护策略

```
视觉回归测试的最大问题是"基线漂移"——每次 UI 改动都要更新截图。

解决方案：

  1. 按组件隔离截图区域（不截全页，只截关键区域）
  2. 设置合理的 diff 阈值（1%-2%）
  3. CI 中视觉测试作为告警（warning）而非阻断（blocking）
  4. 使用 Playwright UI Mode 可视化 diff：
     npx playwright test --ui
  
  工作流：
  开发改 UI → 视觉测试失败 → 人工审查 diff → 
    → 如果是预期改动 → npx playwright test --update-snapshots
    → 如果是非预期改动 → 修复 bug
```

## 五、策略三：状态验证（State Verification）

### 5.1 问题的本质

```
前端交互的可靠性 ≠ DOM 的正确性

用户看到的"卡片显示正确"只是表象，
真正的可靠性在于应用内部状态的一致性：

  编辑器内容 state → CHD 解析结果 state → 预览渲染 state
  
  任何一个环节断裂，UI 都会出 bug，
  但纯 DOM 检查可能发现不了。
```

### 5.2 通过 `page.evaluate()` 验证内部状态

```typescript
// e2e/utils/test-helpers.ts
import { Page } from '@playwright/test';

/**
 * 验证 Zustand store 中的状态
 */
export async function getZustandState(page: Page, storeName: string): Promise<unknown> {
  return await page.evaluate((name) => {
    // Zustand store 挂载在 window 上
    const store = (window as any).__ZUSTAND_STORES?.[name];
    return store?.getState();
  }, storeName);
}

/**
 * 验证编辑器内容
 */
export async function getEditorContent(page: Page): Promise<string> {
  return await page.evaluate(() => {
    // CodeMirror 6 通过 view.state.doc 获取内容
    const cm = (window as any).__CODE_MIRROR_VIEW;
    return cm?.state?.doc?.toString() || '';
  });
}

/**
 * 验证 CHD 解析结果
 */
export async function getCHDBlocks(page: Page): Promise<unknown[]> {
  return await page.evaluate(() => {
    // CHD 解析结果通常存储在缓存或 store 中
    const blocks = (window as any).__CHD_BLOCKS;
    return blocks || [];
  });
}

/**
 * 验证 localStorage 中的数据
 */
export async function getLocalStorageData(page: Page, key: string): Promise<string | null> {
  return await page.evaluate((k) => localStorage.getItem(k), key);
}

/**
 * 检查应用是否处于错误状态
 */
export async function hasAppError(page: Page): Promise<boolean> {
  return await page.evaluate(() => {
    return !!document.querySelector('.error-boundary-fallback');
  });
}
```

### 5.3 状态验证测试示例

```typescript
// e2e/core/01-editor-workflow.spec.ts 扩展
import { test, expect } from '@playwright/test';
import { getEditorContent, getCHDBlocks, getLocalStorageData } from '../utils/test-helpers';

test('编辑 → 保存 → 状态验证', async ({ page }) => {
  await page.goto('/editor/1');
  await page.waitForSelector('.cm-editor');
  
  // 1. 获取编辑前的状态
  const contentBefore = await getEditorContent(page);
  
  // 2. 进行编辑
  const editor = page.locator('.cm-content');
  await editor.type(' 新增内容测试');
  
  // 3. 等待自动保存
  await page.waitForTimeout(3500);
  
  // 4. 【关键验证】localStorage 中保存了正确的数据
  const savedContent = await getLocalStorageData(page, 'doc-content');
  expect(savedContent).toContain('新增内容测试');
  
  // 5. 【关键验证】CHD 解析结果与编辑器内容一致
  const blocks = await getCHDBlocks(page);
  expect(blocks.length).toBeGreaterThan(0);
  
  // 6. 验证没有错误状态
  const hasError = await hasAppError(page);
  expect(hasError).toBe(false);
});
```

## 六、测试可靠性工程（避免"脆性测试"）

### 6.1 常见脆性测试模式及对策

| 脆性模式 | 问题 | 对策 |
|---------|------|------|
| 依赖固定文本 `text=新建文档` | 改文案就挂 | 用 data-testid 属性 |
| `await page.waitForTimeout(3000)` | 慢 + 不稳定 | 用 waitForSelector / waitForResponse |
| 全页截图对比 | 任何像素变化都挂 | 按组件截图 + 设阈值 |
| 测试间状态依赖 | 顺序执行才过 | 每个测试独立 setup + teardown |
| 网络请求硬编码 | Mock 变化就挂 | 用 page.route() 拦截 |

### 6.2 推荐：使用 data-testid

```tsx
// 组件中（示例）
function ExportButton() {
  return (
    <button data-testid="export-btn" onClick={handleExport}>
      导出 HTML
    </button>
  );
}

// 测试中
await page.click('[data-testid="export-btn"]');
```

### 6.3 测试 Retry 策略

```yaml
# CI 配置中的 retry
- name: Run E2E tests
  run: npx playwright test --retries=2
  # 失败自动重试 2 次
  # 如果 3 次全失败，保留截图和 trace
```

## 八、总结：如何确认前端交互的可靠性

```
三层验证 + 工程保障 = 可靠的前端

┌──────────────────────────────────────────────────┐
│  ① 功能验证                                      │
│    10 个核心 E2E 测试用例                        │
│    → 覆盖所有 P0 用户流程                        │
├──────────────────────────────────────────────────┤
│  ② 视觉回归                                      │
│    关键页面截图对比                              │
│    → 发现像素级的 UI 偏差                        │
├──────────────────────────────────────────────────┤
│  ③ 状态验证                                      │
│    验证内部 state（Zustand / localStorage / ...）│
│    → 确认"看起来对"是真的对                      │
├──────────────────────────────────────────────────┤
│  ④ 工程保障                                      │
│    data-testid + retry + 独立测试 + 截图保留     │
│    → 测试本身是可靠的，不会"误报"                │
└──────────────────────────────────────────────────┘
```

> **结论**：一套好的前端 E2E 测试，不应该只验证"元素在不在"，  
> 而应该验证"用户操作后的结果是否符合预期"。  
> 通过功能验证 + 视觉回归 + 状态验证的组合，  
> 才能真正确认这个"偏前端交互设计"的系统是可靠的。
