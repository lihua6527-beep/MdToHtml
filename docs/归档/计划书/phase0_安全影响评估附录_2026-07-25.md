## 逐个分析

### 0.1 E2E 选择器修复

```
操作类型：修改已存在的文件（.spec.ts）
影响范围：仅测试文件
```

**当前状态**：6 个 E2E 测试**全部失败**（因选择器不匹配）。意味着：
- 不修 → 测试全红，CI 被阻挡
- 修了 → 测试变绿，零影响生产代码

**具体操作**：在 `.spec.ts` 中将旧的 CSS class name / data-testid 替换为当前 DOM 中实际使用的值。例如：
- `page.locator('.old-class')` → `page.locator('[data-testid="new-id"]')`
- 或修改等待条件：`page.waitForSelector('.old-class')` → `page.waitForSelector('.current-class')`

**是否需要修改生产组件（.tsx）添加 data-testid？**  
→ 仅在当前 DOM 确实缺少可用的选择器时才需要。根据子代理报告，99% 的情况只需调整测试侧的字符串即可。

**风险断言**：  
✅ 即使改错选择器 → 测试失败，不影响应用运行  
✅ 改对选择器 → 测试通过，零影响

### 0.3 操作类型系统（Plan 01）

```
操作类型：新建文件
影响范围：无（目前为零引用）
```

这是最需要谨慎确认的一项。来看：

**文件 1：`src/types/operation.ts`**
- 只定义 `OperationType` 枚举、`Operation`/`TextOperation`/`CardOperation`/`AiOperation`/`MetaOperation` 接口
- TypeScript 接口在编译时被擦除（compile-time only），**不会产生任何 JS 运行时代码**
- 枚举 `OperationType` 会被编译为 JS 对象，但只有被 import 才会打包——目前无任何文件 import 它

**文件 2：`src/lib/OperationBuilder.ts`**
- 定义工厂类 `OperationBuilder`，所有方法都是静态方法
- 同样，只有被 import 才会被加载——目前无任何文件 import 它

**何时会影响到现有功能？**  
→ 只有当 Phase 1（撤销引擎重构）修改 `useHistory.ts` 并 import `Operation` 时 —— 那是明确的后续阶段，Phase 0 **不触及** `useHistory.ts`。

**确认代码依赖链**：

```
现有的 useHistory.ts（string[]）
        │
        ▼
  不引用任何 operation.ts 中的内容（Phase 0 不做此修改）
        │
        ▼
  现有功能完全独立，不受影响 ✅
```

**风险断言**：  
✅ 纯新增 TypeScript 类型定义 + 工厂函数  
✅ 无任何现有文件引用新文件  
✅ 类型接口编译时不可见，运行时零影响

        验证：npx playwright test 通过
        
Step C: 仅做 0.2（缓存测试）→ 预计 1 小时完成

每个 Step 完成后都可以先跑一遍 `npm run dev` + 手动操作编辑器确认无异常，再继续下一个 Step。

## 结论

**Phase 0 四项子任务全部不属于"修改现有功能逻辑"的范畴。**  
它们是：
- 测试文件修复（0.1）
- 测试文件新增（0.2、0.4）
- 纯新增类型定义 + 工厂函数（0.3）

所有修改均不会影响现有功能的正确使用。如果需要更保守的验证，可以在每个子任务完成后运行 `npm run build` + 手动验证编辑器核心流程（打开文件、编辑、保存、撤销/重做），确保一切正常再继续下一步。
