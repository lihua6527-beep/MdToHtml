# 分析：计划03与06的整合分析与操作规范设计

> **分析日期**：2026-07-12
> **分析目标**：梳理 `03_useHistory撤销重做系统` 与 `06_编辑器内AI内联辅助编辑` 的依赖关系，提出统一的「操作规范」体系，并探讨 AI 辅助编辑的成本控制策略。

## 一、问题综述：两个计划的本质关系

```
               ┌──────────────────────────────┐
               │    编辑器内的操作抽象层        │
               │  (操作类型系统 / Operation DSL) │
               └──────────────┬───────────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
     ┌─────────────────┐ ┌──────────┐ ┌──────────────┐
     │ 手动编辑操作      │ │ AI辅助操作│ │ 未来其他操作  │
     │ (输入/删除/格式化)│ │ (润色/扩充│ │ (拖拽/批注/…)│
     │                 │ │ /转卡片等)│ │              │
     └────────┬────────┘ └─────┬────┘ └──────┬───────┘
              │                │              │
              └────────────────┴──────────────┘
                              │
                              ▼
                   ┌──────────────────┐
                   │  useHistory 撤销   │
                   │   / 重做 引擎     │
                   └──────────────────┘
```

**核心发现**：
- 03 和 06 不是两个独立的功能模块，而是**同一枚硬币的两面**
- 03 提供"操作记录与回退"的基础设施
- 06 是"操作生产者"之一（AI 也是操作源）
- 两者共享同一个抽象层：**操作类型系统**

当前两个计划各自独立设计，未建立统一的「操作规范」是最大的设计缺口。

## 二、核心问题：缺少统一的操作规范

### 2.1 当前现状

| 计划 | 操作定义方式 | 存储什么 | 能否回退 |
|------|------------|---------|---------|
| 03 | 纯文本 `string[]`，只存内容 | 完整文档快照 | ✅ 整篇回退，但粒度粗 |
| 06 | 无操作记录概念 | 无（AI 直接替换文本） | ❌ AI 操作不可撤销 |

### 2.2 问题链

```
没有统一操作规范
  → 03 只能整篇快照回退（粒度不够细）
  → 06 的操作无法被 03 记录
  → 用户用 AI 润色后，Ctrl+Z 无法撤销 AI 变更（UX 灾难）
  → 未来新增任何操作类型，都需要各自实现撤销逻辑（重复劳动）
```

### 2.3 用户提出的「操作编码」思路

用户提到的"对可被接受的操作进行类似于编码，记录每个位置的编码操作序列"——这正是**操作类型系统（Operation Type System）**的核心思想：

```
每个操作 = { type, position, payload, timestamp }

示例:
{ type: "INSERT_TEXT", position: { start: 120, end: 120 }, payload: "新文本" }
{ type: "AI_POLISH",   position: { start: 100, end: 200 }, payload: "润色后内容" }
{ type: "CARD_ADD",    position: { start: 300, end: 300 }, payload: "### Card {...}" }
```

## 三、操作类型系统设计建议

### 3.1 操作类型枚举

这是整个体系的"语法"基础，分为三大类：

```typescript
// ====== 核心操作类型 ======
enum OperationType {
  // --- 文本编辑（手动） ---
  INSERT_TEXT,       // 插入文本
  DELETE_TEXT,       // 删除文本  
  REPLACE_TEXT,      // 替换文本（选中后打字覆盖）
  
  // --- 卡片操作 ---
  CARD_ADD,          // 新增卡片
  CARD_DELETE,       // 删除卡片
  CARD_MOVE,         // 移动卡片位置
  CARD_STYLE_CHANGE, // 修改卡片样式（highlight/normal）
  
  // --- AI 辅助操作（由 06 引入） ---
  AI_POLISH,         // AI润色
  AI_EXPAND,         // AI扩充
  AI_TO_CARD,        // AI转卡片
  AI_SUMMARIZE,      // AI总结
  
  // --- 元操作 ---
  BATCH,             // 组合多个操作为原子操作（用于防抖合并）
  MARKER,            // 标记点（用于快照，不产生实际变更）
}
```

### 3.2 操作对象（Operation）的通用结构

```typescript
interface Operation {
  // 元信息
  id: string;                     // 唯一标识，用 nanoid 或递增序列
  type: OperationType;            // 操作类型
  timestamp: number;              // 发生时间
  batchId?: string;               // 同一批次 ID（用于防抖合并）
  
  // 位置信息（文档中的范围）
  position: {
    start: number;                // 起始字符偏移
    end: number;                  // 结束字符偏移
    // 可选的行列表示（对人友好）
    from?: { line: number; ch: number };
    to?: { line: number; ch: number };
  };
  
  // 操作数据
  payload: {
    before: string;               // 操作前的内容（用于回退）
    after: string;                // 操作后的内容
    // AI 特有的额外信息
    aiContext?: {
      model: string;              // AI 模型
      promptType: string;         // Prompt 类型
      tokensConsumed: number;     // 消耗 Token 数（对成本统计有用）
    };
  };
  
  // 展示信息（用于 UI 展示历史记录）
  display: {
    icon: string;                 // 图标 emoji
    label: string;                // 简短描述，如"润色了第 3 段"
    detail?: string;              // 详细描述
  };
}
```

### 3.3 位置编码：字符偏移 vs 行列号

这里有个关键设计决策：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **字符偏移**（start/end） | 计算简单，支持精确回退 | 如果前面内容变更，偏移会漂移 |
| **行列号**（line/ch） | 对人友好，直观 | 编辑器内部表示不一致 |
| **混合存储** | 兼顾两者 | 存储略大，但可接受 |

**建议**：**以字符偏移为主，行列号为辅助标注**。回退时通过"操作序列重放"而非直接跳转到偏移位置，来避免漂移问题。

## 四、撤销系统的改进：基于操作序列的回退

### 4.1 核心转变：从"快照回退"到"操作回逆"

```
当前 03 的设计：string[] past → 整篇内容的快照数组
                 缺点：粒度粗、无法区分操作类型、存储冗余

新的设计：     Operation[] operationLog → 操作序列
                 优点：粒度细、可选择性回退、支持白名单/黑名单
```

### 4.2 操作回逆（Inverse Operation）

每个操作都应该能生成一个逆操作：

```typescript
class Operation {
  // ...
  
  // 生成逆操作（用于撤销）
  invert(): Operation {
    return {
      ...this,
      type: this.type, // 类型不变
      payload: {
        before: this.payload.after,  // 前后互换
        after: this.payload.before,
      },
    };
  }
}
```

### 4.3 撤销引擎的核心算法

```typescript
class UndoRedoEngine {
  private undoStack: Operation[] = [];
  private redoStack: Operation[] = [];
  
  // 执行操作并记录
  execute(op: Operation) {
    applyOperation(op);               // 应用到编辑器
    this.undoStack.push(op);
    this.redoStack = [];              // 新操作清空重做栈
    this.persist();                   // 持久化
  }
  
  // 撤销：取最后一个操作 → 执行其逆操作
  undo() {
    const op = this.undoStack.pop();
    if (!op) return;
    const inverseOp = op.invert();
    applyOperation(inverseOp);        // 应用到编辑器
    this.redoStack.push(op);
    this.persist();
  }
  
  // 重做：取最后一个撤销的操作 → 重新执行
  redo() {
    const op = this.redoStack.pop();
    if (!op) return;
    applyOperation(op);
    this.undoStack.push(op);
    this.persist();
  }
}
```

### 4.4 如何兼容 AI 操作（06 的引入）

AI 操作与普通文本操作的区别在于：

| 维度 | 普通操作 | AI 操作 |
|------|---------|--------|
| 来源 | 用户键盘 | AI 服务响应 |
| 耗时 | 即时 | 数秒延迟 |
| 数据量 | 小（单次按键/粘贴） | 大（整段润色） |
| 确定性 | 100% 确定 | 概率性（可能不满意） |

**设计要点**：

1. **AI 操作也是 Operation**：06 中的所有 AI 操作（润色/扩充/转卡片/总结）都包装为 `OperationType.AI_POLISH` 等

2. **原子性问题**：AI 操作涉及"AI 返回建议 → 用户确认接受"的异步流程。有两种处理方式：

   ```
   方案 A（推荐）：
   用户点击"润色" → 创建 OPERATION.MARKER（占位标记）
   AI 返回 → 用户确认 → 执行真实的 AI_POLISH 操作
   用户拒绝 → 移除 MARKER，不产生历史记录
   
   方案 B（简单）：
   用户接受 AI 建议后，生成一个 REPLACE_TEXT 操作
   ❌ 丢失了"这是 AI 操作"的语义
   ```

3. **AI 操作的撤销展示**：在历史 UI 中显示"✨ AI 润色：第 3-4 段"而不是笼统的"内容编辑"

## 五、AI 辅助编辑的成本控制策略

### 5.1 问题重述

用户提出的核心痛点：

```
修改卡片文本 → 需要上下文理解
    ↓
如果只传卡片内容 → AI 缺乏上下文，容易"胡编"
如果传整篇文章 → Token 消耗大，缓存命中率低
    ↓
成本与质量的平衡
```

### 5.2 分层上下文策略

```
┌────────────────────────────────────────────┐
│  层级 1：最小上下文                          │
│  ================                           │
│  1. 选中文本本身（必传）                      │
│  2. 选中文本所在段落的前后 2 句（滑动窗口）    │
│  3. 当前 Section 标题                         │
│  → Token 消耗：~200-400 tokens              │
│  → 适用：润色、总结                          │
├────────────────────────────────────────────┤
│  层级 2：中等上下文                          │
│  ================                           │
│  1. 层级 1 的全部                            │
│  2. 当前 Section 的全部内容                   │
│  3. 前后相邻 Section 的标题 + 首句            │
│  → Token 消耗：~800-1500 tokens             │
│  → 适用：扩充、转卡片                        │
├────────────────────────────────────────────┤
│  层级 3：完整上下文                          │
│  ================                           │
│  1. 整篇文章内容                             │
│  2. 文章的元信息（标题、分类、日期等）          │
│  → Token 消耗：~2000-5000 tokens            │
│  → 适用：全篇重写、风格统一转换               │
└────────────────────────────────────────────┘
```

**关键设计**：**传入上下文的同时，标注"操作焦点"**，让 AI 明确知道它应该修改哪一部分：

```text
[文档上下文开始]
...（层级 1/2/3 的文本）...
[文档上下文结束]

========== 操作焦点 ==========
请对以下选中文本执行「润色」操作：
{selectedText}
============================
```

### 5.3 缓存策略

目前系统中已经有 `AIService` 对 DeepSeek API 的调用，缓存命中是关键的成本控制手段：

| 缓存维度 | Key 设计 | 命中场景 |
|---------|---------|---------|
| **精确匹配** | `md5(prompt)` | 用户对同一文本重复执行同一操作 |
| **模糊匹配** | `md5(操作类型 + 文本前 100 字)` | 类似内容的不同操作 |
| **会话内缓存** | 当前编辑会话内的所有 AI 请求 | 用户"试试不同风格"的反复尝试 |

**前缀缓存的优化**：DeepSeek 的 API 缓存机制基于 prompt 前缀。设计 prompt 时，**把固定部分放在前面**：

```text
[固定前缀] 你是一个中文文档助手…
[固定 Prompt 结构] 润色要求：1.… 2.… 3.…
[变量部分] 文本内容：{selectedText}
[更大变量] 上下文：{context}
```

这样多个请求共享相同前缀，提高缓存命中率。

### 5.4 渐进式加载（可选优化）

对于"扩充"这样可能产生大量文本的操作，可以采用流式输出：

```
用户点击"扩充" → 立即显示 loading
    ↓
AI 流式返回 → 逐字展示在建议替换弹窗中
    ↓
用户看到初步结果后可以：
  - 等待完成
  - 立即拒绝（停止流式，不消耗完整 Token）
```

**成本收益**：用户可以通过"预览即拒绝"来终止不满意的生成，避免浪费完整 Token。

## 六、整合建议：六个步骤

### Step 1: 先建立操作类型系统（独立于 03 和 06）

新增文件 `src/types/operation.ts`，定义 `OperationType`、`Operation` 等基础类型。这是两个计划的共同基座。

### Step 2: 改造 useHistory 为"操作序列引擎"

将当前 `string[]` 的 `past/future` 改造为 `Operation[]`，核心逻辑变为：

```
pushState(content: string)  →  pushOperation(op: Operation)
undo() → string              →  undo(): Operation | null
```

### Step 3: 保留防抖和持久化机制

03 中的 localStorage 持久化、300ms 防抖、50 步上限仍然适用，但存储的内容由 `string[]` 变为 `Operation[]`。

### Step 4: 实现 AI 操作的 Operation 包装

在 06 的 `handleAIAction` → `handleAcceptSuggestion` 流程中，生成 `OperationType.AI_POLISH` 等操作并推入引擎。

### Step 5: 实现上下文裁剪模块

新增 `services/ai/ContextBuilder.ts`，实现上文 5.2 节的"分层上下文策略"，供 06 使用。

### Step 6: 更新 USE HISTORY 的验收标准

新增验收项：

- [ ] AI 润色操作可以像普通编辑一样被撤销/重做
- [ ] AI 操作在历史记录中显示为"✨ AI 润色：xxx"（而非笼统的"内容编辑"）
- [ ] AI 操作消耗的 Token 数被记录，可展示

## 八、总结

| 维度 | 当前两个计划的盲区 | 整合后的收益 |
|------|------------------|------------|
| 操作定义 | 03 用纯文本，06 无定义 | **统一操作类型系统**，所有操作可追溯 |
| 回退粒度 | 整篇快照 | **操作级回退**，可选择性撤销 |
| AI 操作记录 | ❌ 不可撤销 | **AI 操作也是普通操作**，可撤销/重做 |
| 扩展性 | 新增操作需各自实现 | **一次实现，所有功能受益** |
| AI 成本 | 无上下文策略 | **分层上下文 + 前缀缓存优化** |
| 代码耦合 | 03 和 06 互相不知 | **通过操作类型系统松耦合** |

最终形成：

```
操作类型系统（规范）
   ├── 操作生产者：手动编辑 → 通过编辑器的 onChange 生成
   ├── 操作生产者：AI 辅助 → 通过 06 的确认按钮生成
   ├── 操作生产者：未来功能 → 基于同一接口扩展
   └── 操作消费者：useHistory → 记录、持久化、回退
```

以上是对两个计划书的全面分析与整合建议，核心结论是：**先定义操作规范（操作类型系统），再分别实现撤销和 AI 功能，两者通过同一抽象层解耦。**
