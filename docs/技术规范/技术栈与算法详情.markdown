# 技术栈与算法详情 (Tech Stack & Algorithms)

## 0. 核心理念与技术映射 (Philosophy to Tech Mapping)

> **你的系统本质上是在回答一个问题： 当AI能生成无限内容时，如何确保输出的品质与一致性？**
> 答案是： **协议化输入、自动化评分、可视化调优、多态化输出**。

本项目通过以下技术栈具体实现了上述理念：

| 核心理念 | 关键技术实现 | 对应模块/文件 |
| :--- | :--- | :--- |
| **协议化输入** | CHD (Canonical HTML Deck) 协议, Markdown AST 解析 | `src/lib/chdParser.ts`, `CHD_protocol.md` |
| **自动化评分** | 基于规则的文档质量打分引擎 | `src/lib/scorer.ts` |
| **可视化调优** | CodeMirror 双向绑定编辑器, 实时预览 | `src/components/Editor/`, `src/components/CHD/` |
| **多态化输出** | Next.js SSG 静态生成, 响应式 Grid 布局 | `app/api/save/`, `src/components/CHD/Section.tsx` |

## 1. 技术栈 (Tech Stack)

### 1.1 前端渲染引擎 (Frontend Rendering Engine)
- **Framework**: [Next.js 14 (App Router)](https://nextjs.org/) - 提供服务端渲染 (SSR) 和静态生成 (SSG) 能力，确保文档加载速度和 SEO。
- **Core Library**: [React 18](https://react.dev/) - 利用 Server Components 与 Client Components 的混合架构，分离静态内容与动态交互。
- **Styling**: 
    - [Tailwind CSS](https://tailwindcss.com/) - 原子化 CSS 框架，构建系统的视觉基座。
    - [shadcn/ui](https://ui.shadcn.com/) - 基于 Radix UI 的无头组件库，提供 Button, Dialog 等标准交互组件，支持 A11y。
- **Language**: TypeScript - 强类型约束，确保 CHD 数据结构解析的安全性。
- **Icons**: Lucide React - 现代、轻量级的图标库。
- **Markdown Plugins**:
    - [remark-breaks](https://github.com/remarkjs/remark-breaks) - 支持 GitHub Flavor 的硬换行逻辑 (Soft break -> Hard break)。
    - [remark-gfm](https://github.com/remarkjs/remark-gfm) - 支持表格、删除线等 GFM 扩展。
    - [remark-math](https://github.com/remarkjs/remark-math) & [rehype-katex](https://github.com/remarkjs/rehype-katex) - 数学公式渲染。

### 1.2 核心组件 (Core Components)
- **CodeMirrorEditor**: 基于 [CodeMirror 6](https://codemirror.net/) 的专业级 Markdown 编辑器，支持语法高亮、行号显示、代码折叠与双向滚动同步。
- **CHDRenderer**: 解析 Markdown AST 并映射为 Grid 布局的核心组件，支持行级交互同步。
- **GlobalErrorBoundary**: 全局异常熔断组件，捕获渲染层错误（如非法 CHD 语法），提供优雅降级 UI 与重试机制。
- **Card**: 遵循“百万级数据展示范式”的卡片组件，支持多种视觉变体 (Stat, Highlight, Quote 等) 及高亮状态。
- **Section**: 负责 L1 层级的网格容器，实现自然流布局。

### 1.3 脚本与工具 (Scripts & Tools)
- **PowerShell / Batch**: Windows 原生脚本语言，用于项目启动 (`start.bat`)、环境校验 (`validate_root.ps1`)。
- **Node.js**: 运行时环境，承载 Next.js 构建任务及运维脚本（如智能端口扫描 `setup-port.js`）。
- **Testing**:
    - **Jest**: 单元测试框架，配合 React Testing Library 进行组件快照与逻辑测试。
    - **Cheerio**: 静态页面解析库，用于自动化巡检生成的 HTML 产物。

## 2. 核心算法 (Core Algorithms)

### 2.1 智能尺寸计算与自动对齐 (Smart Sizing & Auto-Alignment)
**位置**: `src/components/CHD/CHDRenderer.tsx` & `src/components/CHD/Section.tsx`

为了解决卡片大小不一和排版单调的问题，系统实现了一套基于文本量的启发式尺寸计算算法，并结合 CSS Grid 实现了临界区域的自动对齐：

1.  **输入**: 卡片的纯文本内容长度 (`textLen`)。
2.  **逻辑**:
    *   **Micro Card**: `textLen < 150` -> `col-span-1`。适用于短文本、关键指标、简单列表。
    *   **Medium Card**: `150 <= textLen <= 400` -> `col-span-2`。适用于中等长度的描述、代码片段。
    *   **Macro Card**: `textLen > 400` -> `col-span-2` (限制最大宽度，防止霸屏)。长文本强制换行而非无限拉伸。
3.  **自动对齐 (Auto-Alignment)**:
    *   **Grid Flow Dense**: 在 `Section` 容器中启用了 `grid-flow-dense` 算法。
    *   **效果**: 当用户手动调整某张卡片为 `col-span-2` (导致当前行剩余空间不足) 时，后续较小的卡片 (`col-span-1`) 会自动回填到前一行的空缺中，消除布局孔洞，实现紧凑的“Bento Grid”风格布局。
    *   **Summary Override**: 针对 `style="summary"` 的卡片，渲染器强制将其设置为 `col-span-4` (全宽)，确保其作为独立行展示，不参与紧凑流布局。


### 2.2 幽灵卡片过滤 (Ghost Card Filtering)
**位置**: `src/components/CHD/CHDRenderer.tsx`

解析 Markdown 时，分隔符和空行容易产生无效的 AST 节点（幽灵卡片），导致页面出现莫名其妙的空白或细线。

**过滤逻辑**:
1.  **预清洗**: 移除所有仅仅包含 `---`、空格或换行符的内容块。
2.  **严格匹配**: 只有以 `###` 开头的节点才被视为有效卡片。
3.  **尾部修剪**: 自动去除每个卡片内容末尾的 `---` 分隔符。

### 2.3 静态资源自动化巡检与单文件导出 (Static Asset Inspection & Single-File Export)
**位置**: `scripts/process_single_file.js` & `/api/save-export`

为了确保输出产物的独立性与渲染一致性，系统采用了**双重导出策略**：

1.  **单文件结构 (Single-File Structure)**: 
    *   配置 `trailingSlash: false`，使 Next.js 生成 `slug.html` 而非 `slug/index.html`。
    *   **同步导出 (Sync Export)**: 编辑器端的“导出 HTML”按钮会触发客户端渲染，抓取当前完美的 DOM/CSS 状态，生成内联样式的 HTML，并通过 `/api/save-export` 接口同步保存到 `output/` 目录。这确保了静态产物与编辑器预览的**像素级一致 (Pixel-perfect)**。

2.  **目录治理 (Directory Governance)**:
    *   **系统归档**: 自动将 `index.html`, `404.html` 等非内容页面移动到 `output/system/`。
    *   **中文解码**: 自动将 URL 编码的文件名重命名为可读中文。
    *   **依赖清理**: 删除 `_next` 等外部依赖目录，确保 HTML 文件的自包含性。

3.  **自动化巡检 (Legacy)**:
    *   (已废弃/降级) `verify-static-build.js` 曾用于检查 `next build` 产物，现主要依赖上述同步导出机制保证质量。

## 3. 编辑器交互算法 (Editor Interaction Algorithms)

### 3.1 智能编辑模式 (Smart Edit Mode)
**位置**: `src/app/editor/page.tsx` (Logic) & `src/components/CHD/Card.tsx` (UI)

为了实现“所见即所得”的卡片属性调整，系统采用了**逆向源码更新算法**：

1.  **UI 触发**: 用户在预览模式下开启 `editMode`，点击 Card 上的 Size/Style 控件。
2.  **事件冒泡**: 变更事件携带 `lineIndex` (卡片所在的 Markdown 行号) 和 `newAttributes` (如 `{ 'col-span': 2 }`) 向上冒泡。
3.  **源码解析与重构**:
    *   **正则定位**: 使用 `/^(###\s+.*?)(?:\s*(\{.*\}))?$/` 精准匹配目标行。
    *   **属性合并**: 解析现有的 `{ key="val" }` 属性块，将新属性合并覆盖。
    *   **字符串重组**: 将 `### Title` + `Updated Attributes` 重新组合成 Markdown 字符串。
4.  **状态更新**: 更新 React 状态中的 `content`，触发编辑器和渲染器的同步刷新。

### 3.2 训练样本自动录入 (Auto-Training Data Logging)
**位置**: `src/app/api/dataset/route.ts` & `src/lib/chdParser.ts`

为了构建用于训练 "Markdown -> CHD Blocks" 语义解析模型的高质量数据集，系统建立了自动化的数据闭环：

1.  **触发时机**: 用户点击 "Save to Workspace" 保存文件时。
2.  **数据构建**:
    *   **Input**: 当前编辑器的完整 Markdown 文本。
    *   **Output**: 调用 `parseCHDBlocks` 生成的标准 JSON 结构 (包含 Section/Card 层级与元数据)。
3.  **持久化**: 通过 POST 请求发送至 `/api/dataset`，后端将其追加到 `data/training_dataset.jsonl` 文件中。
4.  **价值**: 随着用户使用编辑器编写文档，自动积累了大量人工校对过的 "源码-结构" 对，无需额外标注成本。

### 3.4 静态生成与中文路径兼容性 (Static Export & Chinese Path Compatibility)
**位置**: `src/app/[slug]/page.tsx`

在 `output: export` 模式下，Next.js 对 `generateStaticParams` 返回的参数有严格校验。针对中文路径（如 `示例1.md`），浏览器请求时 URL 往往会被编码（`%E7%A4%BA...`）。
为了确保构建与访问的稳定性，系统采取了双重保障策略：
1.  **双重参数返回**: `generateStaticParams` 同时返回原始中文 Slug (`示例1`) 和 编码后的 Slug (`%E7...`)。
2.  **运行时解码**: 页面组件 (`Page`) 统一对传入的 params 进行 `decodeURIComponent`，确保无论路由匹配到哪种形式，都能正确读取文件。

### 3.5 交互式预览与编辑策略 (Interactive Preview & Editing Strategy)
**位置**: `src/components/InteractivePost.tsx` & `src/app/[slug]/page.tsx`

为了在静态生成的页面 (`[slug]/page.tsx`) 中实现“即时编辑”功能，系统采用了 **Client Component Wrapper** 模式：

1.  **架构分离**: 
    *   `page.tsx` (Server Component): 负责构建时的静态内容获取 (FileSystem Access) 和 SEO 元数据生成。
    *   `InteractivePost.tsx` (Client Component): 负责接管浏览器端的交互状态 (Edit Mode Toggle, State Management)。
2.  **状态接力**: 
    *   Server Component 将读取到的 Markdown 文本作为 `initialContent` prop 传递给 Client Component。
    *   Client Component 使用 `useState` 初始化本地编辑状态，后续交互完全在客户端进行，无需服务器往返。
3.  **统一渲染**: 无论是编辑器页还是独立预览页，均复用 `CHDRenderer` + `useMarkdownInteraction` 组合，确保编辑体验（快捷键、拖拽、属性修改）的高度一致性。

### 3.6 主题系统实现 (Theme System Implementation)
**位置**: `src/lib/themes.ts` & `src/components/ThemeProvider.tsx`

实现了基于 CSS 变量 + Tailwind 的动态主题切换：

1.  **变量定义**: 在 `globals.css` 中定义 `:root` (Light) 和 `.dark` (Dark) 下的语义化变量 (如 `--bg-page`, `--text-primary`)。
2.  **Tailwind 映射**: 在 `tailwind.config.ts` 中将 `bg-page` 映射为 `var(--bg-page)`，使 Tailwind 类名具备主题响应能力。
3.  **状态管理**: `ThemeProvider` 负责监听系统偏好并持久化用户选择 (LocalStorage)，通过 Context API 全局分发主题状态。
4.  **局部主题 (Scoped Theming)**: `EditorPage` 使用 `data-theme` 属性仅将主题应用于预览区域容器，而编辑器 UI 保持中立。

### 3.7 Next.js 模块解析与 Client Manifest 修复 (Next.js Module Resolution & Client Manifest Fix)
**位置**: `src/components/InteractivePost.tsx`

在 React Server Components (RSC) 架构中，Server Component 引用 Client Component 时可能会遇到 `React Client Manifest` 查找失败的错误。这通常是由于 Named Export 在特定的构建缓存状态下解析异常导致的。

**解决方案**:
1.  **Default Export**: 强制将所有被 Server Component 直接引用的顶层 Client Component 改为 `export default`。
2.  **Manifest 重建**: 遇到此类错误时，必须执行 `rm -rf .next` 清除构建缓存，强制 Next.js 重建模块映射表。

### 3.8 Section 级交互控制 (Section Level Interaction)
**位置**: `src/components/CHD/Section.tsx`

为了提升编辑效率，系统在 Section 层级引入了批量控制与样式配置能力：

1.  **字体统一 (Unify Fonts)**: 
    *   **机制**: 遍历 Section 内所有卡片，批量触发 `onCardUpdate` 事件，将 `title-size` 或 `content-size` 属性设置为目标值。
    *   **价值**: 快速统一区块内的视觉层级，避免逐个卡片调整的繁琐。
2.  **区块着色 (Section Color)**:
    *   **机制**: 在 Section 的 `layoutProps` 中存储 `section-color` 字段 (如 `bg-blue-50/50`)。
    *   **渲染**: `Section` 组件读取该属性并将其作为 Tailwind 类名动态注入到 `<section>` 容器的 `className` 中。

### 3.9 单文件导出与主题一致性 (Single File Export & Theme Consistency)
**位置**: `src/lib/export/HtmlBundler.tsx` & `src/lib/export/CssExtractor.ts`

为了满足“编辑分离、导出内聚”的核心理念，并解决导出文件与编辑器主题不一致的问题，系统实现了基于客户端的单文件打包方案：

1.  **资源内聚 (Resource Bundling)**:
    *   **HTML**: 使用 `renderToStaticMarkup` 将 React 组件树渲染为静态 HTML 字符串。
    *   **CSS**: `CssExtractor` 遍历当前页面的 `document.styleSheets`，提取所有 CSS 规则（包括 Tailwind 原子类和组件样式），内联到 `<style>` 标签中。
    *   **Images**: (规划中) 将图片资源转换为 Base64 编码内嵌入 HTML。

2.  **主题一致性 (Theme Consistency)**:
    *   **问题**: 浏览器 `prefers-color-scheme` 可能与用户在编辑器中手动选择的主题（如 Ocean, Mint）不一致，且自定义 CSS 变量（如 `--bg-page`）无法自动跨文件传递。
    *   **解决方案**: `HtmlBundler.bundle` 方法新增 `theme` 参数（如 `ocean`）。
    *   **实现**: 
        *   在导出时捕获当前应用的 `theme` 状态。
        *   将 `data-theme="{theme}"` 属性直接注入到导出模版的 `<html>` 标签中。
        *   移除所有基于系统偏好 (`prefers-color-scheme`) 的自动切换逻辑，强制导出文件的主题与编辑时保持 100% 一致，实现真正的“所见即所得”。

3.  **布局还原 (Layout Fidelity)**:
    *   **容器升级**: 导出页面的容器宽度从默认的 `max-w-4xl` 提升至 `90rem` (约 1440px)，并强制 `min-height: 100vh`，以匹配编辑器在宽屏下的沉浸式体验。
    *   **样式修正**: 修正了 `Card` 组件的背景色映射，从 Shadcn 默认的 `bg-card` 改为项目自定义的 `bg-bg-card`，确保在任何主题下都能正确显示背景色。

4.  **性能优化**:
    *   **Context Isolation**: 仅针对当前编辑的文档进行打包，不涉及服务器端构建，秒级生成。
    *   **Client-Side Blob**: 全部操作在浏览器端完成，生成 `Blob` 对象并触发下载，无服务器带宽消耗。

## 4. 部署与运维 (Deployment & Ops)
