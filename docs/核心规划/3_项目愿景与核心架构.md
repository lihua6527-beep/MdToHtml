# 项目愿景与核心架构 (Project Vision & Architecture)

## 1. 核心愿景：从博客工具到设计引擎

项目的核心诉求从最初的“搭建一个个人博客”演进为“构建一个规范化的 Markdown 多样化转换引擎”。

- **核心目标**: 在 Windows 本地环境中，将 Markdown 文本高效、精准地转换为高质量的静态 HTML 网页。
- **部署场景**: 生成的静态 HTML 文件 (`output/`) 可直接部署到任何静态网站托管服务，但 **转换过程** 严格限制在本地进行。
- **非目标 (Out of Scope)**:
  - ❌ **不支持云端在线转换**: 不提供 SaaS 服务，不涉及后端 API 部署。
  - ❌ **不支持跨平台运行**: 仅针对 Windows 环境优化，不适配 Linux/macOS。
  - ❌ **不支持并发处理**: 采用单线程/顺序处理模式，确保稳定性与简单性。

- **原始痛点**：传统博客工具千篇一律，手动排版耗时且难以维护。
- **终极形态**：一个 **“设计编译器”**。输入是极简、强约束的 Markdown (CHD 协议)，输出是多样化、高品质的网页、幻灯片或 PDF。
- **价值主张**：
  - **智能化输入**：利用 AI 将模糊意图转化为符合协议的精确代码。
  - **确定性内核**：利用规则引擎保证渲染的绝对稳定与高性能。
  - **产品化输出**：同一份内容，一键生成博客、PPT 或 PDF。

## 2. 交互演进三阶段 (Three-Phase Evolution)

为了实现从“人工编辑”到“全面智能”的平滑过渡，我们规划了三个逐渐递进的阶段：

### 第一阶段：标准化输入与人工调整 (Standardization & Manual Adjustment)
**当前状态：Phase 1.5 (Protocol Definition & AI Readiness)**

*   **核心逻辑**：用户使用标准化的 Markdown 文档输入，并自行调整。
*   **实现方式**：
    *   **强约束编辑器**：基于 CodeMirror 6 的专业级 Markdown 编辑器，强制用户按照 CHD 协议（Section -> Card）进行输入。
    *   **实时校验**：前端内置 Linter，实时检测语法错误（如错误的标题层级），引导用户修正。
    *   **人工微调**：用户通过可视化界面手动选择卡片样式（如 `highlight`, `quote`）和布局列数。
*   **目的**：建立用户对 CHD 结构的认知，同时 **积累高质量的“标准输入-标准输出”数据对**。

### 第二阶段：AI 辅助与协议驱动 (AI Assistance & Protocol Driven)
**目标状态：智能增强版 (Phase 1.5 - Phase 2)**

*   **核心逻辑**：以 CHD v1.5 协议为蓝本，利用通用大模型 (LLM) 进行非结构化文本到结构化 Markdown 的转换，并逐步积累数据训练端侧小模型。
*   **实现方式**：
    *   **Prompt 工程**：构建基于 CHD 协议的高质量 System Prompt（详见 `5_CHD协议与AI生成指南.md`），使 GPT-4/Claude 能直接生成可用文档。
    *   **智能识别**：用户粘贴一段自由文本，AI 自动识别语义，将其拆分为 Section 和 Card，并自动应用 `highlight`, `quote`, `code` 等样式。
    *   **布局建议**：AI 根据文本长度和内容类型，自动推荐最佳的布局策略（如识别到多组对比数据推荐 `columns=2`）。
    *   **人机协作**：AI 提供“预填充”结果，用户只需进行确认或微调。
*   **目的**：降低输入门槛，提升写作效率，验证“约束换智能”的可行性。

### 第三阶段：全面智能与个性化 (Full Intelligence & Personalization)
**终极状态：个性化设计引擎**

*   **核心逻辑**：完成小模型训练，同时支持用户个性化页面的选项。
*   **实现方式**：
    *   **个性化微调**：模型根据用户的历史偏好（如喜欢紧凑布局还是宽敞布局，喜欢深色模式还是浅色模式），自动调整渲染参数。
    *   **风格迁移**：支持用户上传参考图或选择风格关键词（如“科技感”、“学术风”），系统自动生成对应的 CSS 变量和组件变体。
    *   **动态重组**：根据浏览者的设备和偏好，动态重组文档结构（如在移动端自动折叠次要卡片）。
*   **目的**：实现“千人千面”的文档呈现，让文档适应人，而不是人适应文档。

## 3. 总体架构：双螺旋协同 (Dual-Helix Architecture)

DocMind 由两个核心子项目构成，互为支撑：

1.  **Markdown 转换项目 (DocMind Core)**：
    - 负责：前端交互、CHD 协议校验、AST 生成、最终渲染。
    - 角色：应用场景提供者、数据生产者。
2.  **数据蒸馏项目 (DocMind AI)**：
    - 负责：训练任务特化小模型（Structure Understanding Model）。
    - 角色：核心智能能力提供者。

### 关键约束 (Architecture Constraints)
1.  **单机运行**: 所有逻辑在用户本地 PC 上执行，无外部网络依赖（除安装依赖外）。
2.  **文件驱动**: 数据源仅为本地 Markdown 文件，不连接数据库。
3.  **Windows 优先**: 脚本与工具链优先使用 PowerShell/Batch，不引入 Unix 兼容层。

### 端到端业务流程

```mermaid
flowchart TD
    subgraph User Input [用户输入层]
        UI[前端表单/编辑器] -->|Phase 1: 强约束| Draft[草稿文本]
        Draft -->|提交| Validator[CHD 协议校验器]
    end

    subgraph AI Processing [智能处理层]
        Validator -->|合格| RuleEngine[规则引擎 (RegEx)]
        Validator -->|Phase 2: 模糊/复杂| SmallModel[任务特化小模型]
        
        RuleEngine --> AST[初步 AST]
        SmallModel -->|语义标注/布局建议| AST
    end

    subgraph Core Engine [核心引擎层]
        AST --> Transformer[AST 转换器]
        Transformer -->|Phase 3: 个性化参数| FinalAST[标准化 AST]
        FinalAST --> Renderer[React/Next.js 渲染器]
    end

    subgraph Output [输出层]
        Renderer --> WebPage[精美网页]
        WebPage -->|用户反馈| DataLake[训练数据湖]
    end

    DataLake -.->|微调| SmallModel
```

## 4. 关键数据流

1.  **输入 (Input)**：用户在前端输入，系统实时校验 CHD 规范。
2.  **智能解析 (AI Processing)**：
    - **规则路径**：标准结构直接正则解析。
    - **模型路径**：复杂文本调用小模型推理，输出语义标签 (Tags) 和布局建议 (Layout Hints)。
3.  **AST 构建 (AST Construction)**：生成包含 `type` (Section/Card), `content`, `metadata` (style, layout) 的 JSON 树。
4.  **渲染 (Rendering)**：渲染引擎遍历 AST，将 `Card` 节点映射为 React 组件，结合个性化主题参数生成最终页面。
