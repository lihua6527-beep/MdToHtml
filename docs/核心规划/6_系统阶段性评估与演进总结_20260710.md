## 2. 架构体系评估

### 2.1 架构模式

```
┌─────────────────────────────────────────────────────────┐
│                   Presentation Layer                      │
│  app/page.tsx → HomeClient → DocumentList / AIArea        │
│  app/editor/ → EditorPage → CodeMirror + CHDRenderer     │
│  app/preview/ → PreviewPage → CHDRenderer                │
├─────────────────────────────────────────────────────────┤
│                   Component Layer                         │
│  CHD/ (CHDRenderer → Section → Card)                     │
│  AI/ (AIArea → AIInputPanel + AITempFileList)             │
│  ui/ (Button, Input, Select, Dialog 等 shadcn 风格)      │
│  SettingsPanel, RecycleBin 等业务组件                     │
├─────────────────────────────────────────────────────────┤
│                   Hooks Layer (逻辑层)                     │
│  useFileSystem, useDocumentState, useMarkdownInteraction   │
│  useCHDSelection, useHistory, useDebounce 等 12+ hooks   │
├─────────────────────────────────────────────────────────┤
│                   Services Layer                          │
│  FileService / TrashService / ConfigService               │
│  core/ (ApiClient, TransactionManager, ErrorHandler)      │
│  ai/ (AIService, PromptEngine, TempFileManager)           │
├─────────────────────────────────────────────────────────┤
│                   Lib Layer (纯函数)                       │
│  chdParser / attributeParser / cache-manager / shapes     │
│  export/ (HtmlBundler, CssExtractor, template)            │
└─────────────────────────────────────────────────────────┘
```

### 2.2 架构评级

| 维度 | 评级 | 说明 |
|------|------|------|
| 分层清晰度 | ⭐⭐⭐⭐⭐ | 严格的 5 层架构：Page → Component → Hook → Service → Lib |
| 依赖方向 | ⭐⭐⭐⭐⭐ | 单向依赖：Page → Component → Hook → Service → Lib，无循环依赖 |
| 组件复用 | ⭐⭐⭐⭐ | 通用 UI 组件化良好，CHD 渲染体系组件可独立使用 |
| 状态管理 | ⭐⭐⭐⭐ | 纯 Hooks 链（无 Redux），简洁高效，但跨组件共享依赖 props 逐层传递 |
| 服务端/客户端分离 | ⭐⭐⭐⭐ | SSR → CSR 切换清晰，API Routes 集中在 /api/ |
| 可测试性 | ⭐⭐⭐ | 纯函数层 (lib/) 测试覆盖好，但组件测试较少 |

### 2.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 状态管理 | 纯 React Hooks（无 Redux） | 项目规模适中，Hooks 链足够；减少依赖复杂度 |
| 数据获取 | SWR | 自动缓存、去重、后台刷新，适合 CRUD 场景 |
| 编辑器 | CodeMirror 6 (@uiw/react-codemirror) | 性能优秀，Markdown 生态好，React 封装完善 |
| 样式方案 | Tailwind CSS + clsx | 原子化 CSS，避免样式冲突，构建体积小 |
| Markdown 渲染 | react-markdown + remark/rehype 插件 | 可扩展的插件生态，支持 GFM/LaTeX/Breaks |
| 缓存策略 | Top 500 + 异步扫描 + 内存 Cache | 首页 O(1) 加载，内存与磁盘两级持久化 |

## 3. 核心算法分析

### 3.1 CHD 块解析器 (lib/chdParser.ts)

| 属性 | 描述 |
|------|------|
| **算法类型** | 逐行状态机 (Line-by-line State Machine) |
| **复杂度** | O(n) — 单次遍历 |
| **状态变量** | `inFrontmatter`, `inCodeBlock`, `inCard`, `currentBlock` |
| **输出** | `CHDBlock[]` (section/card/frontmatter/code) |
| **层级信息** | 通过 startLine/endLine 隐含表达 |

**算法流程**：
```
遍历每一行 →
  检测 Frontmatter (行0 === '---')  → 进入/退出 frontmatter
  检测代码块 (startsWith('```'))    → 进入/退出 codeBlock
  检测 Section (startsWith('## '))  → 新 block
  检测 Card (startsWith('### '))    → 新 block（在 section 内）
  普通内容                          → 归并到当前 block
```

### 3.2 属性解析器 (lib/attributeParser.ts)

| 属性 | 描述 |
|------|------|
| **算法类型** | 正则提取 + 字符串操作 |
| **复杂度** | O(n) |
| **核心正则** | `/([a-zA-Z0-9_-]+)=(?:"([^"]*)"|'([^']*)'|([^,\s}]+))/g` |
| **输入** | `"My Card {card-style=highlight col-span=2}"` |
| **输出** | `{ cleanText: "My Card", props: { "card-style": "highlight", "col-span": "2" } }` |

**边缘情况处理**：
- 中文括号 `｛｝` → 自动标准化为 `{}`
- 无等号内容 `{grid}` → 不视为属性
- 支持双引号/单引号/无引号三种值格式
- 多层嵌套 → 只识别最后一对 `{}`

### 3.3 形状系统 (lib/shapes.ts)

| 属性 | 描述 |
|------|------|
| **设计模式** | 枚举映射 (Enum → CSS Class Lookup) |
| **形状数量** | 12 种 (rect, round, pill, leaf, diamond, hexagon, ticket, message, cut, arrow, circle, floating) |
| **接口** | `getShapeClass(shape: CardShape) → string` |

### 3.4 缓存管理器 (lib/cache-manager.ts)

| 属性 | 描述 |
|------|------|
| **设计模式** | 单例 (Singleton) + 多级缓存 (Multi-tier) |
| **L1 缓存** | 内存 Map — `getAll()` O(1) 返回 |
| **L2 持久化** | 磁盘 `.cache.json` — 启动时加载，定时保存 |
| **同步策略** | 启动后 500ms 异步后台扫描磁盘差异 |
| **容量管理** | Top 500，超限自动归档最旧条目 |
| **并发控制** | `pendingScan` 标志防重复扫描 |

### 3.5 数据流特征

| 模式 | 示例 |
|------|------|
| **单向数据流** | content state → CHDRenderer → Section → Card |
| **编辑器↔渲染器双向同步** | CodeMirror onChange → setContent → CHDRenderer 重渲染 |
| | 渲染区 onCardClick → setActiveLine → CodeMirror scrollToLine |
| **Event 通信** | `app-paths-updated` 事件通知文档列表刷新 |
| **SWR 缓存失效** | 保存/删除操作后 `mutate()` 触发 API 重新请求 |

## 5. 编程风格与质量

### 5.1 风格规范

| 维度 | 规范 | 一致性 |
|------|------|--------|
| 组件定义 | 函数组件 + TypeScript | ⭐⭐⭐⭐⭐ 100% |
| 客户端标记 | `'use client'` 指令 | 客户端组件均标记 |
| 命名规范 | PascalCase (组件/类型), camelCase (变量/函数) | ⭐⭐⭐⭐⭐ |
| 注释风格 | 中文注释 + JSDoc (部分关键函数) | ⭐⭐⭐⭐ |
| 泛型使用 | `useSWR<T>()`, `ApiClient.request<T>()` | ⭐⭐⭐⭐ |
| CSS 方案 | Tailwind CSS + clsx + twMerge | ⭐⭐⭐⭐⭐ |
| 导入组织 | 外部依赖 → 内部模块 → 相对路径 | ⭐⭐⭐⭐ |

### 5.2 设计模式使用

| 模式 | 使用位置 |
|------|----------|
| 策略模式 (Strategy) | `getLayoutStrategy()` — 布局策略动态路由 |
| 状态机 (State Machine) | `chdParser.ts` — 解析状态流转 |
| 单例 (Singleton) | `cache-manager.ts` — 全局唯一缓存实例 |
| 外观模式 (Facade) | `useFileManager` — 聚合多个 SWR Hook |
| 模板方法 (Template) | HtmlBundler.bundle() — 固定导出流程 |

### 5.3 代码质量指标

| 指标 | 评估 |
|------|------|
| DRY 原则 | 较好，lib/ 层纯函数复用度高 |
| 单一职责 | 良好，每个 Hook/Service 职责明确 |
| 错误处理 | 统一 ErrorHandler + ApiClient 重试机制 |
| 边界情况 | 属性解析器处理了中文括号/多层嵌套等边缘案例 |
| 性能考量 | useMemo 缓存解析结果，SWR 去重请求，防抖自动保存 |

## 8. 关键决策复盘

### 8.1 成功决策

| 决策 | 效果 |
|------|------|
| **放弃图标系统** | 移除 ≈15 个文件，减少维护负担，代码库精简 10% |
| **CodeMirror 6** | 编辑器性能与功能远超原生 textarea，支持扩展插件 |
| **Hooks 链替代 Redux** | 无额外依赖，状态流清晰，调试简单 |
| **SWR 数据获取** | 自动缓存 + 去重 + 后台刷新，减少大量模板代码 |
| **Tailwind CSS + clsx** | 样式开发效率高，无 CSS 冲突，构建体积小 |

### 8.2 教训与改进点

| 教训 | 改进措施 |
|------|----------|
| 图标系统投入过大但使用率低 | 在添加功能前应做需求确认和 ROI 评估 |
| API 端点数量膨胀 | 第3阶段已精简合并，后续应遵循开闭原则 |
| 文档未及时同步代码变更 | 建立文档审计流程，关键文档与代码变更绑定 |
