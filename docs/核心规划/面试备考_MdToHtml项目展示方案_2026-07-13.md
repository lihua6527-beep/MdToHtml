## 二、各知识维度学习方案

### 🔴 P0：面试必问（面试核心 — 至少聊 30 分钟）

#### 1. 项目深挖 — 六个核心模块面试话术

**目标**：能对着白板画架构图讲 5 分钟，每个技术点能用自己话讲透。

---
**模块 1：CHD 解析器**

> **面试官**：介绍一下你的 CHD 解析器。  
> **你的回答**：CHD 是我自研的卡片式层级文档协议，三层刚性结构——L0 YAML 元信息、L1 Section 容器、L2 Card 卡片单元。解析器采用 DFA 状态机实现，有 6 个状态（初始/文档元/标题/区块引用/代码块/表格），单遍扫描 O(n) 时间复杂度。与传统正则或递归下降解析相比，DFA 没有回溯，解析 1000 行文档只需 12ms 左右。

> **追问**：为什么用 DFA 不用递归下降？  
> **回答**：递归下降在嵌套结构上优雅，但 CHD 协议是刚性三层，没有深层嵌套，DFA 更简单、更快、天然无栈。和词法分析器类似，状态转移表清晰可测。

---
**模块 2：LRU-500 缓存**

> **面试官**：为什么用 LRU，不用 LFU 或 FIFO？  
> **你的回答**：Markdown 文档访问有时间局部性——用户编辑时反复读写同一篇文档。LRU 正好匹配这个模式。FIFO 不考虑访问频率，可能淘汰高价值缓存；LFU 需要维护计数器，实现更复杂。LRU 用双向链表 + HashMap 的 O(1) 实现，500 的容量经过测试——覆盖了 97% 的日常使用场景，再多收益递减。

> **追问**：缓存击穿怎么处理？  
> **回答**：项目采用缓存预热 + SWR（stale-while-revalidate）策略。热点文档在启动时预加载，缓存失效时先返回旧数据，后台刷新。

---
**模块 3：SSR 首屏优化**

> **面试官**：首屏 280ms 是怎么做到的？  
> **你的回答**：三步策略。首先是 SSR（服务端渲染），Next.js App Router 在服务端生成 HTML，避免客户端空的 HTML 再请求 JS。第二步是惰性编译——编辑器依赖 CodeMirror 6（~200KB），只在用户点击编辑时才加载，不阻塞首屏。第三步是缓存预热，首页文档列表在构建时就生成 HTML 片段。三管齐下，从 1.85s 压到 280ms。

---
**模块 4：AI 集成（本地代理 + 可靠性设计）**

> **面试官**：AI 生成是怎么接入的？API Key 安全怎么保证？  
> **你的回答**：浏览器不直连 DeepSeek，所有请求走本地 Next.js API Route（`/api/ai/generate`）代理——前端只提交「文本 + 模型 + Prompt 变体」，API Key 由服务端 ApiKeyManager 读取，只在服务端拼接 Authorization 头，不出现在任何前端 bundle 里。当前实现是单请求整包返回（`stream: false`），服务端做模型白名单、120s 超时中止、4096 token 封顶与空响应守卫；前端 AIService 做 3 次指数退避重试（1s/2s/4s）和错误码→中文提示映射，让用户看到的是"可行动的报错"而不是干转圈。另外我用三级 Token 预算控制（Minimal 200-400、Medium 800-1500、Full 2000-5000）防止用户误操作产生过高 API 费用。

> **追问**：为什么不做流式输出（SSE）？  
> **回答**：早期评估过 SSE，最终为了先把"超时、重试、幂等、中断恢复"这些可靠性问题做简单、做透，选择了整包返回；体验上用加载动画 + 预计耗时补偿。流式已列入 Roadmap——届时在 `/api/ai/generate` 开启 `stream` 分支，前端用 fetch 的 `ReadableStream` 逐块解析并渐进渲染。

---
**模块 5：四层架构设计**

> **面试官**：为什么分成四层？  
> **你的回答**：分离关注点。Core Library 层是纯函数，不依赖任何 UI 框架，可以独立测试和复用——比如 CHD 解析器如果以后要做 CLI 工具，直接拉走就能用。Service 层封装副作用（文件 IO、AI 调用）。Application 层用 Zustand + SWR 管理状态。Presentation 层纯 UI。每层依赖都是单向的，改 UI 不碰解析逻辑。

---
**模块 6：Electron 打包 + 体积优化**

> **面试官**：18MB 的安装包是怎么做到的？  
> **你的回答**：首先 Electron 本身最小约 50MB，但使用 electron-builder 的 portable 模式 + 精简依赖、选择 asar 打包、去除不必要的 Chromium 特性、使用 prebuilt 二进制，最终压缩到 18MB。相比 Typora 85MB、Obsidian 95MB，我们的体量优势明显。但也要承认，这牺牲了一些内置功能（如拼写检查、自动更新等）。

### 技术类

**Q: 项目中遇到的最大挑战是什么？**
> 首屏优化。初始版本用 CSR，首屏 1.85s。后来改为 SSR + 惰性加载 CodeMirror + 缓存预热三步组合优化，最终 280ms。难点是不只是改一个配置，需要理解 Next.js 渲染机制、React 组件加载时机、浏览器关键渲染路径三个层面的知识才能解决问题。

**Q: 如果让你重新设计这个项目，你会改变什么？**
> 早期把太多逻辑放在 React 组件里，后来才拆出 Core Library 层。如果重新设计，一开始就严格分层。另外会加上 PWA 支持，让离线体验更好。

**Q: 你如何看待单元测试覆盖率？**
> 代码量和 bug 量不成正比，但测试覆盖率和重构信心成正比。我的项目 80% 的门禁其实保证了核心逻辑（解析器、缓存、导出）的可靠性——这些逻辑一旦出 bug 用户能直接感知。UI 层测试覆盖率要求没那么高，因为 UI 变化快。

**Q: 前端性能优化有哪些常用手段？**
> 减少 HTTP 请求（打包合并）、减少重绘重排（虚拟 DOM + 避免强制同步布局）、懒加载（路由级 + 组件级）、缓存策略（内存缓存 + HTTP 缓存 + Service Worker）、首屏/非首屏代码分离等。
