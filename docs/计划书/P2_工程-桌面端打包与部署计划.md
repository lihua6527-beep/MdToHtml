# P2_工程-桌面端打包与部署计划

## 1. 背景与目标
当前项目已完成最小闭环，实现了 Markdown 到 HTML 的转换、编辑、预览及导出功能。为了方便向导师展示初期成果，并为最终交付做准备，需要将现有的 Next.js Web 应用封装为 Windows 桌面应用程序 (`.exe`)。

**目标**：
1.  **零依赖运行**：用户无需安装 Node.js、Git 或 Python 环境，双击 `.exe` 即可运行。
2.  **本地能力集成**：保留并增强本地文件读写能力（如读取本地 Markdown 文件、保存 HTML 到本地）。
3.  **演示便利性**：提供开箱即用的体验，避免繁琐的命令行启动步骤。

## 2. 技术选型与架构

### 2.1 核心框架：Electron
鉴于项目基于 Web 技术栈 (React/Next.js) 且需要深度的本地文件系统访问权限，**Electron** 是最成熟且功能最强大的选择。
- **优势**：
  - 完整的 Chromium 浏览器环境，保证渲染一致性。
  - 强大的 Node.js 主进程，可直接调用系统 API (fs, path, shell)。
  - 丰富的生态系统 (`electron-builder`) 支持生成 Windows 安装包 (NSIS) 和免安装版 (Portable)。
- **劣势**：
  - 打包体积较大 (通常 > 100MB)。
  - 内存占用相对较高。

### 2.2 Next.js 适配方案
由于 Next.js 的 App Router 机制，我们需要选择合适的集成方式：

**方案 A：Next.js 静态导出 (Static Export) + Electron 主进程 API (推荐)**
- **原理**：配置 `output: 'export'`，将 Next.js 编译为纯静态 HTML/CSS/JS 文件，由 Electron 加载。
- **API 处理**：原有的 `/api` 路由无法在静态导出中运行。需要将后端逻辑（文件读写、转换）迁移到 Electron 主进程，通过 **IPC (Inter-Process Communication)** 或 **本地微型 HTTP 服务** 提供。
- **优点**：性能最好，启动快，架构清晰。
- **挑战**：需要修改前端 API 调用逻辑（从 `fetch` 改为 IPC 或本地 localhost 调用）。

**方案 B：Next.js 自定义服务器 (Custom Server) in Electron**
- **原理**：在 Electron 主进程中启动一个完整的 Next.js 生产环境服务器 (`next start`)。
- **优点**：几乎无需修改代码，完全兼容 API 路由和 SSR。
- **缺点**：启动速度慢，资源消耗大，打包配置极其复杂（需处理 `.next` 文件夹的路径和依赖）。

**决策**：
考虑到项目规模和演示需求，采用 **变种方案 A (混合模式)**：
1.  **前端**：使用 `next export` 生成静态资源。
2.  **后端**：在 Electron 主进程中启动一个轻量级 **Express/Koajs** 服务器，托管静态资源并提供 API 接口。
3.  **理由**：这样可以保留大部分 `fetch('/api/...')` 的调用逻辑，只需将 API 路由从 Next.js 迁移到 Express 即可，改动最小且兼容性好。

## 3. 实施计划与步骤

## 3. 实施计划与步骤 (原子化拆分)

### 阶段零：路径与环境适配层 (Phase 0: Path & Env Abstraction) [必须前置]
**背景**：当前代码大量使用 `process.cwd()` 和 `../input` 等相对路径。Electron 打包后，应用运行在 ASAR 归档中且安装目录通常只读，直接沿用原路径会导致运行时错误。
**目标**：解耦业务逻辑与物理文件路径，确保在开发环境和生产环境（Electron）下均能正确读写文件。

- [ ] **任务 0.1：创建环境检测工具**
  - *操作*：创建 `src/lib/platform.ts`。
  - *逻辑*：检测 `process.versions.electron` 判断是否为桌面端环境。
  - *必要性*：后续所有路径决策的基石。
- [ ] **任务 0.2：构建路径管理器 (PathManager)**
  - *操作*：创建 `src/lib/path-manager.ts`。
  - *功能*：
    - `getDataDir()`: 开发环境 -> `../data`; 生产环境 -> `app.getPath('userData')/data`。
    - `getInputDir()`: 开发环境 -> `../input`; 生产环境 -> `app.getPath('documents')/MdToHtml/input` (或用户自定义)。
  - *必要性*：统一管理 I/O 入口，避免硬编码。
- [ ] **任务 0.3：重构现有 API 路径逻辑**
  - *操作*：全局搜索 `fs` 和 `path.join`，替换为 `PathManager` 方法。
  - *范围*：`src/app/api/files`, `src/app/api/save`, `src/lib/posts.ts` 等。
  - *验证*：在 Web 开发模式下运行，确保读写功能未受影响。

### 阶段一：环境初始化 (Phase 1: Environment Setup)
- [ ] **任务 1.1：安装 Electron 核心依赖**
  - *命令*：`npm install --save-dev electron electron-builder`
  - *必要性*：引入桌面端运行时。
- [ ] **任务 1.2：安装并发与工具依赖**
  - *命令*：`npm install --save-dev concurrently wait-on cross-env`
  - *必要性*：用于同时启动 Next.js 前端和 Electron 主进程。
- [ ] **任务 1.3：安装后端服务依赖**
  - *命令*：`npm install express fs-extra get-port`
  - *必要性*：`express` 替代 Next.js API; `fs-extra` 简化文件操作; `get-port` 避免端口冲突。

### 阶段二：Electron 主进程开发 (Phase 2: Main Process Dev)
- [ ] **任务 2.1：搭建主进程脚手架**
  - *操作*：创建 `electron/main.js` 和 `electron/preload.js`。
  - *内容*：基本的窗口创建 (`BrowserWindow`)，加载 `localhost:3000` (Dev) 或 `index.html` (Prod)。
  - *必要性*：Electron 应用的入口。
- [ ] **任务 2.2：集成 Express 微服务**
  - *操作*：在 `electron/server.js` 中创建 Express 实例。
  - *内容*：监听随机端口，提供静态资源托管能力。
  - *必要性*：为静态导出的 Next.js 前端提供 API 支持和静态文件服务。
- [ ] **任务 2.3：实现 IPC 通信桥接**
  - *操作*：在 `preload.js` 中暴露 `window.electronAPI`。
  - *内容*：提供 `getServerPort()` 等基础信息获取方法。
  - *必要性*：前端需要知道后端服务运行在哪个端口。

### 阶段三：API 适配与迁移 (Phase 3: API Migration)
- [ ] **任务 3.1：提取 API 业务逻辑**
  - *操作*：将 `src/app/api/*` 中的逻辑剥离为纯函数（不依赖 `NextRequest/NextResponse`）。
  - *位置*：迁移至 `src/services/*` 或 `electron/services/*`。
  - *必要性*：实现代码复用，Next.js API 和 Express API 共用同一套核心逻辑。
- [ ] **任务 3.2：实现 Express 路由**
  - *操作*：在 `electron/server.js` 中注册对应的 API 接口 (`/api/load`, `/api/save` 等)。
  - *必要性*：在静态导出模式下，原有的 Next.js API 路由将失效，必须由 Express 接管。
- [ ] **任务 3.3：前端 API 调用改造**
  - *操作*：封装 `apiClient`。
  - *逻辑*：开发环境 -> `/api/*`; 生产环境 -> `http://localhost:{port}/api/*`。
  - *必要性*：让前端透明地适配不同的后端地址。

### 阶段四：打包配置与构建 (Phase 4: Build & Package)
- [ ] **任务 4.1：配置 Next.js 静态导出**
  - *操作*：修改 `next.config.js`，设置 `output: 'export'`。
  - *注意*：需处理 `Image` 组件的优化问题 (`unoptimized: true`)。
- [ ] **任务 4.2：配置 Electron Builder**
  - *操作*：在 `package.json` 中添加 `build` 字段。
  - *内容*：指定 `appId`, `directories`, `win` (nsis, portable) 等参数。
- [ ] **任务 4.3：编写构建脚本**
  - *操作*：更新 `scripts` 字段，添加 `build:win`。
  - *流程*：`next build` -> `electron-builder`。

### 阶段五：验证与交付 (Phase 5: Verification)
- [ ] **任务 5.1：冒烟测试 (Smoke Test)**
  - *操作*：启动生成的 `.exe`。
  - *验证点*：窗口是否显示，是否有白屏，控制台有无报错。
- [ ] **任务 5.2：核心流程测试**
  - *操作*：加载文章 -> 编辑 -> 保存 -> 导出。
  - *验证点*：文件是否成功写入到预期的“用户数据目录”或“文档目录”。
- [ ] **任务 5.3：无环境测试**
  - *操作*：在纯净的 Windows 虚拟机中运行。
  - *验证点*：确保不依赖系统安装的 Node.js 或 Python。

## 5. 风险评估与应对
- **风险 1：Next.js 动态路由失效**
  - *应对*：当前项目主要使用 `[slug]` 加载文章，改为通过 URL 参数 (`?file=...`) 或在单页应用中管理状态，避免依赖服务端路由匹配。
- **风险 2：文件路径差异**
  - *应对*：使用 `process.resourcesPath` (生产) 和 `process.cwd()` (开发) 进行路径区分，严禁硬编码绝对路径。
- **风险 3：构建体积过大**
  - *应对*：在 `electron-builder` 配置中排除 `node_modules` 中不必要的开发依赖，仅打包生产依赖。
