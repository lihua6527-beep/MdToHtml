# 元数据缓存与性能分析方案 (Metadata Caching & Performance Plan)

> **目标**: 引入缓存机制提升文档列表加载速度，并分析对性能的正负面影响。
> **状态**: 规划中 (Planning)
> **优先级**: 中 (Medium)

## 1. 需求分析
- **痛点**: 当前每次加载主页时，后端都会遍历所有 Markdown 文件并读取 Frontmatter。随着文件数量增加（如达到 100+），I/O 开销将显著拖慢加载速度。
- **需求**:
  1.  **缓存**: 存储文档元数据（`status`, `mtime`, `title`, `tags`）以避免每次全量解析。
  2.  **性能优化**: 利用缓存进行快速排序和渲染。
  3.  **即时性**: 确保缓存与文件系统状态一致（Watch 机制或按需校验）。

## 2. 技术方案

### 2.1 缓存设计 (`.metadata_cache.json`)
在项目根目录下维护 `.metadata_cache.json`：
```json
{
  "lastUpdated": 1677654321000,
  "files": {
    "my-post.md": {
      "mtime": 1677654321000,
      "status": "completed",
      "title": "我的文档",
      "tags": ["React", "Next.js"]
    },
    "draft.md": {
      "mtime": 1677650000000,
      "status": "incomplete",
      "title": "草稿",
      "tags": []
    }
  }
}
```

### 2.2 缓存逻辑 (Cache Strategy)
- **读取策略**:
  1.  前端请求列表 -> 后端读取 `.metadata_cache.json`。
  2.  后端快速扫描文件系统 (`fs.readdir` + `fs.stat`) 获取当前文件列表及修改时间。
  3.  **增量更新**:
      - **新增**: 文件在磁盘存在但不在缓存 -> 解析 Frontmatter 并写入缓存。
      - **修改**: 文件 `mtime` > 缓存 `mtime` -> 重新解析 Frontmatter 并更新缓存。
      - **删除**: 文件在缓存存在但不在磁盘 -> 从缓存移除。
  4.  返回更新后的元数据列表。
  5.  异步将更新后的缓存写回磁盘（Debounce 写入，避免频繁 I/O）。

### 2.3 性能分析 (Performance Analysis)
- **正向收益**:
  - **加载速度**: 解析 Frontmatter 是 CPU 密集型操作。缓存后，仅需 `fs.stat` (轻量) 即可，首屏加载时间预计降低 90% (对于大量文件)。
  - **排序效率**: 预计算的 `mtime` 和 `status` 可直接用于排序，无需实时读取。
- **负向开销**:
  - **初次构建**: 首次启动需遍历所有文件建立缓存，耗时较长（一次性）。
  - **一致性维护**: 需要处理缓存失效逻辑，增加了代码复杂度。
  - **磁盘空间**: 极小（文本元数据占用忽略不计）。
- **结论**: 对于 Markdown 这种以读多写少、文件数量可能较多的场景，引入缓存是**绝对正向**的优化。

## 3. 实施步骤
1.  **后端库**: 创建 `lib/metadata-cache.ts`，封装读取、写入、更新逻辑。
2.  **API 集成**: 修改 `/api/files` (或 `/api/posts`) 接口，接入缓存层。
3.  **交互优化**: 在缓存构建期间（如初次启动）提供进度提示。

## 4. 注意事项
- **并发写入**: 需使用文件锁或队列机制防止多进程同时写入缓存文件损坏。
- **容错**: 缓存文件损坏时应自动删除并重建，不应阻塞应用启动。
