# 大数据量文档列表扩展方案 (Large-Scale Document List Expansion Plan)

> **目标**: 基于“Top 20 极速启动”架构，扩展文档列表以支持**用户自定义容量**（默认 500）的活跃文档访问与管理，并提供容量监控与超限清理功能。
> **原则**: **严格限制容量**，仅维护最近访问的 Top N 文档，超限文档自动移入系统回收站。
> **状态**: 规划中 (Planning)
> **优先级**: 高 (High)

---

## 1. 需求分析与约束 (Constraints)

- **核心变更**:
    -   **动态容量上限**: 系统限制文档列表仅展示 **最近访问的 N 个文档**（N 由用户在设置中配置，默认 500）。
    -   **回收站机制**: 对于目录下超过 N 的文件（按时间排序靠后的），**自动移入 `.trash` 回收站目录**。
    -   **性能隔离**: 回收站内的文件系统完全忽略，不予扫描、不予缓存、不予解析。

- **功能需求**:
    1.  **Top N 访问**: 在“查看全部文档”列表中，仅加载并渲染前 N 个文档。
    2.  **容量显示**: 实时显示当前文档数量与上限（例如 `32/100` 或 `501/500`）。
    3.  **超限自动清理**: 当文档数 > N 时，后台自动将多余的最旧文档移入回收站。
    4.  **回收站管理**: 提供查看回收站大小和一键清空的功能。

    -   仅展示 Top N 文档。

## 3. 技术实现方案 (Technical Implementation)

### 3.1 数据加载与过滤策略
- **API `/api/files/all`**:
    -   **扫描**: 扫描活跃目录（排除 `.trash`），获取 `files` 并按 `mtime` 倒序。
    -   **自动清理 (Auto-Cleanup Check)**:
        -   读取配置 `limit`。
        -   若 `files.length > limit`:
            -   触发后台任务：将 `files.slice(limit)` 移入 `.trash`。
            -   返回截断后的 `files.slice(0, limit)` 给前端。
    -   **解析**: 仅对返回的 Top N 进行 Frontmatter 解析和缓存更新。

### 3.2 缓存策略调整
- **`.metadata_cache.json`**:
    -   `recentFiles`: 依然维持 Top 20（用于首页极速启动）。
    -   `allFilesCache`: 维持 Top N 的元数据缓存。
    -   **一致性**: 当文件被移入回收站后，立即从缓存中移除对应条目。

### 3.3 性能优势
-   **零干扰**: 回收站内的文件（即使有 10000 个）完全不参与系统扫描，对启动速度和列表加载速度 **零影响**。
-   **内存稳定**: 无论用户存了多少旧文档，内存中始终只维护 <= N 个活跃文档对象。

## 4. 可行性分析 (Feasibility Analysis)

-   **技术路线**: **可行且安全**。
    -   使用 `fs.rename` 实现瞬间归档。
    -   通过文件路径排除（Glob Ignore Pattern）实现性能隔离。
-   **原子化拆分**:
    1.  **设置模块**: 实现 `limit` 配置的持久化。
    2.  **清理逻辑**: 实现 `move_to_trash` 函数（含重名处理）。
    3.  **后端扫描**: 集成“扫描 -> 检查 -> 清理 -> 返回”的流水线。

---

## 5. 风险与对策

-   **误删风险**: 移入回收站而非直接删除，用户可随时手动还原。
-   **扫描死循环**: 确保扫描器配置 `ignore: ['**/.trash/**']`，防止重复扫描回收站文件。
