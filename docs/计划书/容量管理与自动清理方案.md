# 容量管理与自动清理方案 (Capacity Management & Auto-Cleanup Plan)

> **目标**: 在“系统设置”中提供直观的容量管理面板，允许用户**自定义**自动清理阈值（如 20/100/500），并引入**回收站 (Trash)** 机制作为中间缓冲区，确保数据安全与性能平衡。
> **状态**: 规划中 (Planning)
> **优先级**: 中 (Medium) - 配合扩展方案实施

---

## 1. 需求分析与核心变更

- **背景**: 用户需要灵活控制“活跃文档”的数量，避免长期积累导致的清理困难。硬性限制 500 可能不适合所有用户（如轻量用户可能希望超过 20 个就清理）。
- **核心变更**:
    1.  **用户自定义阈值**: 允许用户在设置中指定“容量上限”（如 20, 50, 100, 500）。
    2.  **强制回收站机制**: 所有“清理”操作（无论是自动还是手动）**默认行为必须是移入回收站**，严禁直接物理删除。
    3.  **回收站管理**: 系统不再关注回收站内文件的内容与状态，仅统计其数量/大小，并提供“一键清空”功能。

## 2. 交互设计 (Interaction Design)

## 3. 技术路线分析：移入回收站 vs 直接删除

### 3.1 方案对比

| 维度 | 方案 A: 直接删除 (Direct Delete) | 方案 B: 移入回收站 (Move to Trash) |
| :--- | :--- | :--- |
| **安全性** | **低**。误删无法找回，用户心理负担大，可能导致用户不敢开启自动清理。 | **高**。提供“后悔药”，用户可随时从 `.trash` 目录找回误删文件。 |
| **性能** | **高**。文件系统 `unlink` 操作极快，释放磁盘空间。 | **中**。`rename` 操作极快，但文件仍占磁盘空间（直到清空回收站）。 |
| **复杂度** | **低**。只需调用 API 删除。 | **中**。需维护 `.trash` 目录，处理重名冲突（如 `a.md` 被移入后，新 `a.md` 又被移入）。 |
| **系统干扰** | **无**。 | **低**。需确保文件扫描器 (`glob`) 显式排除 `.trash` 目录。 |

### 3.2 结论：选择方案 B (移入回收站)
-   **必要性**: 对于个人知识库，**数据安全是第一位的**。自动化的“直接删除”极易引发灾难性后果（如时间戳错误导致误删重要文档）。
-   **可行性**:
    -   **隔离**: 创建项目根目录下的 `.trash` 文件夹（或 `_trash`），并配置系统扫描器忽略该目录。
    -   **零干扰**: 系统对 `.trash` 内的文件**不解析、不缓存、不展示**，因此回收站内文件数量（即使有 10000 个）不会影响启动性能和列表加载速度。
    -   **实现**: Node.js 的 `fs.rename` 操作是原子且极快的，不会阻塞 UI。

## 4. 技术实现 (Technical Implementation)

### 4.1 自动清理逻辑 (Auto-Cleanup Logic)
-   **触发**: 应用启动后 / 设置变更时 / 文档列表加载时。
-   **流程**:
    1.  读取用户配置的 `limit` (如 100)。
    2.  扫描活跃目录，获取 `files` 并按 `mtime` 倒序。
    3.  若 `files.length > limit`:
        -   截取 `excess_files = files.slice(limit)`。
        -   **执行移动**:
            -   目标路径: `.trash/{filename}_{timestamp}.md` (添加时间戳防重名)。
            -   更新 `metadata_cache.json` 移除对应条目。
    4.  UI 通知: *"已将 X 个旧文档移入回收站"*。

### 4.2 回收站接口
-   `POST /api/trash/empty`: 清空回收站（`rm -rf .trash/*`）。
-   `GET /api/trash/stats`: 返回回收站文件数和总大小。

---

## 5. 风险控制

-   **重名冲突**: 必须处理同名文件。
    -   *对策*: 移入回收站时，文件名追加时间戳后缀，如 `my-doc.md` -> `my-doc_1677654321.md`。
-   **扫描泄露**: 防止扫描器意外扫描到回收站。
    -   *对策*: 在 `fast-glob` 或 `fs.readdir` 中显式添加 `ignore: ['**/.trash/**']`。
