## 一、执行摘要 (Executive Summary)

### 1.1 当前痛点

本系统目前实现了从 **CHD 格式 Markdown → HTML 静态网页** 的渲染管线，但输入端存在**严重割裂**：

```
用户需求：
  输入任意文档 → AI 自动识别 → 生成 CHD Markdown → 渲染 HTML
                    ↑
现有系统（断裂处）：
  需要手动编写 CHD 格式 Markdown → 渲染 HTML
```

用户需要手动理解 CHD 协议规范 → 手动将原始文本转化为符合三级刚性结构的 Markdown → 才能进入渲染流程。这导致：
- **学习成本高**：需要掌握 CHD 协议的完整规范
- **效率低下**：长篇文档的手工转换耗时巨大
- **质量不稳定**：人工转换容易遗漏属性或格式错误

### 1.2 目标

为系统新增 **AI 智能转换层**，实现以下完整闭环：

```
用户输入（任意文本/文档/URL）
    ↓
AI 服务层（调用大语言模型）
    ↓  生成符合 CHD 协议 v2.1 的 Markdown
CHDRenderer 核心渲染引擎
    ↓
HTML 静态网页输出
```

### 1.3 架构定位

| 方向 | 未来架构 |
|------|----------|
| **输入层** | 人工编写 + AI 自动生成（双模式并行） |
| **处理层** | 本地 CHD 渲染管线 + 云端/本地 AI 推理 |
| **输出层** | 实时预览渲染 + 静态 HTML 导出 |

```typescript

  // 构建完整 Prompt（系统指令 + 用户文本 + 示例）
```

**Prompt 结构设计**：
```

  - 智能列数规则
  - 富文本规范（LaTeX 公式、GFM 表格）
  - 常见错误自检清单

Few-Shot Examples:
  - 1 个项目文档示例
  - 1 个论文摘要示例
  - 1 个技术架构示例

User Input:
  - 用户提供的原始文本
```

#### S3. ResponseValidator — AI 返回校验器

| 项目 | 说明 |
|------|------|
| 文件 | `src/services/ai/ResponseValidator.ts` |
| 导出 | `class ResponseValidator` |

**核心方法**：
```typescript
class ResponseValidator {
  // 校验 AI 返回是否符合 CHD 协议
  static validate(markdown: string): ValidationResult;

  // 自动修复常见格式错误
  static autoFix(markdown: string): string;

  // 提取错误列表
  static getErrors(result: ValidationResult): ValidationError[];
}
```

**校验规则**：
| 检查项 | 规则 | 严重级别 |
|--------|------|----------|
| L0 Frontmatter | 必须包含 title, subtitle, tags | error |
| L0 Frontmatter 格式 | YAML 语法有效 | error |
| L1 Section | 必须使用 `##`，不能有孤儿文本 | error |
| L1 布局属性 | 必须包含 `layout="grid"` | warning |
| L2 Card | 必须使用 `###`，不能有 `####` | error |
| Card 样式 | 仅允许 normal/highlight/quote | warning |
| LaTeX 公式 | 必须使用 `$`，不能使用代码块包裹 | error |
| 表格 | 必须使用 GFM 语法，禁止 HTML table | warning |
| 图标名称 | 必须存在于图标资产库 | info |
| 列数规则 | 1-4→N列, 5+→3列 | warning |

| 项目 | 说明 |

| 文件 | `src/services/ai/ModelConfig.ts` |

```typescript
// AI 提供商
type AIProvider = 'openai' | 'ollama' | 'custom';

// AI 配置
interface AIConfig {
  provider: AIProvider;
  apiEndpoint: string;
  apiKey: string;
  model: string;
  temperature: number;
  maxTokens: number;
  timeout: number;
  streamOutput: boolean;
  defaultMode: OutputMode;
}

// 输出模式
type OutputMode = 'direct' | 'editor';

// AI 生成结果
interface AIResult {
  markdown: string;           // 生成的 CHD Markdown
  rawResponse: string;        // API 原始返回
  usage?: {
    promptTokens: number;
    completionTokens: number;
    totalTokens: number;
  };
  validation?: ValidationResult;  // 校验结果
  error?: string;             // 错误信息
}

// 校验结果
interface ValidationResult {
  isValid: boolean;
  errors: ValidationError[];
  warnings: ValidationWarning[];
  autoFixApplied: boolean;
  fixedMarkdown?: string;
}

// 默认配置
const DEFAULT_AI_CONFIG: AIConfig = {
  provider: 'openai',
  apiEndpoint: 'https://api.openai.com/v1',
  apiKey: '',
  model: 'gpt-4o',
  temperature: 0.3,
  maxTokens: 4096,
  timeout: 60000,
  streamOutput: true,
  defaultMode: 'direct'
```

## 四、重点难点分析 (Key Challenges)

### 难度评级：★★★★☆

| # | 难点 | 详细描述 | 风险等级 | 解决方案 |
|---|------|----------|----------|----------|
| **1** | **LLM API 多提供商兼容** | 需要支持 OpenAI、Ollama、DeepSeek、自定义端点等多套 API 规范，各自有不同的认证方式和请求格式 | **高** | 统一使用 OpenAI 兼容接口格式（Ollama 和 DeepSeek 均支持）；封装 `HttpClient` 模块处理差异 |
| **2** | **CHD 协议 Prompt 工程** | 需要精确的 Prompt 设计确保 AI 生成的 Markdown 严格符合 CHD 三级结构，避免幻觉和格式错误 | **高** | 在 CHD协议.md 第 3 节已有成熟的 System Prompt，在此基础上封装为可复用模板；加入更多负面示例（不该怎么做） |
| **3** | **AI 返回结果校验与修复** | LLM 可能返回格式错误的 Markdown（缺失 Frontmatter、错误嵌套、越级标题等），直接渲染会崩溃 | **高** | 实现校验器自动检测 10+ 种常见错误；实现自动修复逻辑；提供降级方案（用户手动修正） |
| **4** | **流式输出 (SSE) 实现** | 长文本生成需要流式输出提升体验，但 Next.js App Router 下 SSE 实现需要特殊处理 | **中** | 使用 Next.js Route Handler 的流式响应；前端使用 `ReadableStream` 逐块解析 |
| **5** | **配置安全存储** | API Key 需要安全存储，不能明文暴露 | **中** | 前端使用 localStorage 加密存储；生产环境建议通过后端环境变量代理调用 |
| **6** | **长文档处理** | 超过模型上下文窗口的文档需要分块处理 | **中** | 实现文本分块策略（按段落/章节切分）；逐块生成后合并 |
| **7** | **错误处理完整闭环** | 网络异常、API 超时、格式错误、Token 超限等需要优雅处理 | **低** | 全局错误边界 + 重试机制（最多 3 次）+ 友好的用户提示 |

## 八、与现有系统的集成策略

### 8.1 页面路由集成

在现有导航中加入 AI 入口：

```
首页 (/)             → 现有
├── 编辑器 (/editor)  → 现有
├── AI 转换 (/ai-input)  → 新增
└── 设置 (/ai-input/settings)  → 新增
```

### 8.2 数据流集成点

| 集成点 | 方式 | 说明 |
|--------|------|------|
| AI → CHDRenderer | direct prop 传递 | 在 AI 页面内直接使用 CHDRenderer 渲染 |
| AI → CodeMirror | localStorage + URL param | 跳转编辑器时携带生成内容 |
| AI → HtmlBundler | 复用现有导出模块 | 渲染后调用 HtmlBundler.bundle() |
| AI → FileService | 复用现有保存 | 保存 AI 生成的 Markdown 到 posts/ |

### 8.3 向后兼容

- 所有新增代码在 `src/services/ai/` 和 `src/components/AI/` 新目录中
- 不修改现有业务逻辑
- 仅对 CHDRenderer 做最小化扩展（增加 `source` prop）
- 用户可自由选择手工编辑或 AI 生成

## 九、风险与缓解措施

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| LLM 生成格式不稳定 | 高 | 中 | ResponseValidator 自动修复 + 用户手动修正 |
| API 服务不可用（网络/限流） | 中 | 高 | 本地 Ollama 备选 + 重试机制 + 缓存 |
| API Key 泄露 | 低 | 高 | 前端加密存储 + 生产环境后端代理 |
| 长文本 Token 超限 | 中 | 中 | 分块处理 + 模型选择建议 + 错误提示 |
| 用户对生成质量不满意 | 高 | 低 | 提供重新生成 + 编辑器微调双模式 |

## 十、验收标准 (Acceptance Criteria)

完成此计划后，应满足以下验收条件：

1. ✅ 用户可在 `/ai-input` 页面输入任意文本（至少 5000 字）

8. ✅ API 配置可管理（提供商、Model、Key、参数）
9. ✅ 导出 HTML 功能正常
10. ✅ 所有新增功能不影响现有编辑-渲染管线
