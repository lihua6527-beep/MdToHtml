# Plan 04: AI 上下文与成本控制策略

> **计划日期**：2026-07-12（第二次修订，简化版）
> **计划目标**：明确 AI 操作时应该传入什么样的上下文，以及如何控制 Token 消耗。不写死代码实现，只定策略原则。
> **前置依赖**：计划01（操作类型系统）
> **对应总体计划**：Phase 3（叠加 AI 操作支持）

---

## 一、核心问题

AI 辅助编辑需要传入上下文。但：

```
传少了 → AI 缺乏上下文信息，容易"胡编乱造"
传多了 → Token 消耗大，成本高，且响应慢

平衡点在哪里？
```

### 类比理解

> 这就像你给一个实习生布置任务：
> - 只告诉他当前这一段 → 他可能写跑偏（因为你没给项目背景）
> - 把整个项目文档都甩给他 → 他读半天才开始干活（成本高，效率低）
>
> 最佳做法是：**给他当前任务相关的上下文，不多不少**。

## 二、策略：按操作类型选择上下文量

### 2.1 三种上下文层级

| 层级 | 内容范围 | 估算 Token | 适用操作 |
|------|---------|-----------|---------|
| **轻量** | 选中文本 + 前后各 200 字 + 所在 Section 标题 | ~200-400 | 润色、总结 |
| **中等** | 当前 Section 全文 + 相邻 Section 的标题+首句 | ~800-1500 | 扩充、转卡片 |
| **完整** | 整篇文章 + 元信息 | ~2000-5000 | 较少使用，仅在必要时 |

### 2.2 层级选择规则

```
润色 (AI_POLISH)     → 轻量级  （只改表达，不需要太多上下文）
总结 (AI_SUMMARIZE)  → 轻量级  （总结片段，不需要全文）
扩充 (AI_EXPAND)     → 中等级  （需要当前 Section 的完整内容来保持连贯）
转卡片 (AI_TO_CARD)  → 中等级  （需要理解段落之间的结构关系）
```

**一句话原则**：只看当前工位需要什么，不需要看整层楼的图纸。

### 2.3 上下文结构模板

传入 AI 的 prompt 使用固定格式：

```
[文档上下文]
(这里放按照规则筛选出来的上下文内容)

========== 操作焦点 ==========
请对以下文本执行「XXXX」操作：
(这里放用户选中的文本)
============================
```

这样 AI 知道"哪些是你需要看的背景信息，哪些是你要动手改的内容"。

## 三、缓存：节省重复请求的成本

### 3.1 三种缓存场景

| 场景 | 做法 | 省了多少 |
|------|------|---------|
| **用户对同一段文字再次求同一种操作** | 存完整 prompt → 完全命中 | 省 100% Token |
| **用户改了少量文字后再次求同一操作** | 存"操作类型+文本前100字"模糊匹配 | 省约 80% Token |
| **用户尝试不同风格（连续请求）** | 当前会话内的缓存 | 省约 50% Token |

### 3.2 缓存清理时机

- 切换到另一篇文章 → 清空所有缓存
- 缓存太久（超过10分钟）→ 自动过期
- 用户主动刷新 → 清空

> **注意**：缓存是锦上添花，不是必需功能。可以在第一个版本不做缓存，后面再补。

## 四、流式输出：用户低成本终止

### 4.1 代价最低的终止方式

```
普通模式：用户点"润色" → 等AI返回全量结果 → 用户看 → 不满意 → 重来
          全程不管满不满意，都得等完。

流式模式：用户点"润色" → AI逐字输出 → 用户看了前几句就觉得不对 → 点击"停止"
          只花了全部 Token 的 10%-20% 就放弃了。
```

流式输出的核心价值不是"加速"，而是**给了用户一个低成本的终止点**。

### 4.2 如何识别"该停了"

```
用户看到输出前半部分就已经知道 AI 写偏了：
  原文："该算法的时间复杂度为 O(n²)"
  AI开头的输出："综上所述，这个算法效率很高..."
  → 用户一看就知道 AI 没理解，可以立刻喊停
```

## 五、成本追踪（简单做法）

### 5.1 需要记录什么

每个 AI 操作执行后，记录：

```
操作类型: AI_POLISH / AI_EXPAND / ...
模型: flash / deepseek
消耗 Token: 356
上下文层级: 轻量 / 中等 / 完整
```

这些信息存在 `Operation` 的 `aiContext` 字段里（计划01已定义）。

### 5.2 成本追踪的三种用途

| 用途 | 怎么做 |
|------|--------|
| **用户看得到** | 每次 AI 操作后，在 UI 角落显示"消耗 xx tokens"（可选） |
| **开发者统计** | 导出所有 AI 操作的 Token 消耗，看平均每次多少钱 |
| **优化依据** | 如果发现某个操作的 Token 消耗异常高，检查上下文层级设置是否合理 |

### 5.3 成本估计（参考）

```
假设 DeepSeek 价格：¥0.5 / 1M tokens

每次 AI 操作：
  轻量级 ~300 tokens → 约 ¥0.00015（几乎免费）
  中等级 ~1200 tokens → 约 ¥0.0006
  完整级 ~3500 tokens → 约 ¥0.00175

用户一天操作 100 次 AI 编辑（很多了），
  全部是中等层级 → 约 ¥0.06 / 天
```

**结论**：对于个人编辑器场景，AI 成本几乎可以忽略。更重要的是**响应速度**——中等上下文比完整上下文快 2-3 倍。所以优先用轻量+中等级，只在必要时用完整级。

## 六、实现建议

### 6.1 最简单的实现

```javascript
// 不写单独的文件，直接在 AI 调用前做这件事：

function buildContext(document, selectedText, operationType) {
  const levelMap = {
    AI_POLISH: 'light',
    AI_SUMMARIZE: 'light',
    AI_EXPAND: 'medium',
    AI_TO_CARD: 'medium',
  };
  const level = levelMap[operationType] || 'medium';

  // 轻量级：截取选中的前中后
  if (level === 'light') {
    const start = Math.max(0, selectionStart - 200);
    const end = Math.min(doc.length, selectionEnd + 200);
    return doc.slice(start, end);
  }

  // 中等级：找当前 Section
  if (level === 'medium') {
    return findCurrentSection(doc, selectionStart);
  }

  // 完整级：全文
  return doc;
}
```

### 6.2 后续优化路径

```
V1：直接用简单函数判断（上面这段代码就够了）
V2：提取为独立的 ContextBuilder（方便测试和维护）
V3：加入缓存（如果发现重复请求多）
V4：加入流式输出（如果用户经常等得不耐烦就放弃）
```

## 七、验收标准

- [ ] AI 操作根据类型自动选择上下文层级（润色/总结用少量上下文，扩充/转卡片用中等量）
- [ ] 上下文结构清晰区分"背景信息"和"操作焦点"
- [ ] 不传入不必要的大段上下文（避免 Token 浪费）
- [ ] (可选) 缓存机制减少重复请求
- [ ] (可选) 流式输出给用户低成本的终止选择
- [ ] Token 消耗记录在 Operation 中，可查询
