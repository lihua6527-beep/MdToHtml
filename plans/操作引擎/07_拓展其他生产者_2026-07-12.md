## 一、设计背景

### 1.1 当前状态

操作引擎第一阶段覆盖了手动编辑和 AI 操作两大生产者。但编辑器中还有更多"变更源"未被接入：

```
接入完毕：         待接入（本计划）：
┌─────────────┐   ┌─────────────┐
│ 手动编辑     │   │ 卡片属性变更 │
│ (CodeMirror) │   │ (样式修改)   │
├─────────────┤   ├─────────────┤
│ AI 内联编辑  │   │ 拖拽排序     │
│ (润色/扩充)  │   │ (卡片移动)   │
└─────────────┘   ├─────────────┤
                   │ 批注/评论    │
                   └─────────────┘
```

### 1.2 核心原则

```
扩展新生产者时，必须遵循：
1. 不修改撤销引擎核心代码（计划02）
2. 不修改 Operation 接口定义（计划01）
3. 只新增：
   - 新的 OperationType 枚举值（如果现有类型不够用）
   - 对应生产者代码
   - 对应的逆操作逻辑（可选特化）
```

## 二、生产者接入规范

### 2.1 标准接入流程

任何新的操作生产者接入操作引擎需要以下步骤：

```typescript
// 标准接入流程（伪代码）
class OperationProducer {
  // Step 1: 创建 Operation（使用 OperationBuilder）
  const op = OperationBuilder.someOperation(...);

  // Step 2: 验证 Operation 合法性
  const { valid, errors } = validateOperation(op);
  if (!valid) throw new Error(`非法操作: ${errors.join(', ')}`);

  // Step 3: 推入撤销引擎
  pushOperation(op);

  // Step 4: 应用变更到编辑器
  applyToEditor(op);
}
```

### 2.2 接入检查清单

| 检查项 | 说明 |
|--------|------|
| ✅ 类型选择 | 选择合适的 OperationType，必要时新增枚举值 |
| ✅ 位置编码 | 正确填充 position.start / end |
| ✅ 前后内容 | payload.before 为变更前内容，after 为变更后内容 |
| ✅ 展示信息 | display.icon / label / detail 对用户有描述价值 |
| ✅ 逆操作验证 | invert() 在逻辑上正确 |
| ✅ 持久化兼容 | Operation 可被 JSON.stringify 序列化 |
| ✅ 后端兼容 | 不会破坏现有 useHistory 接口 |

## 三、卡片属性变更（P1 优先级）

### 3.1 使用场景

用户通过卡片属性面板修改卡片的 `card-style`（如从 normal 改为 highlight）：

```
卡片属性面板
  │
  ├── 卡片样式: [normal] → [highlight]
  ├── 卡片标题: 可编辑
  ├── 卡片标签: 可编辑
  └── 确认修改 → 生成 Operation
```

### 3.2 操作类型

```typescript
// 已有类型 CARD_STYLE_CHANGE 可直接使用
enum OperationType {
  // ...
  CARD_STYLE_CHANGE, // 修改卡片样式（highlight/normal）
  // ...
}
```

### 3.3 操作创建

```typescript
function createCardStyleChangeOp(
  cardId: string,
  oldStyle: string,
  newStyle: string,
  cardContent: string
): Operation {
  return {
    id: OperationBuilder.nextId(),
    type: OperationType.CARD_STYLE_CHANGE,
    timestamp: Date.now(),
    position: {
      start: 0,  // 卡片在文档中的字符偏移（由调用方填充）
      end: cardContent.length,
    },
    payload: {
      before: `### Card {card-style="${oldStyle}"}\n${cardContent}`,
      after: `### Card {card-style="${newStyle}"}\n${cardContent}`,
    },
    display: {
      icon: '🎨',
      label: `卡片样式: ${oldStyle} → ${newStyle}`,
      detail: `卡片 ID: ${cardId}`,
    },
  };
}
```

### 3.4 接入点

在卡片属性面板的"确认修改"事件中：

```typescript
// CardPropertyPanel.tsx
function handleStyleChange(newStyle: string) {
  const op = createCardStyleChangeOp(
    currentCard.id,
    currentCard.style,
    newStyle,
    currentCard.content
  );
  pushOperation(op);
  // 应用样式变更
  updateCardStyle(currentCard.id, newStyle);
}
```

## 四、拖拽排序（P2 优先级）

### 4.1 使用场景

用户在编辑器中拖拽卡片，改变其在文档中的顺序：

```
拖拽前：                     拖拽后：
┌─────────────────────┐   ┌─────────────────────┐
│ ### Card A           │   │ ### Card B           │
├─────────────────────┤   ├─────────────────────┤
│ ### Card B           │   │ ### Card C           │
├─────────────────────┤   ├─────────────────────┤
│ ### Card C           │   │ ### Card A (移动到此)│
└─────────────────────┘   └─────────────────────┘
```

### 4.2 操作类型

```typescript
// 已有类型 CARD_MOVE 可直接使用
enum OperationType {
  // ...
  CARD_MOVE, // 移动卡片位置
  // ...
}
```

### 4.3 操作创建

```typescript
function createCardMoveOp(
  cardId: string,
  cardContent: string,
  fromPosition: number,  // 原位置的字符偏移
  toPosition: number     // 目标位置的字符偏移
): Operation {
  return {
    id: OperationBuilder.nextId(),
    type: OperationType.CARD_MOVE,
    timestamp: Date.now(),
    position: {
      start: Math.min(fromPosition, toPosition),
      end: Math.max(fromPosition, toPosition) + cardContent.length,
    },
    payload: {
      before: `[位置 ${fromPosition}] → [位置 ${toPosition}]`,  // 位置描述
      after: `[位置 ${toPosition}] ← [来自 ${fromPosition}]`,
    },
    display: {
      icon: '🔄',
      label: `移动卡片`,
      detail: `卡片从 ${fromPosition} 移至 ${toPosition}`,
    },
  };
}
```

### 4.4 逆操作特化

```typescript
// CARD_MOVE 的逆操作：反方向移动
function invertCardMove(op: Operation): Operation {
  // 提取原位置和目标位置
  const matchBefore = op.payload.before.match(/位置 (\d+)/);
  const matchAfter = op.payload.after.match(/位置 (\d+)/);
  
  if (!matchBefore || !matchAfter) {
    // 降级：使用通用 invert
    return OperationFactory.invert(op);
  }

  const originalPos = parseInt(matchBefore[1]);
  const targetPos = parseInt(matchAfter[1]);

  return {
    ...op,
    payload: {
      before: op.payload.after,
      after: op.payload.before,
    },
    display: {
      icon: '↩️',
      label: `撤销: 移动卡片`,
      detail: `卡片从位置 ${targetPos} 移回 ${originalPos}`,
    },
  };
}
```

## 五、批注/评论（P3 优先级）

### 5.1 使用场景

用户在文档中添加/删除/回复批注：

```
文档内容：
==========
### 标题
正文文本 [批注: 这里需要补充引用] ← 行内批注
                                    
右侧面板：                   ← 侧边批注
┌─ 批注 ──────────────┐
│  ↗ 这里需要补充引用   │
│  回复：已添加         │
└─────────────────────┘
```

### 5.2 操作类型

```typescript
// 需要新增的枚举值
enum OperationType {
  // ... 现有类型 ...

  // --- 批注操作（未来） ---
  NOTE_ADD,      // 添加批注
  NOTE_DELETE,   // 删除批注
  NOTE_REPLY,    // 回复批注
  NOTE_RESOLVE,  // 解决批注
}
```

### 5.3 操作定义

```typescript
interface NotePayload {
  noteId: string;           // 批注唯一 ID
  type: 'inline' | 'sidebar'; // 批注类型
  content: string;          // 批注内容
  replyTo?: string;         // 回复的批注 ID
  resolved?: boolean;       // 是否已解决
}

function createNoteAddOp(
  noteId: string,
  noteType: 'inline' | 'sidebar',
  content: string,
  position: number
): Operation {
  return {
    id: OperationBuilder.nextId(),
    type: OperationType.NOTE_ADD,
    timestamp: Date.now(),
    position: { start: position, end: position },
    payload: {
      before: '',
      after: JSON.stringify({
        noteId,
        type: noteType,
        content,
      } satisfies NotePayload),
    },
    display: {
      icon: '💬',
      label: `添加批注`,
      detail: content.slice(0, 50),
    },
  };
}
```

### 5.4 NOTE_ADD 逆操作（= NOTE_DELETE）

```typescript
function invertNoteOp(op: Operation): Operation {
  if (op.type === OperationType.NOTE_ADD) {
    return {
      ...op,
      type: OperationType.NOTE_DELETE,
      payload: { before: op.payload.after, after: '' },
      display: { icon: '↩️', label: '撤销: 删除批注' },
    };
  }
  if (op.type === OperationType.NOTE_DELETE) {
    return {
      ...op,
      type: OperationType.NOTE_ADD,
      payload: { before: '', after: op.payload.before },
      display: { icon: '↩️', label: '撤销: 恢复批注' },
    };
  }
  return OperationFactory.invert(op);
}
```

## 六、可扩展性验证

### 6.1 扩展场景测试

| 测试场景 | 需要修改什么 | 不需要修改什么 |
|---------|-------------|--------------|
| 新增 CARD_STYLE_CHANGE 生产者 | 卡片属性面板代码 | 撤销引擎核心、Operation 接口、useHistory 接口 |
| 新增 CARD_MOVE 生产者 | 拖拽排序代码、CARD_MOVE 逆操作特化 | 撤销引擎核心、持久化逻辑 |
| 新增 NOTE_ADD/DELETE 生产者 | 新增枚举值、批注面板代码、NOTE 逆操作逻辑 | 撤销引擎核心、防抖合并器 |
| 新增任意操作 | 生产者代码 + 必要特化逻辑 | 无需修改撤销引擎核心 |

### 6.2 验证结论

> 操作引擎的**稳定性与可扩展性边界**：
> - ✅ 撤销引擎核心（Plan02）完全不需要为新增生产者而修改
> - ✅ 防抖合并器（Plan03）完全不需要修改
> - ✅ 持久化层（Plan03）完全不需要修改
> - ✅ 操作日志面板（Plan06）在新操作类型出现时，通过 icon + label 自动适配展示
> - ⚠️ 仅当新增的枚举值有独特的逆操作逻辑时（如 NOTE_ADD↔NOTE_DELETE 互逆），才需要在 `invert()` 中添加特化分支
