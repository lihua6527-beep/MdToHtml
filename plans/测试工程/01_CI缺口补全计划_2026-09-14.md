## 二、P6 — 运维闭环（remote + push 验收 + 发布自动化）

**目标**：让 GitHub Actions 真实运行并全绿，且一次打 tag 能自动产出便携版 exe。

### 6.0 远端现状与平台适配（2026-09-14 实测，重要）

已为本地仓库配置远端：`origin = https://gitee.com/njustzjh/md-to-html.git`（凭据可用，`git fetch origin --prune` 成功拉取全部分支）。

| 发现 | 说明 |
|------|------|
| **平台不匹配（阻塞项）** | 远端是 **Gitee**，而 `.github/workflows/*.yml` 是 **GitHub Actions** —— 在 Gitee 上**永远不会执行**。仅"配置 remote + push"并不能让 CI 变绿 |
| **分支分叉 2 / 2** | 远端 `feat/exe-package-ready` 有 2 个本地没有的提交（`d249e43` 07-26 工作区快照、`01bc1ce` README 克隆说明）；本地有 2 个远端没有的提交（`a0db033`、`424be17`，含全部 09-14 测试与门禁修复）。直接 push 会被拒（非快进），**禁止 force push** |
| **远端快照落后** | `git diff a0db033 d249e43` = 47 个文件差异：远端**不含** `config.e2e.json`（已删除）、仍是旧版嵌套 `.github/workflows/ci.yml`、`jest.config.js` 为旧口径、缺 `route.test.ts` / `useSearch.test.tsx` / `OperationBuilder.test.ts` 等 09-14 新增用例 |

**平台决策（P6 前置，三选一）**：

| 方案 | 做法 | 优点 | 代价 |
|:----:|------|------|------|
| **A**（要"看到绿勾"时推荐） | 另建 GitHub 仓库并 `git remote add github <url>`，推 `master` → 现有 `ci.yml` / `pr-check.yml` 直接生效 | 零改造成本，日志 / 徽章 / artifact 即插即用 | 需要 GitHub 账号；代码存在两处远端 |
| **B** | 改用 **Gitee Go**：新增 `.workflow/<name>.yml`（Gitee 流水线规范），步骤复刻 `npm run verify` 与 `npx playwright test` | 全流程在 Gitee 内闭环 | 需按 Gitee Go 语法重写；并行 / 缓存 / artifact 能力与 Actions 不同；个人版有构建时长限制 |
| **C** | 保持本地门禁（`npm run verify` + `npx playwright test`），Gitee 仅作代码备份 | 零成本 | 拿不到"远端全绿"这一可展示证据，P6 原目标无法达成 |

> **结论**：不能用"采用远端版本"的方式来消除分叉 —— 远端 `d249e43` 会回退本次全部测试与 CI 成果。正确顺序是：**先选定 CI 平台（A/B/C）→ 再选择 `git merge`（保留双方历史）或以远端为基线重放本地改动（线性历史、内容更干净）→ 最后 push 验收**。

### 6.1 建立 remote 并触发首次 CI（🔴 必做，本计划最高优先级）

| ID | 任务 | 操作 | 验收 |
|----|------|------|------|
| 6.1.1 | 创建远端仓库并添加 remote | `git remote add origin <仓库URL>` | `git remote -v` 有两行输出 |
| 6.1.2 | 确认待推送分支与 workflow 匹配 | workflow 只监听 `master`；当前工作区在 `feat/exe-package-ready` | 决定：合并到 `master` 后推送，或临时把 `ci.yml` / `pr-check.yml` 的分支列表改为该特性分支 |
| 6.1.3 | 首次 push | `git push -u origin master` | Actions 页面出现 `CI Pipeline` 运行记录 |
| 6.1.4 | 观察 `build` job | 应依次通过 npm ci → typecheck → lint:strict → test:ci → build | 绿色 ✅（首个最可能的失败点：`npm ci` 与 `package-lock.json` 版本不一致） |
| 6.1.5 | 观察 `e2e` job | needs build → install chromium → test:e2e | 绿色 ✅（若失败见 §5 风险：首次 CI 的 E2E 时序） |
| 6.1.6 | 制造一次 PR 演练 | 开一个只改源码的 PR（非 `**.md`，以避开 `paths-ignore`） | `PR Check` 触发并绿 |

> **注意 `paths-ignore`**：两个 workflow 都忽略 `docs/**` 与 `**.md`。**纯文档提交不会触发 CI，这是设计而非故障**（见 SOP §6.1）。验收 CI 时必须改源码文件。

### 6.2 发布流水线 `release.yml`（🟡 建议）

**设计**（沿用 `docs/归档/计划书/CI_CD流水线/00_CI_CD流水线总体计划书_2026-07-12.md` 的阶段三设计稿，并按当前技术栈落地）：

```yaml
name: Release

on:
  push:
    tags: ['v*']          # 由 npm version / 手动 tag 触发
  workflow_dispatch:       # 支持手动触发

permissions:
  contents: write          # 创建 Release 需要

jobs:
  package:
    name: Package Portable EXE
    runs-on: windows-latest          # ★ 必须 Windows：electron-builder 打 Windows 包在 Linux 上需要 wine
    timeout-minutes: 30
    defaults:
      run:
        working-directory: MdToHtml
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          cache-dependency-path: MdToHtml/package-lock.json
      - name: Install dependencies
        run: npm ci
      - name: Verify gates              # 打包前再跑一次门禁，防止把红灯代码打成包
        run: npm run verify
      - name: Build Next.js
        run: npm run build
      - name: Build Portable EXE
        run: npm run build:electron     # electron-builder --win portable → release/
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: portable-exe
          path: MdToHtml/release/*.exe
      - name: Create GitHub Release
        uses: softprops/action-gh-release@v2
        with:
          files: MdToHtml/release/*.exe
          generate_release_notes: true
```

| ID | 任务 | 说明 |
|----|------|------|
| 6.2.1 | 新建 `.github/workflows/release.yml` | 内容如上（`runs-on: windows-latest`） |
| 6.2.2 | 确认打包配置 | `package.json` 的 `build` 段已就绪：`target: portable`、`asar: false`、`sign: false`、产物名 `MdToHtml Pro-Portable-1.0.0.exe`（`directories.output: release`） |
| 6.2.3 | 版本号规范 | 唯一来源 `MdToHtml/package.json` 的 `version`；发版用 `npm version patch|minor`（会自动 commit + tag，tag 再 push 即触发） |
| 6.2.4 | 本地预演 | `npm run build && npm run build:electron`，确认 `release/` 出现 exe 且能启动 |
| 6.2.5 | 首次真实发版 | `git push origin v1.0.0`，确认 Release 页面自动挂载 exe |

> 与既有规范一致：`docs/工程目录与版本规范.md` 第 3 节已规定"`release/` 只保留最新一次打包结果""交付前必须重新打包"；本流水线把这两条从"人工纪律"变为"自动约束"。`release/` 已在根 `.gitignore` 中，不会污染仓库。

## 六、风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 首次 CI 中 E2E 时序不稳定（本地 3 workers，CI 1 worker + retries 2） | build job 绿、e2e job 红 | 保留 `retries: 2` + `trace: on-first-retry`；失败先看 artifact 里的报告与截图再改断言，**不要**把 `continue-on-error` 加回去 |
| `npm ci` 与 `package-lock.json` 不一致 | 首个 job 即失败 | 提交前本地跑一次 `npm ci` 验证；注意仓库根目录那个 **87 字节的空壳 `package-lock.json`** 不参与 CI（CI 用的是 `MdToHtml/package-lock.json`），但建议按 G8 裁决清理以免误导 |
| electron-builder 在 Linux runner 上打 Windows 包失败 | 发布流水线红 | 已规避：`release.yml` 使用 `runs-on: windows-latest` |
| 打包体积 / 时间超限 | 30min 超时 | 已设 `timeout-minutes: 30`；必要时先上传 artifact 再创建 Release |
| Codecov 需要额外账号与 token | 8.1 阻塞 | 可先做 8.1.2 徽章（CI 徽章不需要 token），Codecov 延后 |
| 阈值抬升触发"为了过门禁而改口径"的诱惑 | 门禁失去意义 | SOP §4.2 明确禁止；阈值改动必须单独提交并在提交信息中写明 x→y |
