## 三、本次新增与更正的事实（Plan 01 未涵盖）

### 3.1 隐患一（已修）：`.gitignore` 裸 `data/` 屏蔽源码 → 漏入库 → CI 必红

| 项 | 内容 |
|----|------|
| 现象 | 干净检出后 `npm run typecheck` 报 `TS2307: Cannot find module '@/data/editor-defaults'` |
| 根因 | 根 `.gitignore` 写的是**裸 `data/`**（匹配任意层级同名目录），把源码目录 `MdToHtml/src/data/` 一并屏蔽 → `editor-defaults.ts`（8.7 KB，被 `MarkdownEditor.tsx` 引用）**从未入库** |
| 教训 | `.gitignore` 不写裸目录名（`data/`、`build/`、`out/`、`temp/`…），除非确认全仓库无同名源码目录；**"本地一直能跑" ≠ "CI 能跑"，只有干净检出能暴露漏水** |
| 处置 | 改为显式 `MdToHtml/data/` + 补入该源码（提交 `6c5e8dc`）；系统排查手法记录为 `git check-ignore -v <文件>` / `git ls-files --others --ignored --exclude-standard` |

### 3.2 隐患二（已修）：`upload-artifact@v4` 默认跳过隐藏目录 → 步骤绿、产物空

| 项 | 内容 |
|----|------|
| 现象 | run #1 的 `Upload Build Artifact` 结论 success，但 artifacts 里只有 `playwright-report`，**没有 `next-build`** |
| 根因 | `upload-artifact@v4` 默认**跳过隐藏文件/目录**，而 path 指向的 `.next/` 是点开头；默认 `if-no-files-found: warn` 只警告不报错 → "绿得看不出来" |
| 处置 | 补 `include-hidden-files: true`，并把 `if-no-files-found` 收紧为 `error`（提交 `a3cc700`）；run #2 实证 `next-build` 28.52 MB 已上传 |

### 3.3 风险（未修，已文档化）：本地 E2E 多 worker 并行会互相干扰

`playwright.config.ts` 的 `workers: process.env.CI ? 1 : undefined` → 本地按 CPU 开多 worker，而 `fullyParallel: false` **只禁止同一文件内并行**，不同 spec 文件仍并行，同时读写同一份隔离目录 `.e2e-tmp/`：

| 场景 | 实测 |
|------|------|
| 干净检出 + 3 workers（非 CI） | ❌ 6 passed / 1 failed（"导入本地文件 → 出现在文档列表"） |
| 干净检出 + `CI=true`（1 worker + retries 2） | ✅ **7/7**（28.1s） |
| GitHub runner（同上 CI 语义） | ✅ 7/7（39.7s） |

> **更正**：旧报告"E2E 已 100% 稳定"属**绝对化表述**，应限定为"CI 语义（`CI=true`、1 worker）下稳定"。本地以多 worker 跑全量时存在偶发失败，处置见 §四 B 阶段。

## 六、风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 覆盖率门禁余量仅 **1.5pp** | 新增未覆盖代码即红掉 CI | 新增功能同步补测试；确需调整阈值时按 SOP §4.2 重新标定（须有实测依据 + 单独提交） |
| 孤立代码占分母 **5.1%** | 覆盖率被稀释、读者误判"系统只测了 20%" | 先按 2.2.3 裁决：删除，或在 `collectCoverageFrom` 中显式排除（排除项必须附理由注释） |
| E2E 依赖中文文案 | 文案一改用例静默失效（假绿/假红） | 2.2.1 全量换 `data-testid` |
| 本地多 worker 跑 E2E 偶发失败 | 误判为代码回归、浪费排查时间 | 2.2.2 收敛为 1 worker，或明确文档化"全量请用 `CI=true`" |
| `release.yml` 首次运行的不确定性（electron 下载 / 打包工具链） | 发布流水线红 | 先 `workflow_dispatch` 手动跑一次（只出 artifact、不建 Release）验证工具链，再推 tag |
| 覆盖率爬坡出现"为数字而写测试" | 测试形式化、门禁失去意义 | 用例必须断言真实行为（参照 Plan 00 §8.2：把发现的实现局限如实写成"已知局限"用例）；禁止只跑不断言 |
| Codecov 需要外部账号 | D 阶段阻塞 | 先用自研方案（artifact 留档 + Actions Summary）顶上，Codecov 列为可选 |
| `next-build` 产物 28.5 MB/次 | 消耗 artifact 额度 | 按 2.1.4 决策去留 |

## 七、执行顺序与工时汇总

```
① 2.1.1–2.1.3  发布链路真实验收（推 v* tag → 看 Release 与 exe）   1–2h  ← 唯一能把 P6 推到"可交付"的动作
② 2.2.1 + 2.2.2  E2E 去中文文案 + 并行收敛                          2–3h  ← 提高门禁可信度，避免后续假红假绿
③ 2.3.1         覆盖率第一档（cache-manager 8 例 + trash-manager 6 例） 3–4h  ← 补 P0 欠账 G4，性价比最高
④ 2.2.4 + 2.2.3  文档同步 + 残留裁决                                 1–2h
⑤ 2.3.2 + 2.3.3  覆盖率第二、三档（api 路由 / services / 导出引擎）   9–11h
⑥ 2.1.5         PR 门禁演练                                          0.5h
⑦ 2.4.x         覆盖率趋势 + 失败通知                                2–3h
⑧ 2.3.4         覆盖率第四档（→ 60%）                                8–12h  ← 长期项，与功能开发并行
```

**关键路径**：① 独立无阻塞（应先做）；③ 与 ⑤ 是同一条覆盖率线的两段，**必须"先补测试、再抬阈值"**，禁止倒序。

## 八、范围外（明确不做）

| 项 | 原因 |
|----|------|
| 视觉回归测试（截图比对基线） | UI 迭代频繁，基线维护成本高于收益；功能正确性已由 E2E 兜底 |

| 迁移或删除 Gitee 流水线内容（`.workflow/ci.yml`） | 已退役但保留备查；删除需单独确认 |
