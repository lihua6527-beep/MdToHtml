> **分析日期**：2026-07-12  
> **核心问题**：频繁重构导致测试失效，如何设计测试体系在重构中保持有效？  
> **核心理念**：**不是不写测试，而是写对层次的测试**。

## 一、你的顾虑完全正确

### 1.1 "测试在快速迭代下失准失灵" 的根因

```
常见错误模式：

  写了一大堆测试 → 重构渲染引擎 → 
  
  ① 单元测试挂了（mocked 的接口变了）
  ② 集成测试挂了（组件 props 变了）
  ③ E2E 测试也挂了（DOM 结构变了）
  
  → 结论：测试全是负担，重构 1 天，改测试 2 天
  → 结果：再也不写测试了

根因分析：
  不是"测试没用"，而是"测试写在错误的层次上"。
```

### 1.2 本系统各模块的重构风险矩阵

| 模块 | 重构概率 | 重构影响范围 | 应该写的测试层次 |
|------|---------|-------------|----------------|
| **CHD 解析器** | **高**（你刚重构成 DFA） | 底层，被渲染器/编辑器依赖 | **单元测试**（纯函数，重构后只需改期望值） |
| **CHD 渲染引擎** | **高**（你正在考虑） | UI 层，被预览面板依赖 | **E2E + 视觉回归**（测试不关心内部实现） |
| **操作引擎** | **中**（正在做） | 服务层，被撤销/重做/AI 依赖 | **单元测试 + E2E** |
| **缓存管理器** | **低** | 独立模块 | **单元测试** |
| **编辑器 UI** | **中**（样式/交互调整） | 用户界面 | **E2E 测试**（不关心 CSS 类名，关心功能正确） |
| **文件系统** | **低** | 基础服务 | **集成测试** |
| **AI 服务层** | **中**（API 变更） | 对外接口 | **单元测试（mock API）+ E2E** |

## 二、核心解决方案：按层次选择测试策略

### 2.1 测试金字塔（针对本系统的定制版）

```
                  ┌──────────┐
                  │  E2E 测试 │   ← 重构渲染引擎/UI 时 ✅ 不需要改
                  │  稳定层   │     因为 E2E 只关心"用户看到的结果"，
                  └──────────┘     不关心内部组件叫什么名、怎么渲染的
                         
              ┌──────────────────┐
              │   集成测试         │  ← 重构服务层时 ✅ 可能需要少量调整
              │   （中等稳定）      │     但改了接口后只需调 mock 数据
              └──────────────────┘
         
     ┌──────────────────────────────┐
     │  单元测试（纯函数层）         │  ← 重构时 ❌ 需要改，但改得少
     │  CHD解析器 / 缓存 / 工具库    │     因为纯函数输入输出明确
     └──────────────────────────────┘

关键原则：
  ✅ 底层模块 → 单元测试（纯函数，输入输出稳定）
  ✅ 上层模块 → E2E 测试（不关心实现，只关心结果）
  ❌ 避免：中间层写大量集成测试（重构时最脆弱）
```

### 2.2 具体到你的重构场景

#### 场景一：重构渲染引擎（你提到的）

```
当前状态：
  渲染引擎负责 "CHDBlocks[] → DOM 卡片"
  你的焦虑：重构完 renderer，测试全挂

正确策略：
  
  ① E2E 测试（不依赖 renderer 内部实现）：
     "编辑器输入 CHD 内容 → 预览出现卡片"
     → 重构渲染引擎后 ✅ 不需要改
     → 因为测试验证的是"最终结果"，不是"渲染过程"
  
  ② 视觉回归测试（截图对比）：
     "重构后卡片外观是否和之前一样？"
     → 重构后 ✅ 只需更新基线截图（一条命令）
  
  ③ 不需要写：
     renderer.renderBlocks() 的单元测试
     → 因为你一重构测试就挂，测试反而成为包袱
```

#### 场景二：重构 CHD 解析器（你刚做完）

```
正确做法（你实际做的）：
  解析器是纯函数：string → CHDBlock[]
  14 个单元测试覆盖各种边界情况
  → 重构前后，测试只需改期望值，不涉及 mock 和依赖注入
  → ✅ 这是正确的单元测试写法

已验证：你的 14 个测试在这次 DFA 重构后仍然有效
```

### 2.3 哪些测试最容易在重构中失效（以及如何避免）

| 测试类型 | 重构后失效率 | 为什么 | 怎么做 |
|---------|------------|--------|--------|
| **E2E 测试（功能验证）** | **低** | 只测"用户能看到的结果" | 优先写 |
| **E2E 测试（视觉回归）** | **低** | 截图对比，改 UI 后跑一次更新基线 | 需要手动确认 |
| **纯函数单元测试** | **中** | 输入输出明确，重构后改期望值即可 | 值得写 |
| **React 组件单元测试** | **高** | 改 props/state 结构就挂 | **不推荐写** |
| **集成测试（多模块联调）** | **高** | 中间任何模块接口变化就挂 | 少写，用 E2E 替代 |
| **Mock 过多的测试** | **极高** | 重构后 mock 的接口变了 | **禁止写** |

## 四、推荐方案：E2E 优先 + 纯函数单元测试

### 4.1 对本系统最合理的测试策略

```
不是"等稳定了再写"，而是：

写对层次的测试 → 重构时只需要改底层测试 → 上层 E2E 自动保护

┌──────────────────────────────────────────────────────────────────┐
│  第一优先：E2E 测试（5 个核心流程）                              │
│  → 重构渲染引擎时不需要改                                        │
│  → 重构编辑器 UI 时不需要改                                      │
│  → 重构 AI 服务层时不需要改（只要接口兼容）                      │
├──────────────────────────────────────────────────────────────────┤
│  第二优先：纯函数单元测试（解析器/缓存/工具库）                  │
│  → 重构时只需要调整期望值（输入输出不变）                        │
│  → 重构成本：每 10 个测试约改 3 个期望值                         │
├──────────────────────────────────────────────────────────────────┤
│  谨慎写：React 组件测试 / Hooks 测试                             │
│  → 重构时几乎必定失效                                            │
│  → 除非组件极其稳定（如主题切换按钮），否则不值得                │
├──────────────────────────────────────────────────────────────────┤
│  避免写：Mock 过多的测试                                          │
│  → "为了测试而造的 mock 数据"在重构后 90% 需要重写               │
│  → 宁愿不写，也不写虚假的测试                                    │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 "先写 E2E 再重构" 的工作流

```
你的重构工作流（推荐）:

  ① 写 E2E 测试（覆盖重构前后的功能）
     └→ 重构后 E2E 不需要改，它就是"功能不变"的证明

  ② 写纯函数单元测试（覆盖边界情况）
     └→ 重构后只需要改少数期望值

  ③ 开始重构
     └→ 跑 E2E → 通过 → 重构正确 ✅
     └→ 跑单元测试 → 失败 → 更新期望值 ⚡

  ④ 更新单元测试期望值
     └→ E2E 仍然保护你没有破坏用户功能

  ⑤ 完成 ✔
```

## 六、总结

| 问题 | 答案 |
|------|------|
| "重构后测试会失效吗？" | **会，但只有底层单元测试会** |
| "那还要写测试吗？" | **要，但只写对的层次** |
| "E2E 测试在重构时会失效吗？" | **不会**，因为只测"用户看到的结果" |
| "纯函数单元测试在重构时会失效吗？" | **会，但改期望值即可，比重写便宜** |
| "React 组件测试在重构时会失效吗？" | **几乎一定，所以不写** |
| "什么时候写测试？" | **现在就可以写 E2E，不会因为重构而浪费** |

**最终建议**：
1. 现在就把这 3 个 E2E 测试跑通（它们不会因为重构渲染引擎而失效）
2. 操作引擎做完后补单元测试（当时补，别等）
3. 渲染引擎重构时：E2E 保护你 → 重构完跑一遍 → 过了就是正确
4. **不要写"为了测试而测试"的 mock 密集型测试**
