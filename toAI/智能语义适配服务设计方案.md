# 智能语义适配服务设计方案 (Intelligent Semantic Adaptation Service)

> **版本**: v1.0
> **日期**: 2026-02-05
> **状态**: 已归档 (Implemented)
> **关联**: `portable_ml_package/llm_service/`

## 1. 需求背景与核心洞察 (Background & Insight)

### 1.1 初始误区
早期的需求设计试图将所有长文本机械地拆分为 3-4 个固定字数的片段。这种“一刀切”的策略在实际处理中存在严重问题：
- **语义破碎**: 强行拆分短小精悍的总结句，导致信息支离破碎。
- **逻辑断裂**: 对叙事性强的长文直接截断，丢失了上下文关联。
- **机械化**: 缺乏对文本实际形态的感知。

### 1.2 核心洞察 (Requirements Analyst Report)
作为需求分析师，我们重新定义了业务目标：**不是“拆分”，而是“语义适配” (Semantic Adaptation)**。
我们的核心任务是将不同形态的用户输入（短句、列表、长叙事），平滑地装入 CHD 协议定义的“原子化卡片容器”中。

---

## 2. 自适应策略设计 (Adaptive Strategy)

基于上述洞察，我们设计了一套**三级决策漏斗 (Three-Level Decision Funnel)**，取代单一的拆分逻辑。

### Level 1: 保持 (Check & Keep)
*   **场景**: 用户输入了一句简练的总结（如“系统延迟降低了 30%”）。
*   **判定**: 长度 < 50字 **且** 语义单一。
*   **决策**: **不拆分**。
*   **动作**: 仅进行 Markdown 格式清洗和关键词高亮 (`<strong>`)。
*   **价值**: 尊重短句的完整性，避免过度工程化。

### Level 2: 物理拆分 (Physical Split)
*   **场景**: 用户输入了一段包含明确逻辑的列表（如“第一...第二...；首先...其次...”）。
*   **判定**: 长度 > 50字 **且** 包含结构化连接词。
*   **决策**: **按逻辑点拆分**。
*   **动作**: 根据标点或连接词将长句物理切割为 2-4 个片段。
*   **价值**: 将复杂长句转化为符合 CHD 粒度的卡片，是最理想的转化路径。

### Level 3: 概括重组 (Summarize & Reconstruct)
*   **场景**: 用户输入了一大段冗长的叙事或复杂的背景描述，没有明显的分割点。
*   **判定**: 长度 > 100字 **且** 语义缠绕。
*   **决策**: **先概括，后拆分**。
*   **动作**:
    1.  **Extract**: 让 LLM 提炼出 3 个核心要点 (Key Takeaways)。
    2.  **Generate**: 基于这 3 个要点重写为独立的原子化片段。
*   **价值**: 解决“无法拆分”的死胡同，通过“语义降维”适配容器标准。

---

## 3. 系统架构与实现 (Architecture & Implementation)

### 3.1 微服务架构
该服务被封装在 `portable_ml_package/llm_service/` 中，作为独立的可移植模块。

*   **入口**: `app.py` (FastAPI + Ollama)
*   **协议**: `POST /api/segment`
*   **约束**: `constraint.md` (运行时动态注入)

### 3.2 提示词工程 (Prompt Engineering)
System Prompt 被重新设计为决策树模式：

```python
# 伪代码逻辑
if len(text) < 50 and is_atomic(text):
    return Strategy.KEEP
elif has_list_structure(text):
    return Strategy.SPLIT
else:
    return Strategy.SUMMARIZE
```

### 3.3 接口定义
响应结构中新增了 `strategy_used` 字段，提供处理依据的可解释性。

```json
{
  "strategy_used": "Summarize", // Keep | Split | Summarize
  "segments": [
    {
      "title": "主题+结论",
      "text": "原子化内容...",
      "char_count": 25
    }
  ],
  "fixed_markdown": "GFM 规范文本",
  "latency_ms": 750.0
}
```

---

## 4. 业务约束 (Constraints)

所有处理均需遵循以下红线，定义于 `constraint.md`：
1.  **原子化区间**: 片段字数控制在 20-40 字。
2.  **禁止广告**: 严禁营销词汇。
3.  **引用保留**: 必须保留 `[1]` 等引用标注。
4.  **格式规范**: 严格符合 GFM (GitHub Flavored Markdown)。

---

## 5. 总结

本方案标志着系统从“机械式工具”向“智能适配引擎”的转变。通过引入自适应策略，我们确保了无论用户输入何种形态的文本，系统都能产出高质量、符合 CHD 协议的结构化文档。
